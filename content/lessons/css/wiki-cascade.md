# 캐스케이드와 상속

## 학습 목표

- 한 요소의 같은 속성에 선언이 겹칠 때 캐스케이드가 명시도보다 먼저 비교하는 기준을 설명할 수 있습니다.
- 명시도의 세 칸과 작성 순서로 앞선 조건이 같은 선언 가운데 이기는 선언을 고를 수 있습니다.
- 자식에 선언이 없을 때 부모 값을 이어받는 상속과 `inherit`·`initial`·`unset`의 차이를 설명할 수 있습니다.
- 스타일이 예상과 다를 때 겹친 선언의 문제인지 상속의 문제인지 나눠 원인을 찾을 수 있습니다.

## 먼저 확인할 개념

[CSS 기초: 적용 방법과 선택자](#/learn/css/wiki-css-basics)에서 한 요소가 여러 선택자와 일치할 수 있음을 먼저 확인해 보세요.

## 캐스케이드란

캐스케이드(cascade)는 한 요소의 같은 속성에 여러 선언이 겹칠 때 우선순위를 비교해 하나를 고르는 과정입니다.
한 요소는 여러 선택자와 동시에 일치할 수 있습니다.
그런데 글자색 같은 속성은 한 요소에 값이 하나만 있어야 합니다.
그래서 브라우저는 겹친 선언을 정해진 순서로 비교해 남길 값을 고릅니다.

반대로 어떤 요소에는 그 속성의 선언이 하나도 없을 수 있습니다.
이때는 부모의 값을 이어받거나 속성마다 정해진 초기값을 씁니다.
부모의 값을 이어받는 것을 상속이라고 합니다.
한 요소의 속성값은 이 두 과정을 거쳐 정해지므로 이 문서에서 함께 살펴봅니다.

예를 들어 앞 문서의 책모임 카드에 오늘 모임 문단이 있다고 해 보겠습니다.

```html
<article class="meeting-card">
  <h2>저녁 책모임</h2>
  <p id="today" class="notice">오늘 저녁 7시에 만납니다.</p>
</article>
```

```css
p { color: gray; }
.notice { color: navy; }
#today { color: darkgreen; }
```

세 선택자가 같은 문단과 일치하지만 글자색은 하나로 정해져야 합니다.
이 문서는 이 카드 하나로 어떤 선언이 이기는지와 선언이 없을 때 값이 어디서 오는지를 차례로 살펴봅니다.

## 캐스케이드의 비교 순서

브라우저는 겹친 선언을 한꺼번에 점수로 비교하지 않습니다.
여러 기준을 정해진 순서대로 하나씩 보고 앞 기준에서 우선순위가 정해지면 뒤 기준은 보지 않습니다.

선택자와 조건이 실제 요소에 맞는지 먼저 확인합니다.
후보끼리는 출처·중요도·레이어처럼 명시도보다 앞선 기준을 비교합니다.
그 조건이 같을 때 명시도를 비교하고 명시도까지 같으면 나중에 작성된 선언이 이깁니다.

| 순서 | 기준 | 뜻 |
| --- | --- | --- |
| 1 | 출처와 중요도 | 브라우저 기본·사용자·사이트 작성자 가운데 누가 썼는지와 `!important`가 있는지 |
| 2 | 직접 적은 스타일 | 요소의 `style` 속성에 적은 선언인지 |
| 3 | 레이어 | `@layer`로 나눈 묶음의 순서 |
| 4 | 명시도 | 선택자가 얼마나 구체적인지 |
| 5 | 작성 순서 | CSS에서 나중에 나오는지 |

브라우저 기본 스타일·사용자 스타일·사이트 작성자 스타일은 출처가 다릅니다.
책모임 카드처럼 사이트를 만드는 사람이 쓴 규칙은 모두 작성자 스타일입니다.
그래서 작성자 규칙끼리 비교할 때는 중요도부터 봅니다.

> [!note]- 이 표가 캐스케이드 전체 순서인가요?
> 전체 캐스케이드에는 애니메이션·전환·`@scope`·Shadow DOM 같은 기준도 들어 있습니다.
> 이 문서의 예제는 같은 작성자가 쓴 일반 규칙끼리의 비교이므로 위 표의 기준만으로 설명할 수 있습니다.
> 애니메이션이나 전환을 쓰는 규칙을 만나면 공식 명세의 캐스케이드 정렬 순서를 확인합니다.

뒤쪽 기준부터 살펴보겠습니다.
대부분의 규칙은 출처·중요도·레이어가 같기 때문에 명시도와 작성 순서를 비교해 우선순위를 정합니다.

## 명시도와 작성 순서

명시도(specificity)는 선택자가 얼마나 구체적인지를 세 칸으로 나타낸 값입니다.
십진수 점수 하나로 더하지 않고 왼쪽 칸부터 비교합니다.

```text
(ID 개수, 클래스·속성·가상 클래스 개수, 요소·가상 요소 개수)
```

| 선택자 | 명시도 |
| --- | --- |
| `p` | `(0, 0, 1)` |
| `.notice` | `(0, 1, 0)` |
| `article .notice` | `(0, 1, 1)` |
| `#today` | `(1, 0, 0)` |

왼쪽 칸이 크면 오른쪽 칸은 보지 않습니다.
클래스를 여러 개 이어 붙여도 ID 칸으로 올림되지 않습니다.
그래서 `.a.b.c.d`처럼 클래스가 많은 선택자도 `#today` 하나를 이기지 못합니다.

책모임 문단에 세 가지 규칙 묶음을 따로 적용해 보겠습니다.
세 칸의 문단이 각각 무슨 색일지 먼저 예상해 보세요.

![같은 책모임 문단에 규칙 묶음 세 개를 적용한 결과다. 첫째 p와 notice와 today 세 선택자가 일치하면 today가 이겨 초록색이다. 둘째 today 규칙을 먼저 적고 notice를 나중에 적어도 today가 이겨 초록색이다. 셋째 notice 규칙 두 개가 겹치면 나중에 적은 crimson이 이겨 빨간색이다.](content/assets/css/cascade-specificity.png)

첫째 칸은 ID 칸이 가장 큰 `#today`가 선택되므로 글자색이 darkgreen입니다.
둘째 칸에서는 `.notice`가 나중에 나오지만 여전히 darkgreen입니다.
작성 순서는 명시도가 같을 때만 비교하기 때문입니다.

```css
.notice { color: navy; }
.notice { color: crimson; }
```

셋째 칸처럼 앞선 조건과 명시도가 같을 때만 뒤의 crimson이 선택됩니다.
여기서 작성 순서는 CSS에 선언을 적은 순서를 말합니다.
HTML의 `class="notice urgent"`에서 클래스 이름을 적은 순서나 `urgent` 같은 이름의 뜻은 우선순위와 상관없습니다.
클래스가 재사용하기 쉽다는 장점도 캐스케이드의 승패 기준이 아닙니다.

> [!note]- 두 선언이 겹치면 둘 다 무효가 되나요?
> 같은 속성에 유효한 선언이 여러 개 적용되는 것은 정상입니다.
> 브라우저는 캐스케이드로 그중 하나를 고르며 겹쳤다는 이유로 선언을 버리지 않습니다.

명시도와 작성 순서는 비교 순서의 마지막 두 단계입니다.
이제 명시도보다 먼저 우선순위를 정하는 기준을 살펴보겠습니다.

## 중요 선언과 style 속성

`!important`는 명시도 점수를 높이지 않고 선언을 다른 중요도 그룹에서 비교하게 합니다.
요소의 `style` 속성에 직접 적은 선언은 같은 작성자의 일반 선언 가운데 선택자 규칙보다 우선합니다.
`@layer`는 스타일 묶음의 순서를 정하며 이 순서도 명시도보다 먼저 비교합니다.

세 칸에서 모두 `#today` 규칙이 함께 있습니다.
ID 규칙이 이길지 먼저 예상해 보세요.

![명시도보다 먼저 비교하는 기준 세 가지다. 첫째 notice에 navy important를 붙이면 today의 darkgreen을 이겨 남색이다. 둘째 문단의 style 속성에 color purple을 적으면 today 규칙을 이겨 보라색이다. 셋째 base 레이어의 today와 components 레이어의 notice가 겹치면 뒤 레이어인 components의 navy가 이겨 남색이다.](content/assets/css/cascade-important.png)

세 칸 모두 `#today`의 darkgreen이 졌습니다.
첫째 칸의 navy는 중요 선언이어서 일반 선언인 darkgreen보다 먼저 비교됩니다.
`!important`가 클래스 선택자의 ID 개수를 늘린 것이 아닙니다.
나중에 적은 일반 선언이 앞선 중요 선언을 지우지도 않습니다.

둘째 칸의 purple은 `style` 속성에 직접 적은 선언이어서 선택자 규칙을 이깁니다.
셋째 칸은 `@layer base, components;`로 레이어 순서를 먼저 정했습니다.
같은 작성자의 일반 선언에서는 뒤 레이어가 앞서므로 명시도가 작은 `.notice`가 이깁니다.

다만 셋 다 언제나 이기는 것은 아닙니다.
예를 들어 선택자 규칙의 `!important` 선언은 `style` 속성의 일반 선언을 이깁니다.
그래서 규칙이 예상과 다르면 `!important`부터 붙이지 않습니다.
개발자 도구에서 같은 속성의 이긴 선언을 찾고 어떤 비교 기준이 달랐는지 확인합니다.

> [!note]- 레이어 밖의 선언과 중요 선언의 레이어 순서
> 같은 작성자의 일반 선언에서는 레이어 밖에 적은 선언이 레이어 안의 선언보다 앞섭니다.
> 중요 선언에서는 레이어 순서가 반대가 되어 앞 레이어의 중요 선언이 이깁니다.
> 작은 예제에서 레이어를 쓰지 않는다면 지금은 비교 범위만 알아 둡니다.

지금까지는 문단에 선언이 여러 개 있을 때를 보았습니다.
그렇다면 문단에 color 선언이 하나도 없으면 글자색은 어디서 올까요?

## 상속과 초기값

상속은 자식에 값이 직접 정해지지 않았을 때 상속되는 속성이 부모의 계산된 값을 이어받는 과정입니다.
계산된 값은 부모에서 캐스케이드가 고른 값을 브라우저가 쓸 수 있는 형태로 바꾼 값입니다.
상속되는 속성인지는 속성마다 명세에 정해져 있습니다.
상속되지 않는 속성은 부모와 상관없이 그 속성의 초기값을 씁니다.

이번에는 제목과 문단에 color나 border를 직접 정하지 않았습니다.
카드에만 규칙을 추가했을 때 자식에도 테두리가 생길지 먼저 예상해 보세요.

```css
.meeting-card {
  color: navy;
  border: 2px solid crimson;
}
```

![왼쪽은 카드에 규칙이 없어 제목과 문단이 기본 검은색이다. 오른쪽은 카드에 color navy와 border 2px solid crimson을 준 결과로 제목과 문단의 글자가 남색이 되었고 빨간 테두리는 카드 바깥에만 있고 제목과 문단에는 생기지 않았다.](content/assets/css/inherit-color-border.png)

color는 상속되므로 제목과 문단도 같은 글자색을 씁니다.
반면 border는 상속되지 않아 자식마다 테두리가 생기지 않습니다.
부모의 border 색이 자식의 글자색으로 바뀌어 전해지지도 않습니다.

부모가 작성한 CSS 문장 전체를 자식에게 복사하는 것은 아닙니다.
글자 모양에 관한 속성은 상속되는 경우가 많고 박스 모양에 관한 속성은 상속되지 않는 경우가 많습니다.
그래도 예외가 있으므로 속성 문서의 상속 여부를 확인합니다.

상속은 속성마다 자동으로 정해져 있습니다.
그런데 이 동작을 한 요소에서만 바꾸고 싶을 때도 있습니다.

## inherit·initial·unset 사용법

`inherit`·`initial`·`unset`은 모든 속성에 쓸 수 있는 값으로 그 속성의 값을 어디서 가져올지 직접 정합니다.

| 값 | 동작 |
| --- | --- |
| `inherit` | 원래 상속되는 속성인지와 관계없이 부모의 계산값을 사용합니다 |
| `initial` | 해당 속성의 명세에 정해진 초기값을 사용합니다 |
| `unset` | 원래 상속되는 속성이면 `inherit` 아니면 `initial`처럼 작동합니다 |

카드에는 앞 절과 같은 color와 border가 있습니다.
문단에 세 값을 하나씩 적용하면 글자색과 테두리가 어떻게 될지 예상해 보세요.

![카드에 color navy와 빨간 테두리가 있을 때 문단에 세 값을 적용한 결과다. 첫째 border inherit를 준 문단에는 카드와 같은 빨간 테두리가 생겼다. 둘째 color initial을 준 문단만 글자가 검은색이다. 셋째 color unset과 border unset을 준 문단은 글자가 남색이고 테두리가 없다.](content/assets/css/inherit-keywords.png)

첫째 칸의 `inherit`는 원래 상속되지 않는 border도 부모 값을 가져오게 했습니다.
둘째 칸의 `initial`은 color의 초기값을 써서 부모의 navy 대신 기본 글자색이 되었습니다.
셋째 칸의 `unset`은 속성마다 다르게 동작했습니다.
color는 상속되는 속성이라 부모 값을 받았고 border는 상속되지 않는 속성이라 초기값인 테두리 없음이 되었습니다.

같은 원리로 부모에 `margin-left: 24px`가 있고 자식에 `margin-left: unset`을 주면 자식의 왼쪽 바깥 여백은 0입니다.
margin-left는 상속되지 않는 속성이고 초기값이 `auto`가 아니라 0이기 때문입니다.

`initial`은 브라우저가 h1이나 ul에 제공한 기본 모양으로 돌아가라는 뜻이 아닙니다.
예를 들어 h1에 `font-size: initial`을 주면 제목 크기가 아니라 font-size의 초기값인 보통 글자 크기가 됩니다.
요소 종류의 기본 스타일과 속성 자체의 초기값은 다르기 때문입니다.

> [!note]- 이름 붙인 값도 상속될까요?
> 반복되는 값에 `--`로 시작하는 이름을 붙이고 `var()`로 사용할 수 있습니다.
> 이런 사용자 정의 속성도 기본적으로 상속됩니다.
> 그래서 `:root`에 `--color-accent: #315efb;`를 적으면 모든 자손이 `color: var(--color-accent);`로 그 값을 쓸 수 있습니다.
> 이름은 대소문자를 구분하며 이름만 붙였다고 색이나 단위 형식이 자동으로 검증되는 것은 아닙니다.

이제 한 요소의 속성값이 정해지는 두 과정을 모두 보았습니다.
마지막으로 스타일이 예상과 다를 때 두 과정을 어떻게 나눠 확인하는지 정리해 보겠습니다.

## 캐스케이드와 상속의 활용

스타일이 예상과 다를 때는 먼저 그 요소에 그 속성의 선언이 있는지부터 봅니다.
선언이 있으면 캐스케이드의 문제이고 선언이 없으면 상속이나 초기값의 문제입니다.

| 상황 | 확인할 것 | 고치는 방법 |
| --- | --- | --- |
| 같은 속성의 선언이 여러 개 있음 | 이긴 선언과 진 선언 사이에서 달랐던 비교 기준 | 선택자를 역할에 맞게 고치거나 규칙 위치를 정리합니다 |
| 선언이 있는데 이기지 못함 | 중요도·`style` 속성·레이어 | `!important`를 더하기 전에 앞선 기준을 찾습니다 |
| 선언이 없는데 색이 바뀜 | 어느 조상에게서 상속되었는지 | 원하는 조상이나 자식에 값을 직접 정합니다 |
| 부모 값이 자식에게 오지 않음 | 그 속성이 상속되는 속성인지 | 필요하면 `inherit`를 적습니다 |

개발자 도구에서 자식의 최종 color를 확인한 뒤 어느 조상에게서 왔는지 추적해 봅니다.
Computed 창에서 속성을 펼치면 그 값을 만든 규칙을 볼 수 있습니다.
자식에 직접 정한 color가 있다면 부모에게서 자동으로 이어받는 경우와 나누어 확인합니다.

책모임 카드에서 긴급 모임 문단만 다른 색으로 바꾼다고 해 보겠습니다.
긴급 문단에만 있는 클래스를 이으면 명시도가 커져 일반 문단의 색은 그대로 두고 긴급 문단만 바꿀 수 있습니다.

```css
.notice { color: navy; }
.notice.urgent { color: crimson; }
```

이처럼 원하는 요소만 고르는 선택자를 먼저 찾으면 `!important` 없이도 캐스케이드를 예상대로 쓸 수 있습니다.

## 정리

- 캐스케이드는 출처·중요도·`style` 속성·레이어를 명시도보다 먼저 비교하고 그 조건이 같을 때 명시도를 거쳐 작성 순서로 하나를 고릅니다.
- 명시도는 ID·클래스·요소의 세 칸을 왼쪽부터 비교하며 `!important`는 명시도를 더하지 않고 중요도 그룹을 바꿉니다.
- 선언이 없으면 상속되는 속성은 부모 값을 이어받고 나머지는 초기값을 쓰며 `inherit`·`initial`·`unset`으로 이 동작을 직접 정합니다.

## 핵심 질문 답

한 요소의 같은 속성에 선언이 겹치면 캐스케이드가 출처·중요도·`style` 속성·레이어를 먼저 비교합니다.
그 조건이 같으면 명시도의 세 칸을 왼쪽부터 비교하고 그것도 같으면 나중에 작성된 선언을 고르므로 마지막 줄이나 큰 명시도가 언제나 이기지는 않습니다.
선언이 하나도 없으면 상속되는 속성은 부모의 계산값을 이어받고 상속되지 않는 속성은 초기값을 씁니다.
`inherit`는 부모 값을 `initial`은 속성의 초기값을 쓰고 `unset`은 그 속성의 상속 여부에 따라 둘 중 하나처럼 동작합니다.
