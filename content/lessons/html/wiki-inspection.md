# HTML 검증: 문법·의미·접근성 점검

## 학습 목표

문법·의미·접근성 문제에 맞는 검사 방법을 고르고 수정한 결과를 다시 확인할 수 있습니다.

## 한줄 요약

Checker로 문법과 콘텐츠 모델을 확인하고 의미·대체 정보·키보드 사용은 문맥과 실제 조작으로 다시 확인합니다.

## 먼저 확인할 개념

[시맨틱 HTML: 내용의 역할과 제목 계층](#/learn/html/wiki-semantic-structure), [링크와 버튼, 이동할 주소](#/learn/html/wiki-links-buttons), [이미지의 목적과 대체 텍스트](#/learn/html/wiki-image-alternatives), [행과 열의 관계를 나타내는 표](#/learn/html/wiki-tables), [신청 폼을 끝까지 읽고 조작하기](#/learn/html/wiki-form-flow)의 관계를 알고 있으면 이 문서를 읽기 쉽습니다.

## 세 종류를 먼저 구분한다

| 종류 | 묻는 질문 | 주로 확인하는 방법 |
| --- | --- | --- |
| 문법·콘텐츠 모델 | 태그와 속성을 올바르게 썼고, 이 요소 안에 허용된 내용을 넣었는가? | Nu HTML Checker |
| 의미 | 제목과 요소가 실제 정보 관계를 올바르게 나타내는가? | 요구사항과 코드를 사람이 비교 |
| 접근성 | 다양한 사람이 내용을 알고 키보드 등으로 이용할 수 있는가? | 자동 검사와 사람의 직접 사용 확인 |

이 세 칸은 완전히 떨어진 벽이 아니다.
레이블이 빠진 입력처럼 한 문제가 의미와 접근성에 함께 영향을 줄 수 있다.
구분의 목적은 문제에 맞는 확인 방법을 고르는 데 있다.

콘텐츠 모델은 `이 요소 안에는 어떤 내용을 넣을 수 있는가`를 정한 HTML 규칙이다.

## Nu HTML Checker가 도와주는 일

W3C Nu HTML Checker는 작성자가 놓치기 쉬운 HTML 오류를 찾는다.

브라우저에 화면이 보이더라도 HTML이 올바르다고 단정할 수 없다.
브라우저가 일부 잘못된 구조를 고쳐서 해석할 수 있기 때문이다.

- 잘못된 태그 문법
- 허용되지 않는 중첩과 콘텐츠 모델
- 잘못되거나 금지된 속성과 값
- 필요한 일부 문서 정보나 속성의 누락
- 브라우저가 예상과 다르게 해석할 수 있는 구조

검사 결과의 `error`는 먼저 고칠 문제다.
`warning`은 문맥을 읽고 판단해야 하는 주의 신호다.
첫 오류 때문에 뒤에서 다른 오류가 연달아 생길 수 있으므로 위에서부터 하나씩 고친 뒤 다시 검사한다.

Checker 오류가 0개라는 결과를 인증서나 영구적인 합격 판정처럼 사용하지 않는다.
Checker가 일부 접근성 관련 경고를 보여 줄 수는 있지만 전체 접근성을 보증하지는 않는다.

## Checker만으로 알 수 없는 일

자동 검사만으로 다음을 완전히 판단할 수 없다.

- 페이지 제목과 본문 제목이 실제 내용을 잘 설명하는가?
- `section`, `article`, `aside` 중 문맥에 알맞은 것을 골랐는가?
- 이미지의 `alt`가 그 페이지에서 이미지가 맡은 목적을 대신하는가?
- `여기` 같은 링크 문구만 보고도 목적지를 알 수 있는가?
- 키보드만으로 논리적인 순서에 따라 조작할 수 있는가?
- 오류 안내가 사용자가 고칠 방법을 알려 주는가?
- 선택한 웹 콘텐츠 접근성 지침(WCAG) 기준을 충족하며 여러 사용 환경에서 필요한 기능을 이용할 수 있는가?

자동 도구는 빠르게 찾을 수 있는 단서를 제공한다.
최종 판단에는 내용을 아는 사람과 실제 이용 흐름의 확인이 필요하다.

## 하나의 오류 예시를 나눠 보기

다음 코드는 문제를 구분하기 위해 일부러 잘못 작성했다.
정상 예제로 복사하지 않는다.

```html
<main>
  <h1>밤마을 책모임</h1>

  <p>
    <section>
      <h3>9월 일정</h3>
      <p>9월 20일 오후 7시</p>
    </section>
  </p>

  <form action="/club-applications" method="post">
    <label>이메일</label>
    <input type="email" name="email" required>
    <button>신청</button>
  </form>
</main>
```

문제를 하나씩 나눈다.

| 코드의 문제 | 먼저 분류할 곳 | 이유 |
| --- | --- | --- |
| `p` 안에 `section`을 넣음 | 문법·콘텐츠 모델 | `p`에 허용되지 않는 구조라 브라우저가 예상과 다르게 고칠 수 있다. |
| `h1` 다음에 `h3`가 나옴 | 의미 | `9월 일정`이 어느 단계인지 관계가 불분명하다. Checker가 경고할 수 있어도 내용 판단은 사람이 한다. |
| `label`과 `input`이 연결되지 않음 | 의미·접근성 | 글은 보이지만 어느 입력의 이름인지 프로그램으로 연결되지 않았다. |
| 버튼의 `type`이 없음 | 의도 확인 | 문법 오류는 아니고 이 예의 기본값도 `submit`이다. 다만 제출 의도를 분명히 적는 편이 안전하다. |

다음은 같은 의도를 더 분명하게 고친 코드다.

```html
<main>
  <h1>밤마을 책모임</h1>

  <section>
    <h2>9월 일정</h2>
    <p>9월 20일 오후 7시</p>
  </section>

  <form action="/club-applications" method="post">
    <label for="email">이메일</label>
    <input id="email" name="email" type="email" required>
    <button type="submit">신청</button>
  </form>
</main>
```

수정 이유도 함께 남긴다.

- `section`을 `p` 밖으로 꺼내 올바른 내용 관계로 바꿨다.
- 대표 제목 아래의 주제이므로 `h3`를 `h2`로 바꿨다.
- `for`와 `id`로 레이블과 입력칸을 연결했다.
- 버튼이 폼을 제출한다는 의도를 `type="submit"`으로 밝혔다.

## 실제 수정 순서

### 1. 문서를 저장하고 전체를 검사한다

[Nu HTML Checker](https://validator.w3.org/nu/)에서 주소·파일 업로드·직접 입력 중 가능한 방법을 사용한다.
문서 일부만 붙이면 `doctype`, `title`, `lang` 같은 전체 문서 정보는 확인할 수 없으므로 최종 단계에서는 전체 파일을 검사한다.

### 2. 첫 오류부터 원인을 읽는다

오류 줄만 지우지 않는다.
어떤 요소 안에 무엇이 허용되지 않았는지, 앞에서 닫히지 않은 태그가 뒤 오류를 만든 것은 아닌지 확인한다.
수정한 뒤 다시 검사한다.

### 3. 요구사항과 제목·요소를 비교한다

- `h1`부터 제목 관계가 내용을 따라가는가?
- 주요 이동은 `nav`, 중심 내용은 `main`으로 구분했는가?
- 이동에는 `a`, 현재 행동에는 `button`을 사용했는가?
- 목록과 표가 실제 정보 관계에 맞는가?

### 4. 이미지와 폼을 문맥으로 확인한다

- 정보를 전하는 이미지라면 보지 않아도 `alt`와 주변 글을 통해 빠지는 핵심 정보가 없는가? 장식 이미지라면 `alt=""`인가?
- 각 입력칸에 연결된 레이블과 제출할 `name`이 있는가?
- 필수값과 허용 형식을 입력 전에 알 수 있는가?
- 오류가 색만이 아니라 글로도 설명되는가?

### 5. 키보드로 처음부터 끝까지 사용한다

`Tab`·`Shift+Tab`으로 초점을 이동하고, 각 요소에 맞는 `Enter`·`Space`·화살표 키 동작을 확인한다.
초점이 보이고 이동 순서가 자연스러운지도 살핀다.

필요하면 브라우저가 보조 기술에 전달하는 구조 정보인 접근성 트리, 페이지 구조 목록, 화면의 글을 읽어 주는 스크린 리더로 확인 범위를 넓힌다.
한 도구의 통과 결과만으로 전체 접근성을 확정하지 않는다.

## ARIA를 먼저 붙이지 않는 이유

접근 가능한 인터넷 응용프로그램을 위한 속성 모음인 ARIA는 기본 HTML에 없는 접근성 의미와 상태를 보강할 때 사용하는 기술이다.
`<div role="button">`처럼 역할만 붙인다고 버튼의 키보드 동작이 자동으로 생기지 않는다.

먼저 알맞은 기본 HTML 요소를 고른다.

```html
<button type="button">신청 안내 열기</button>
```

기본 `button`은 브라우저가 버튼의 의미와 기본 키보드 동작을 함께 제공한다.
ARIA가 필요한 복잡한 위젯은 HTML 입문 뒤에 별도로 배운다.

ARIA 속성을 많이 붙였다고 더 접근 가능한 HTML이 되는 것은 아니다.
기본 HTML만으로 표현할 수 없는 의미나 상태가 있을 때 알맞게 보강해야 한다.

## 핵심 질문 답

브라우저는 잘못된 구조도 복구해 표시할 수 있습니다.
Checker는 문법·콘텐츠 모델의 단서를 찾지만 요소 선택의 의미나 실제 접근성을 모두 판단하지는 못합니다.
전체 문서를 검사하고 첫 오류의 원인을 고친 뒤 다시 검사하며 요구사항·제목·이미지·폼·키보드 순서로 확인합니다.
ARIA 역할만 추가해도 기본 키보드 동작이 생기지 않으므로 먼저 알맞은 네이티브 요소를 선택합니다.
