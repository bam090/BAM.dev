# 동시성: 공유 상태의 원자성·가시성·순서

## 학습 목표

공유 갱신의 위험을 찾고 원자성·가시성·순서에 맞는 보장을 선택할 수 있습니다.

## 한줄 요약

공유 값의 읽기·계산·쓰기와 값이 보이는 관계는 별개이며 volatile만으로 복합 갱신이 원자적이 되지는 않습니다.

## 먼저 확인할 개념

[final과 불변](#/learn/java/wiki-final-immutability) · [컬렉션 선택: 보관 규칙과 연산 비용](#/learn/java/wiki-collection-choice)을 먼저 확인하면 예제의 전제를 이해하기 쉽습니다.

## 같은 장부를 함께 고치면 순서가 중요해진다

두 사람이 한 장부의 완료 횟수를 동시에 올린다고 생각해 보자.
두 사람 모두 `현재 값 0`을 읽고 각자 `1`을 쓴다면 일을 두 번 마쳤어도 장부에는 `1`만 남는다.

프로그램에서도 여러 작업이 같은 바뀔 수 있는 값, 즉 공유 가변 상태(shared mutable state)를 읽고 쓰면 같은 일이 생길 수 있다.
코드에 `count++` 한 줄만 보여도 실제로는 값을 읽고, 1을 더하고, 결과를 쓰는 과정이 필요하다.

| 순서 | 작업 A | 작업 B | 공유된 `count` |
| --- | --- | --- | --- |
| 시작 |  |  | `0` |
| 1 | `0`을 읽는다. |  | `0` |
| 2 |  | `0`을 읽는다. | `0` |
| 3 | `1`을 쓴다. |  | `1` |
| 4 |  | `1`을 쓴다. | `1` |

이처럼 실행 순서에 따라 결과의 옳고 그름이 달라지는 문제를 경쟁 상태(race condition)라고 한다.
그중 서로 다른 스레드가 같은 변수를 충돌하게 접근하고, 적어도 하나가 쓰기이며, 두 접근이 happens-before 관계로 정렬되지 않은 경우를 Java 언어 명세에서는 데이터 경쟁(data race)으로 정의한다.

두 용어를 처음부터 외우는 것보다 `누가 같은 값을 쓰는가`, `읽기와 쓰기 사이에 다른 작업이 끼어들 수 있는가`를 먼저 찾는 편이 중요하다.

## 안전하려면 무엇을 보장해야 할까

공유 상태의 문제를 판단할 때는 원자성, 가시성, 순서를 구분한다.

| 성질 | 뜻 | 놓치기 쉬운 예 |
| --- | --- | --- |
| 원자성(atomicity) | 다른 작업이 중간 상태를 끼어들어 보지 못하도록 한 덩어리로 처리된다. | `count++`은 보통 읽기와 쓰기가 나뉘므로 그 자체로 원자적이지 않다. |
| 가시성(visibility) | 한 스레드가 쓴 결과를 다른 스레드가 정해진 시점에 볼 수 있다. | 한 스레드의 평범한 필드 변경이 다른 스레드에 언제 보일지는 동기화 없이 보장되지 않는다. |
| 순서(ordering) | 메모리 작업이 다른 스레드에 어떤 순서로 관찰되어야 하는지 정해진다. | 소스 코드의 위아래 순서만 보고 다른 스레드도 같은 순서로 본다고 단정할 수 없다. |

`synchronized`, `volatile`, 원자 변수, 동시성 컬렉션은 모두 같은 해결책이 아니다.
각 도구가 보장하는 범위가 다르므로 먼저 보호하려는 상태와 한 덩어리여야 하는 작업을 정해야 한다.

## 공유해야 한다면 필요한 보장을 고른다

상태를 공유하지 않을 수 없을 때는 다음 선택을 비교한다.

| 선택 | 알맞은 상황 | 기억할 경계 |
| --- | --- | --- |
| 불변 값 | 만든 뒤 내용을 바꾸지 않고 여러 곳에서 읽는다. | 객체가 불변이어도 그 참조를 다른 스레드에 전달하는 과정은 안전해야 한다. |
| `synchronized` | 여러 필드나 여러 문장을 하나의 규칙으로 묶어야 한다. | 같은 잠금을 사용해야 상호 배제와 가시성 보장이 이어진다. |
| `AtomicInteger` 같은 원자 변수 | 숫자 하나의 증가처럼 지원되는 단일 연산을 원자적으로 처리한다. | 여러 변수의 관계까지 자동으로 보호하지 않는다. |
| `volatile` | 한 스레드가 바꾼 상태 표시 값을 다른 스레드가 보게 한다. | `count++` 같은 읽기·계산·쓰기 전체를 원자적으로 만들지 않는다. |
| `ConcurrentHashMap` 같은 스레드 안전 컬렉션 | 여러 스레드가 컬렉션의 지원 연산을 함께 수행한다. | 여러 메서드를 이어 만든 업무 규칙까지 자동으로 한 덩어리가 되지는 않는다. |

예를 들어 `containsKey()`로 확인한 뒤 `put()`하는 두 호출 사이에는 다른 작업이 끼어들 수 있다.
`ConcurrentHashMap`에서 한 키의 확인과 저장을 함께 처리해야 한다면 `putIfAbsent()`나 `compute()`처럼 해당 구현이 원자적으로 보장하는 단일 연산을 먼저 살핀다.

스레드 안전 컬렉션을 사용했다는 사실만으로 컬렉션 밖의 다른 필드와 함께 지켜야 하는 규칙까지 안전해지는 것은 아니다.
`진행률을 올리면서 완료 시각도 함께 기록한다`처럼 두 값이 반드시 같이 바뀌어야 하면 같은 잠금이나 공유 변경을 없애는 새 구조가 필요하다.

## 보이는 관계도 함께 확인하기

happens-before는 다른 스레드에 값이 어떤 관계로 보여야 하는지를 정한다.
같은 잠금을 해제한 뒤 다른 스레드가 그 잠금을 획득하는 관계와 volatile 쓰기·이후 읽기 등이 이 보장의 근거다.
두 필드가 한 상태를 나타내면 쓰는 쪽뿐 아니라 읽는 쪽도 같은 잠금 계약을 따라야 중간 조합을 피할 수 있다.
`Thread.sleep()`은 시간을 쉬게 할 뿐 공유 상태의 가시성이나 작업 완료를 보장하지 않는다.

## 핵심 질문 답

읽기·계산·쓰기가 한 번의 갱신이어야 한다면 그 전체를 원자적으로 보호해야 합니다. volatile만으로 count++는 원자적이 되지 않습니다. 숫자 하나는 AtomicInteger의 단일 연산을 검토하고 두 필드의 관계는 읽는 쪽과 쓰는 쪽이 같은 잠금 계약을 지켜야 합니다. 가능하면 공유 변경을 줄이고 happens-before가 생기는 완료·잠금 관계를 사용하며 sleep 시간만으로 동기화하지 않습니다.
