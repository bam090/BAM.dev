# 테스트: 계약에서 조건을 찾고 도구로 확인하기

## 학습 목표

- 메서드의 공개 계약에서 정상·경계·예외 조건을 골라 적은 수의 의미 있는 테스트로 확인할 수 있습니다.
- 테스트 하나를 준비·실행·검증으로 읽고 내부 구현을 바꿔도 유지할 확인 대상을 고를 수 있습니다.
- JUnit·AssertJ·Mockito가 맡는 실행 틀·결과 비교·협력 대역의 역할을 나누고 필요한 도구만 고를 수 있습니다.

## 먼저 확인할 개념

[메서드의 입력·출력 계약](#/learn/java/wiki-methods)과 [예외 처리와 자원 정리](#/learn/java/wiki-exceptions)와 [상속·인터페이스·조합: 타입 관계 고르기](#/learn/java/wiki-inheritance-dispatch)를 먼저 확인해 보세요.

## 테스트란

자동화된 테스트는 정해 둔 입력으로 코드를 실행하고 관찰한 결과가 기대와 같은지 반복해서 확인하는 코드입니다.
앞 문서에서는 여러 작업의 결과를 안전하게 모았습니다.
이번에는 그렇게 만든 코드가 약속을 지키는지 확인하는 방법을 살펴봅니다.

계산기를 한 번 눌러 보고 맞았다고 생각해도 다른 숫자나 경계에서는 틀릴 수 있습니다.
코드를 고칠 때마다 같은 확인을 사람이 반복하면 빠뜨리거나 결과를 잘못 읽기도 합니다.
그래서 확인을 코드로 남겨 두고 언제든 다시 실행합니다.
좋은 테스트는 어떤 순서로 계산했는지보다 호출한 사람이 볼 수 있는 약속을 지켰는지를 확인합니다.

예를 들어 할인 계산기를 만들고 할인을 마치면 알림을 보내는 서비스가 있다고 해 보겠습니다.
이 문서는 이 할인 계산기와 알림 하나로 테스트 조건 고르기와 테스트 도구의 역할을 차례로 살펴봅니다.

## 테스트 조건의 종류

공개된 메서드 계약(method contract)은 호출자가 알아야 하는 입력·반환값·발생할 수 있는 예외·밖에서 관찰되는 변화입니다.
테스트 도구를 고르기 전에 이 계약에서 확인할 사실을 찾습니다.
할인 계산기의 계약은 다음과 같습니다.

- 원래 가격은 `0` 이상입니다.
- 할인율은 `0`부터 `100`까지입니다.
- 유효한 값을 받으면 할인된 가격을 반환합니다.
- 범위를 벗어난 값을 받으면 `IllegalArgumentException`을 던집니다.

이 계약에서 확인할 조건은 세 종류로 나눌 수 있습니다.

| 조건 | 확인하는 이유 | 할인 계산기 예 |
| --- | --- | --- |
| 정상 조건 | 평소 입력에서 핵심 계산이 맞는지 봅니다 | `10,000원`에 `20%`를 적용하면 `8,000원`입니다 |
| 경계 조건 | 허용 범위가 바뀌는 가장자리를 봅니다 | 할인율 `0`과 `100`을 허용합니다 |
| 예외 조건 | 거부해야 할 입력과 실패 방식이 맞는지 봅니다 | 할인율 `101`은 예외를 던집니다 |

가능한 모든 숫자를 시험하는 것이 목표는 아닙니다.
계약의 서로 다른 규칙을 대표하는 값을 고르면 적은 테스트로도 무엇을 확인했는지 분명해집니다.

## 테스트 조건 찾기

계약을 코드로 옮긴 할인 계산기입니다.
클래스 안에 선언하는 Java 25 예제입니다.

```java
final class DiscountCalculator {
    int finalPrice(int price, int discountPercent) {
        if (price < 0 || discountPercent < 0 || discountPercent > 100) {
            throw new IllegalArgumentException("가격과 할인율을 확인해 주세요.");
        }
        int discount = (int) ((long) price * discountPercent / 100);
        return price - discount;
    }
}
```

곱하기 전에 `price`를 `long`으로 넓혀 중간 결과가 `int` 범위를 넘는 오버플로를 피합니다.
이 메서드에서 확인할 값을 먼저 골라 보세요.

- 정상: `10,000원`에 `20%`면 `8,000원`입니다.
- 경계: `0%`면 원래 가격인 `10,000원`이고 `100%`면 `0원`입니다.
- 예외: `101%`나 음수 가격이면 반환값 대신 `IllegalArgumentException`이 발생합니다.

`20%`의 정상 결과와 `101%`의 예외만 확인했다면 허용 경계인 `0%`와 `100%`가 빠진 것입니다.

테스트 하나는 준비(Arrange)·실행(Act)·검증(Assert)의 세 부분으로 읽을 수 있습니다.

```text
준비: 필요한 객체와 입력을 만든다.
실행: 확인할 메서드를 한 번 호출한다.
검증: 반환값·예외·외부 변화가 기대와 같은지 본다.
```

세 부분을 반드시 주석이나 별도 블록으로 나눌 필요는 없습니다.
짧은 테스트는 위에서 아래로 읽을 때 준비한 값과 실행 결과와 검증할 사실이 바로 보이면 충분합니다.

공개 동작을 확인하면 내부를 정리해도 테스트가 계속 쓸모 있습니다.
예를 들어 계산 일부를 private helper 메서드로 나누거나 계산 순서를 바꿔도 공개된 반환값·예외·외부 변화가 같다면 같은 테스트로 계속 검증할 수 있습니다.
반대로 private helper의 이름이나 호출 순서를 검사하면 동작이 같아도 테스트가 깨집니다.

확인할 조건을 골랐습니다.
이제 이 조건을 실제 테스트 코드로 옮길 도구를 살펴보겠습니다.

## 테스트 도구의 종류

먼저 도구가 쓰이는 환경의 말을 정리합니다.
IDE(Integrated Development Environment, 통합 개발 환경)는 코드를 작성하고 실행하는 개발 프로그램입니다.
빌드 도구는 컴파일·테스트 실행·필요한 라이브러리 준비 같은 작업을 자동화합니다.
테스트 엔진은 테스트를 찾아 실행하고 assertion(검증문)은 실제 결과가 기대한 조건과 같은지 확인합니다.

| 도구 | 맡는 일 | 맡지 않는 일 |
| --- | --- | --- |
| JUnit Jupiter 5.14.4 | `@Test`로 테스트를 표시하고 Jupiter 테스트를 실행할 규칙과 기본 assertion을 제공합니다 | 외부 알림 객체를 대신 만들지 않습니다 |
| AssertJ Core 3.27.7 | 반환값과 예외를 읽기 쉬운 assertion으로 확인합니다 | 테스트를 찾거나 생명 주기를 관리하지 않습니다 |
| Mockito 5.23.0 | 알림 협력자를 대신하고 전달된 메시지를 검증합니다 | 할인 계산의 정답을 대신 판단하거나 테스트를 실행하지 않습니다 |

세 도구가 있다고 모든 테스트에 세 도구를 다 쓸 필요는 없습니다.
확인할 사실이 단순한 계산이면 JUnit과 assertion 하나로 충분합니다.
실제 협력 경계를 떼어 내야 할 때만 Mockito를 더합니다.

## JUnit과 AssertJ 사용법

JUnit 5에서 JUnit Platform은 IDE나 빌드 도구가 테스트 엔진을 실행할 수 있는 기반입니다.
JUnit Jupiter는 `@Test` 같은 애너테이션과 생명 주기와 기본 assertion과 Jupiter 테스트를 실행하는 엔진을 제공합니다.

| 기능 | 역할 |
| --- | --- |
| `@Test` | 해당 메서드가 실행할 테스트임을 표시합니다 |
| `Assertions` | 실제 값이 기대와 같은지와 예외가 발생했는지 등을 확인합니다 |
| `@BeforeEach` · `@AfterEach` | 각 테스트 전후에 반복할 준비와 정리를 실행합니다 |
| `@BeforeAll` · `@AfterAll` | 한 테스트 클래스 전체의 시작과 끝에 한 번씩 준비하고 정리합니다 |

AssertJ는 `assertThat(actual).isEqualTo(expected)`처럼 실제 값에서 시작해 조건을 이어 쓰는 assertion 라이브러리입니다.
JUnit 테스트 안에서 결과를 더 읽기 쉽게 표현하고 실패했을 때 비교 정보를 보여 줍니다.

다음은 JUnit Jupiter와 AssertJ가 준비된 별도 테스트 프로젝트를 가정한 읽기 예제입니다.
밤데브 앱 안에서 실행하는 코드가 아닙니다.

```java
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.assertj.core.api.Assertions.assertThat;

class PriceTest {
    @Test
    void comparesPrice() {
        int actualPrice = 8_000;
        assertEquals(8_000, actualPrice);
        assertThat(actualPrice).isEqualTo(8_000);
    }
}
```

두 검증문은 같은 정수 비교를 각 도구의 표현으로 적은 것입니다.
설명을 위해 함께 두었으며 실제 테스트에서는 같은 비교를 한 번만 씁니다.
한 assertion에 관련 없는 조건을 길게 붙이기보다 테스트 이름과 검증할 사실을 한 방향으로 맞춥니다.

> [!note]- 생명 주기 메서드를 쓸 때 확인할 것
> 기본 테스트 인스턴스 생명 주기에서 `@BeforeAll`과 `@AfterAll` 메서드는 보통 `static`이어야 합니다.
> 테스트 클래스마다 인스턴스를 하나만 쓰는 생명 주기를 명시하면 인스턴스 메서드로 둘 수도 있습니다.
> 공통 준비가 길게 반복될 때 `@BeforeEach`를 쓰고 객체 하나를 바로 만드는 편이 더 잘 읽히면 생명 주기 메서드를 추가하지 않습니다.
> 각 테스트는 다른 테스트의 실행 결과나 실행 순서에 기대지 않아야 합니다.
> 한 테스트가 남긴 공유 상태를 다음 테스트가 쓰면 따로 실행했을 때 결과가 달라질 수 있기 때문입니다.

## Mockito 사용법

할인을 마친 서비스가 이메일 전송기에 알림을 부탁한다면 테스트할 때 실제 이메일까지 보내고 싶지는 않습니다.
Mockito의 Mock 객체는 그 협력자와 같은 타입 자리에 놓여 테스트에 필요한 응답과 호출 기록을 제공합니다.

| Mockito 동작 | 쉬운 뜻 |
| --- | --- |
| `mock(Type.class)` | 실제 협력자 대신 쓸 객체를 만듭니다 |
| `when(...).thenReturn(...)` | 지정한 호출에 돌려줄 값을 미리 정합니다 |
| `verify(...)` | 기대한 협력 요청이 실제로 있었는지 확인합니다 |

무엇을 실제 객체로 두고 무엇을 대역으로 바꿀지는 계약에서 정합니다.
할인 계산기는 빠르고 결과가 늘 같으므로 실제 객체로 확인합니다.
알림 전송처럼 테스트 범위를 벗어난 협력 경계만 Mock으로 바꾸면 무엇을 검증하는지 더 잘 보입니다.
`verify`는 `send`에 올바른 메시지를 요청했는지 확인할 뿐 실제 이메일 도착이나 계산 정답을 보장하지 않습니다.

테스트가 통과했다는 것은 선택한 조건에서 관찰한 결과가 기대와 같았다는 뜻입니다.
모든 입력과 실행 환경을 확인한 것이 아니므로 결함이 전혀 없다는 증명은 아닙니다.
그래서 경계값을 빠뜨렸는지와 예외가 원래 원인을 숨기지 않는지와 동시 실행에서 다른 위험이 있는지 계속 살핍니다.
테스트는 정한 약속이 다시 깨졌는지 빠르게 알려 주는 안전망입니다.

## 입력에서 검증까지의 흐름

지금까지 배운 Java 내용은 따로 떨어진 문법 목록이 아닙니다.
한 기능을 만들고 확인하는 순서에서 각 문서의 역할이 이어집니다.

| 흐름 | 앞 문서에서 쓰는 내용 | 확인할 질문 |
| --- | --- | --- |
| 입력을 받습니다 | 타입·변수·배열·문자열 | 어떤 값이 들어오며 허용 범위는 어디까지인가요? |
| 판단과 계산을 나눕니다 | 조건·반복·메서드 | 어느 계산을 이름 있는 메서드로 나눌까요? |
| 상태와 책임을 묶습니다 | 클래스·캡슐화·`static`·`final` | 어떤 객체가 값을 지키고 바꾸어야 하나요? |
| 구현을 연결합니다 | 상속·인터페이스·제네릭·컬렉션 | 역할과 보관 규칙에 맞는 타입은 무엇인가요? |
| 실패와 변환을 다룹니다 | 예외·자원·람다·Stream·시간 | 실패를 어디까지 전달하고 값을 어떤 단계로 처리하나요? |
| 여러 작업을 안전하게 잇습니다 | executor·happens-before·공유 상태 | 어떤 값을 공유하며 결과는 언제 보이나요? |
| 계약을 다시 확인합니다 | 테스트 | 호출자가 관찰할 정상·경계·예외 결과는 무엇인가요? |

새 기능을 만나면 문법 이름부터 고르기보다 입력·상태·판단·출력과 외부 협력 경계를 먼저 그립니다.
그 뒤 필요한 Java 도구를 고르면 문법이 기능의 이유와 연결됩니다.

## 정리

- 테스트는 공개 계약에서 정상·경계·예외 조건을 대표하는 값을 골라 준비·실행·검증으로 확인합니다.
- private helper보다 공개된 반환값·예외·외부 변화를 확인해야 내부를 정리해도 테스트가 유효하며 통과는 고른 조건에서만 확인한 결과입니다.
- JUnit은 실행 틀을 맡고 AssertJ는 결과 비교를 맡으며 Mockito는 필요한 외부 협력 경계만 대역으로 바꿉니다.

## 핵심 질문 답

입력 범위·반환값·예외·외부에서 보이는 변화에서 정상·허용 경계·거부 조건을 고르고 준비한 입력으로 실행해 관찰한 약속을 검증합니다.
private helper의 이름이나 호출 순서보다 공개 동작을 검사하면 내부를 정리해도 검증이 유효하며 선택한 사례의 통과가 모든 입력·환경에서 결함이 없다는 증명은 아닙니다.
JUnit Platform·Jupiter는 테스트 실행 틀과 생명 주기·기본 assertion을 제공하고 AssertJ는 결과 비교를 읽기 쉽게 하며 Mockito는 외부 협력 대신 응답과 호출 확인을 제공하는 대역을 만듭니다.
빠르고 결과가 늘 같은 계산은 실제 객체로 확인하고 필요한 외부 경계만 대역으로 바꾸며 `verify`는 협력 요청 확인일 뿐 계산 정답이나 실제 전송 성공을 증명하지 않습니다.
