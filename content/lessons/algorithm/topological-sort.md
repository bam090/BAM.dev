# 위상 정렬: 선후 관계를 지키며 작업 순서 정하기

## 학습 목표

- 진입 차수를 세고 큐로 진입 차수가 0인 작업부터 꺼내는 칸 알고리즘으로 위상 정렬 순서를 만들 수 있습니다.
- 정렬된 작업 수로 사이클을 찾아내고 위상 정렬이 불가능한 경우를 판단할 수 있습니다.

## 한줄 요약

위상 정렬은 먼저 끝나야 하는 작업이 항상 앞에 오도록 방향 그래프의 노드를 한 줄로 늘어놓는 방법이고 진입 차수가 0인 노드부터 큐로 꺼내며 사이클이 있으면 순서를 만들 수 없습니다.

## 위상 정렬이란

**위상 정렬**은 "A가 끝나야 B를 할 수 있다" 같은 선후 관계를 모두 지키도록 작업을 한 줄로 늘어놓는 방법입니다.
앞 문서들의 정렬은 값의 크기를 비교해 순서를 정했습니다.
위상 정렬은 크기 대신 **무엇이 먼저 와야 하는지**라는 관계로 순서를 정한다는 점이 다릅니다.

선후 관계는 [그래프](#/learn/algorithm/bfs-dfs-graph-grid)로 나타냅니다.
작업 하나가 노드이고 "A가 끝나야 B를 시작"은 A에서 B로 가는 화살표 하나입니다.
이렇게 화살표에 방향이 있는 그래프를 **방향 그래프**라고 합니다.

예를 들어 팀이 웹 서비스를 만든다고 해 보겠습니다.
이 문서는 이 여섯 작업으로 끝까지 설명합니다.

- 기획이 끝나야 디자인과 DB 설계를 시작합니다.
- 디자인이 끝나야 화면 개발을 하고 DB 설계가 끝나야 서버 개발을 합니다.
- 화면 개발과 서버 개발이 모두 끝나야 배포합니다.

![여섯 작업의 선후 관계. 기획에서 디자인과 DB 설계로 화살표가 가고 디자인은 화면 개발로 DB 설계는 서버 개발로 이어지며 화면 개발과 서버 개발은 모두 배포로 이어진다. 진입 차수는 기획 0 · 디자인 1 · DB 설계 1 · 화면 개발 1 · 서버 개발 1 · 배포 2이다.](content/assets/algorithm/topological-sort-graph.png)

이 그래프로 만들 수 있는 올바른 순서 중 하나는 `기획 → 디자인 → DB 설계 → 화면 개발 → 서버 개발 → 배포`입니다.
어떤 화살표를 골라도 화살표의 출발 작업이 도착 작업보다 앞에 있습니다.

## 진입 차수

위상 정렬의 핵심 도구는 진입 차수입니다.
**진입 차수**는 한 노드로 들어오는 화살표의 수이고 작업으로 말하면 그 작업 전에 끝나야 하는 작업의 수입니다.

그림에서 작업 상자 모서리의 동그라미 안 숫자가 진입 차수입니다.
`배포`는 화면 개발과 서버 개발이 모두 끝나야 하므로 진입 차수가 2입니다.
`기획`은 기다릴 작업이 없으므로 진입 차수가 0입니다.

진입 차수가 0이라는 것은 **지금 바로 시작할 수 있다**는 뜻입니다.
그리고 작업 하나를 끝내면 그 작업에서 나가는 화살표가 사라지므로 다음 작업들의 진입 차수가 1씩 줄어듭니다.
위상 정렬은 이 두 사실만으로 동작합니다.

## 칸 알고리즘

**칸 알고리즘**(Kahn's algorithm)은 진입 차수가 0인 노드를 큐에 넣고 하나씩 꺼내며 순서를 만드는 위상 정렬 방법입니다.
과정은 네 단계입니다.

1. 모든 노드의 진입 차수를 셉니다.
2. 진입 차수가 0인 노드를 모두 큐에 넣습니다.
3. 큐에서 노드를 하나 꺼내 순서에 추가하고 그 노드가 가리키는 노드들의 진입 차수를 1씩 줄입니다.
4. 줄인 결과 진입 차수가 0이 된 노드를 큐에 넣고 큐가 빌 때까지 3번으로 돌아갑니다.

큐가 어떻게 바뀌는지 따라가 보겠습니다.

| 꺼낸 작업 | 진입 차수를 줄인 작업 | 새로 0이 되어 넣은 작업 | 꺼내고 넣은 뒤 큐 |
| --- | --- | --- | --- |
| 기획 | 디자인 1→0 · DB 설계 1→0 | 디자인 · DB 설계 | 디자인 DB 설계 |
| 디자인 | 화면 개발 1→0 | 화면 개발 | DB 설계 화면 개발 |
| DB 설계 | 서버 개발 1→0 | 서버 개발 | 화면 개발 서버 개발 |
| 화면 개발 | 배포 2→1 | 없음 | 서버 개발 |
| 서버 개발 | 배포 1→0 | 배포 | 배포 |
| 배포 | 없음 | 없음 | 비어 있음 |

`화면 개발`을 끝내도 `배포`의 진입 차수는 1이 남아 아직 큐에 들어가지 못합니다.
`서버 개발`까지 끝나서 진입 차수가 0이 된 뒤에야 들어갑니다.
그래서 진입 차수가 0이 되는 순간이 곧 **먼저 끝나야 할 작업이 모두 끝난 순간**입니다.

큐에서 꺼내는 모습이 [BFS](#/learn/algorithm/bfs-dfs-graph-grid)와 닮았습니다.
다만 BFS는 처음 발견한 노드를 바로 큐에 넣고 칸 알고리즘은 진입 차수가 0이 되어야 넣는다는 점이 다릅니다.

## Java로 위상 정렬 구현

이제 칸 알고리즘을 Java 코드로 옮겨 보겠습니다.
작업은 번호로 다루고 이름은 배열에 둡니다.

```java
static String[] tasks = {"기획", "디자인", "DB 설계", "화면 개발", "서버 개발", "배포"};

int[][] edges = {{0, 1}, {0, 2}, {1, 3}, {2, 4}, {3, 5}, {4, 5}};
```

`{0, 1}`은 0번 기획이 끝나야 1번 디자인을 할 수 있다는 화살표입니다.

```java
static List<String> topologicalSort(int[][] edges) {
    int n = tasks.length;
    List<List<Integer>> next = new ArrayList<>();
    for (int i = 0; i < n; i++) next.add(new ArrayList<>());
    int[] inDegree = new int[n];
    for (int[] e : edges) {
        next.get(e[0]).add(e[1]);
        inDegree[e[1]]++;
    }
    System.out.println("진입 차수: " + Arrays.toString(inDegree));

    Queue<Integer> queue = new ArrayDeque<>();
    for (int i = 0; i < n; i++) {
        if (inDegree[i] == 0) queue.add(i);
    }

    List<String> order = new ArrayList<>();
    while (!queue.isEmpty()) {
        int now = queue.poll();
        order.add(tasks[now]);
        for (int after : next.get(now)) {
            inDegree[after]--;
            if (inDegree[after] == 0) queue.add(after);
        }
    }

    if (order.size() < n) {
        System.out.println("사이클이 있어 " + order.size() + "개만 정렬됨: " + order);
        return List.of();
    }
    return order;
}
```

`next.get(i)`는 `i`번 작업이 끝나면 할 수 있게 되는 작업들의 목록이고 `inDegree[i]`는 `i`번 작업의 진입 차수입니다.
화살표 하나를 읽을 때마다 출발 작업의 목록에 도착 작업을 넣고 도착 작업의 진입 차수를 1 올립니다.

위의 단계별 표를 보며 출력을 예상해 보세요.

```text
진입 차수: [0, 1, 1, 1, 1, 2]
작업 순서: [기획, 디자인, DB 설계, 화면 개발, 서버 개발, 배포]
```

진입 차수는 그림의 동그라미 안 숫자와 같고 순서는 표에서 꺼낸 순서와 같습니다.
모든 노드를 한 번씩 꺼내고 모든 화살표를 한 번씩 확인하므로 노드 수를 `V` · 화살표 수를 `E`라고 하면 시간 복잡도는 `O(V + E)`입니다.

> [!question]- 위상 정렬의 답은 하나뿐인가요?
> 아닙니다.
> 예제에서 `기획 → DB 설계 → 디자인 → 서버 개발 → 화면 개발 → 배포`도 모든 화살표를 지키는 올바른 순서입니다.
>
> 진입 차수가 0인 작업이 동시에 여러 개이면 무엇을 먼저 꺼내느냐에 따라 순서가 달라집니다.
> 문제에서 "가능한 순서가 여럿이면 번호가 작은 것부터"처럼 조건을 주면 큐 대신 `PriorityQueue`로 가장 작은 번호부터 꺼냅니다.

## 사이클과 위상 정렬

그런데 팀에서 "서버 개발이 끝나야 DB 설계를 마무리할 수 있다"는 조건이 하나 더 생겼다고 해 보겠습니다.
그러면 DB 설계는 서버 개발을 기다리고 서버 개발은 DB 설계를 기다립니다.

![같은 그래프에 서버 개발에서 DB 설계로 가는 빨간 화살표를 더한 모습. 기획·디자인·화면 개발은 초록으로 정렬되었지만 DB 설계와 서버 개발은 남은 진입 차수가 1이라 서로를 기다리고 배포도 진입 차수 1이 남아 빨간색이다.](content/assets/algorithm/topological-sort-cycle.png)

DB 설계와 서버 개발 사이에 한 바퀴 도는 길인 **사이클**이 생겼습니다.
사이클 안의 작업은 서로가 먼저 끝나기를 기다리기 때문에 진입 차수가 영원히 0이 되지 않습니다.
그래서 큐에 들어가지 못하고 그 뒤에 이어진 배포도 함께 막힙니다.

```java
int[][] cycle = {{0, 1}, {0, 2}, {1, 3}, {2, 4}, {3, 5}, {4, 5}, {4, 2}};
System.out.println("작업 순서: " + topologicalSort(cycle));
```

마지막 `{4, 2}`가 새로 더한 화살표입니다.
몇 개의 작업이 정렬될지 그림을 보며 예상해 보세요.

```text
진입 차수: [0, 1, 2, 1, 1, 2]
사이클이 있어 3개만 정렬됨: [기획, 디자인, 화면 개발]
작업 순서: []
```

작업은 6개인데 정렬된 작업은 3개뿐입니다.
이렇게 큐가 비었을 때 **정렬된 노드 수가 전체 노드 수보다 적으면 사이클이 있다**는 뜻입니다.
사이클이 있는 그래프에는 모든 화살표를 지키는 순서가 존재하지 않으므로 위상 정렬이 불가능합니다.

그래서 위상 정렬은 사이클이 없는 방향 그래프에서만 할 수 있습니다.
이런 그래프를 영어 머리글자로 **DAG**(Directed Acyclic Graph)라고 부릅니다.
칸 알고리즘은 순서를 만들면서 사이클이 있는지도 함께 알려 준다는 장점이 있습니다.

## 위상 정렬의 활용

그렇다면 어떤 문제에서 위상 정렬을 떠올려야 할까요?
문제에 "A를 하려면 먼저 B를 해야 한다"는 조건이 여러 개 주어지고 전체 순서나 가능 여부를 물으면 위상 정렬입니다.

| 상황 | 노드 | 화살표 |
| --- | --- | --- |
| 수강 신청 순서 | 과목 | 선수 과목 → 다음 과목 |
| 프로젝트 빌드 | 모듈 | 먼저 빌드할 모듈 → 그 모듈을 쓰는 모듈 |
| 요리 순서 | 조리 단계 | 앞 단계 → 뒤 단계 |
| 작업 일정 | 작업 | 먼저 끝낼 작업 → 이어서 할 작업 |

실무에서도 자주 만납니다.
Gradle 같은 빌드 도구는 모듈 사이의 의존 관계를 보고 빌드할 순서를 정하고 스프레드시트는 다른 셀을 참조하는 셀을 어떤 순서로 다시 계산할지 정합니다.
두 경우 모두 참조가 한 바퀴 돌면 순환 의존 오류를 알려 주는데 이것이 곧 사이클을 찾아낸 것입니다.

위상 정렬 순서를 따라가며 값을 누적하면 더 많은 문제를 풀 수 있습니다.
예를 들어 작업마다 걸리는 시간이 있을 때 모든 작업이 끝나는 가장 빠른 시각은 위상 정렬 순서대로 "앞 작업들이 끝나는 가장 늦은 시각 + 내 작업 시간"을 채워 가며 구합니다.

## 정리

- 위상 정렬은 방향 그래프의 모든 화살표에서 출발 노드가 도착 노드보다 앞에 오도록 노드를 한 줄로 늘어놓습니다.
- 진입 차수는 들어오는 화살표 수이고 0이면 먼저 끝나야 할 작업이 없어 바로 시작할 수 있습니다.
- 칸 알고리즘은 진입 차수가 0인 노드를 큐에서 꺼내 순서에 넣고 이어진 노드의 진입 차수를 줄이며 `O(V + E)`에 끝납니다.
- 정렬된 노드 수가 전체보다 적으면 사이클이 있는 것이고 이때는 위상 정렬 순서가 존재하지 않습니다.

## 핵심 질문 답

위상 정렬은 선후 관계를 방향 그래프로 나타낸 뒤 모든 화살표의 출발 작업이 도착 작업보다 앞에 오도록 작업을 한 줄로 늘어놓습니다.
칸 알고리즘은 먼저 끝나야 하는 작업 수인 진입 차수를 세고 진입 차수가 0인 작업부터 큐에서 꺼내며 이어진 작업의 진입 차수를 줄여 새로 0이 된 작업을 큐에 넣습니다.
큐가 빌 때까지 정렬된 작업 수가 전체 작업 수보다 적으면 서로를 기다리는 사이클이 있는 것이고 이때는 모든 선후 관계를 지키는 순서가 없으므로 위상 정렬이 불가능합니다.
