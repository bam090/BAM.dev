## 요청에서 응답까지 이어지는 경로

`GET /notices/3`에서 GET은 요청 메서드, `/notices/3`은 경로다. 서버는 이 HTTP 요청을 받아 어떤 Java 메서드를 부를지 결정해야 한다. 클라이언트가 서버 객체의 메서드를 직접 호출하는 것은 아니다.

Servlet 기반 Spring MVC의 중심에는 `DispatcherServlet`이 있다. 요청 매핑과 메서드 호출, 결과 처리에 필요한 구성 요소에 작업을 맡기며 공통 흐름을 조정한다.

```text
HTTP 요청
→ 매핑 조건에 맞는 컨트롤러 메서드 선택
→ 요청값을 읽고 인수 준비
→ 컨트롤러가 필요한 업무 서비스 호출
→ 반환값 또는 예외를 HTTP 응답으로 처리
```

실제 호출에는 매핑과 인수 변환 등을 담당하는 여러 구성 요소가 참여한다. `DispatcherServlet`이 모든 업무 계산을 직접 한다는 의미는 아니다. 입력 변환이나 검증이 실패하면 업무 메서드 호출까지 가지 못할 수도 있다.

## HTTP 경계와 업무 규칙

컨트롤러는 URL의 값을 읽고 필요한 서비스에 전달한 뒤 결과를 응답으로 연결한다. 서비스는 “공지 내용을 가져온다”, “제목을 변경한다”처럼 업무 행동을 맡게 나눌 수 있다.

같은 업무를 HTTP 외의 다른 호출자에서도 쓰려면, 서비스를 URL·응답 상태 코드에 불필요하게 묶지 않는 편이 좋다. 그렇다고 메서드 하나마다 무조건 새로운 계층을 만들라는 뜻은 아니다. 실제로 구분할 책임을 기준으로 나눈다.

직접 해볼 일: “URL에서 id 읽기”, “해당 공지 찾기”, “찾지 못함을 404 응답으로 바꾸기”의 담당을 나누어 적는다. 입력값이 Java 타입으로 바뀌지 못하면 어느 단계에서 멈출지도 표시한다.

## 핵심 질문 답

HTTP 요청은 DispatcherServlet이 조정하는 MVC 흐름에서 매핑된 컨트롤러 메서드로 연결됩니다. 인수를 준비한 뒤 컨트롤러가 업무 처리를 호출하고 반환값이나 예외를 HTTP 응답으로 바꿉니다. 컨트롤러의 HTTP 처리와 서비스의 업무 규칙을 나누면 같은 업무를 다른 호출 흐름에서도 쓰기 쉽습니다.
