# 세션 기반 로그인과 로그아웃

## 학습 목표

세션을 통한 인증 지속과 표준 로그아웃의 상태 정리를 설명할 수 있습니다.

## 한줄 요약

세션 기반 로그인은 서버의 인증 정보를 다음 요청에 이어 쓰고, 로그아웃은 그 상태를 정리합니다.

## 먼저 확인할 개념

[로그인 폼이 인증으로 이어지는 과정](#/learn/spring/security-form-login)

## 요청 하나가 끝나도 로그인은 이어질 수 있다

**세션(Session)**은 여러 요청에서 사용할 상태를 서버 쪽에 이어 두는 방법이다. 기본 세션 기반 폼 로그인에서는 인증 성공 시 보안 컨텍스트를 세션에 저장하고 다음 요청에서 다시 사용할 수 있다. 브라우저는 보통 세션 ID 쿠키를 보내고 서버가 그 ID에 연결된 상태를 찾는다.

```text
로그인 성공 → 서버 세션에 SecurityContext 저장
다음 요청의 세션 ID 쿠키 → 서버에서 인증 상태 조회 → 요청별 권한 판단
```

쿠키 자체에 원문 비밀번호나 `Authentication` 객체 전체를 넣어 보내는 흐름이 아니다. 로그인 상태를 이어 쓰더라도 각 요청의 권한 검사는 계속 필요하다. 세션이 만료되면 그 인증 상태를 계속 사용할 수 있다고 가정하지 않는다.

## 로그인 전후와 로그아웃 뒤를 관찰한다

세션 고정 공격은 공격자가 알고 있는 세션 ID가 로그인 뒤에도 사용되도록 노리는 공격이다. Servlet 3.1 이상 환경의 기본 세션 고정 방어는 로그인 시 기존 세션의 ID를 변경한다. ID가 달라졌다는 것만으로 로그인이 풀렸다고 판단하지 않는다.

기본 CSRF 보호와 표준 로그아웃을 유지한 경우에는 다음처럼 읽는다.

| 요청 | 담당하는 행동 |
| --- | --- |
| `GET /logout` | 로그아웃 확인 화면을 보여 준다. |
| 유효 CSRF 토큰을 포함한 `POST /logout` | 세션을 무효화하고 보안 컨텍스트와 저장된 CSRF 토큰 등을 정리한다. |

확인 화면을 여는 것과 실제 로그아웃 처리는 다르다. 로그아웃 뒤 기본 성공 처리는 `/login?logout`으로 이동시킨다. 사용자 정의 설정을 쓰면 요청 경로나 후속 응답이 달라질 수 있다.

## 화면만 바꾸면 서버 상태는 남을 수 있다

로그아웃 버튼을 숨기거나 화면에서 사용자 이름을 지운 일은 서버의 인증 정리가 아니다. 표준 로그아웃 흐름과 후속 보호 요청까지 연결해서 보아야 한다. 또한 이 설명은 세션 기반 폼 로그인의 범위다. 외부 발급자가 만든 토큰의 수명과 다른 서비스의 로그인까지 자동으로 끝난다는 뜻은 아니다.

직접 해볼 일: 표준 로그아웃 전·후에 “브라우저가 보내는 표식 / 서버에 남은 인증 상태 / 보호 요청의 다음 판단”을 각각 적는다. CSRF 토큰이 왜 필요한지는 다음 교안에서 이어서 확인한다.

## 핵심 질문 답

기본 세션 기반 폼 로그인은 서버 세션의 보안 컨텍스트를 다음 요청에 이어 쓰며, 브라우저는 세션 ID 쿠키로 그 상태를 연결합니다. 기본 CSRF 보호 아래 GET /logout은 확인 화면이고 유효 토큰을 보낸 POST /logout이 세션과 인증 상태를 정리합니다. 화면만 바꾸는 일과 서버 로그아웃을 구분하고, 외부 토큰까지 자동 폐기된다고 확대하지 않아야 합니다.
