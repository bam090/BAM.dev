# 쿠키 인증과 CSRF 방어

## 학습 목표

세션 인증·인가와 변경 요청의 CSRF 검사를 별도 조건으로 판단할 수 있습니다.

## 한줄 요약

CSRF 방어는 브라우저가 자동으로 보내는 인증 정보만으로 변경 요청을 믿지 않도록 돕습니다.

## 로그인 쿠키가 있어도 요청 의도는 다를 수 있다

**CSRF(Cross-Site Request Forgery)**는 사용자가 로그인한 브라우저를 이용해, 사용자가 의도하지 않은 변경 요청을 보내게 하는 공격이다. 공격자가 쿠키 값을 읽지 못해도 브라우저의 쿠키 전송 조건에 맞으면 해당 서비스의 쿠키가 요청에 자동으로 붙을 수 있다.

```text
로그인한 브라우저 → 다른 사이트가 유도한 변경 요청
→ 서비스 쿠키가 함께 전달될 수 있음 → 사용자 의도와 별도로 인증될 수 있음
```

서버가 “세션 쿠키가 있고 쓰기 권한도 있다”만 확인하면 이 차이를 놓칠 수 있다. **CSRF 토큰**은 서버가 제공한 예측하기 어려운 값을 요청 파라미터나 헤더로 함께 보내고 확인하는 데 사용한다. 인증 정보, 권한, CSRF 토큰은 담당하는 판단이 다르다.

## 변경 요청에서 별도 조건을 확인한다

Spring Security의 기본 CSRF 보호는 POST 같은 안전하지 않은 HTTP 메서드에 적용된다. 아래는 세션 인증과 쓰기 권한이 이미 있는 사용자의 요청을 줄인 예제다. 본문 형식과 업무 입력은 유효하다고 보자.

```text
POST /notices
세션 쿠키: 있음
쓰기 권한: 있음
CSRF 토큰: 없음
```

기본 CSRF 검사와 기본 거부 처리를 사용하면 이 요청은 CSRF 단계에서 거부되어 403으로 이어진다. 로그인이나 쓰기 권한을 더 붙이는 것으로 누락된 토큰이 채워지지 않는다. 서버가 제공한 토큰을 정해진 파라미터 또는 헤더로 전달하는 경로를 확인한다.

## 공개 허용과 보호 해제는 다르다

`permitAll()`은 인가 조건이다. 해당 POST가 공개라고 선언해도 기본 CSRF 검사는 남는다. 반대로 GET은 기본 CSRF 검사 대상이 아니라는 점을 악용해 삭제·수정 기능을 GET으로 옮기면 안 된다. 안전한 메서드는 상태를 바꾸지 않도록 설계한다.

“REST API”나 “JWT”라는 이름만으로 CSRF가 불필요해지는 것도 아니다. 인증 정보가 쿠키처럼 자동 전송되는지 등 실제 전달 방식을 확인해야 한다. 이 세션 입문에서는 기본 보호를 유지한다.

직접 해볼 일: 위 요청에 “서버가 제공한 유효 CSRF 토큰”을 추가했을 때 달라지는 판단을 적는다. 토큰이 유효해져도 별도로 남는 권한·업무 검사를 하나씩 표시한다.

## 핵심 질문 답

CSRF 방어는 로그인한 브라우저가 자동으로 보내는 인증 정보만으로 변경 요청을 믿지 않도록 돕습니다. 세션 인증과 쓰기 권한이 있어도 기본 보호가 적용되는 POST에는 유효한 CSRF 토큰이 필요합니다. permitAll은 CSRF 검사를 없애지 않으며, API나 JWT라는 이름 대신 인증 정보의 실제 전송 방식을 보고 보호 조건을 판단해야 합니다.
