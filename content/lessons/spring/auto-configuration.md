# 자동구성의 조건 읽기

## 학습 목표

자동구성이 적용되는 조건과 직접 등록한 Bean이 그 조건에 미치는 영향을 설명할 수 있습니다.

## 한줄 요약

자동구성은 라이브러리·기존 Bean·설정값 등의 조건에 따라 기본 구성을 선택합니다.

## 먼저 확인할 개념

[Starter와 의존성](#/learn/spring/starters)

## 기본 구성은 조건을 보고 선택한다

두 앱이 같은 Boot 버전을 사용해도 라이브러리나 직접 등록한 Bean이 다르면 자동구성 결과가 달라질 수 있다. 자동구성은 모든 기능을 무조건 켜는 명령이 아니다.

아래는 자동구성의 조건을 읽기 위한 가상의 사례다. 실제 Boot 내장 기능의 이름이나 실행 로그가 아니다.

| 확인 조건 | 앱 A | 앱 B |
| --- | --- | --- |
| 알림 라이브러리가 있는가? | 있음 | 있음 |
| 이미 `Notifier` Bean을 등록했는가? | 없음 | 있음 |
| “기존 Notifier가 없을 때 기본 빈 제공” 조건 | 조건을 만족함 | 조건을 만족하지 않음 |

## 직접 등록하면 달라지는 조건

`@ConditionalOnMissingBean`처럼 특정 Bean이 없을 때만 적용되는 조건이 있다. 이 조건을 가진 자동구성은 사용자가 해당 타입의 Bean을 등록했으면 기본 Bean을 추가하지 않도록 설계할 수 있다. 직접 등록한 Bean이 모든 자동구성을 일괄 취소하는 것도 아니고, Boot가 사용자 Bean을 항상 덮어쓰는 것도 아니다. 각 조건을 확인해야 한다.

필요한 Bean이 없다면 먼저 라이브러리와 적용 조건을 확인한다. 실제 외부 프로젝트에서는 `--debug`로 조건 보고서를 확인할 수 있다. 보고서는 어떤 조건이 맞았거나 맞지 않았는지 조사하는 자료이며, 오류를 자동으로 고치는 스위치는 아니다.

직접 해볼 일: 표에서 앱 A가 `Notifier`를 직접 등록한 경우 달라질 칸을 고른다. 라이브러리 유무와 기존 Bean 유무 중 어느 조건이 바뀌었는지 한 문장으로 설명한다.

## 핵심 질문 답

Boot 자동구성은 클래스 경로의 라이브러리, 기존 Bean, 설정값 등의 조건을 보고 선택됩니다. 기존 Bean이 없을 때만 제공하는 기본 구성이라면 직접 등록한 Bean 때문에 그 조건이 달라질 수 있습니다. 필요한 구성이 없을 때는 어노테이션을 더 붙이기 전에 의존성과 조건 보고서를 확인합니다.
