# 개발·검증·통합 파이프라인

## 목적

`[확정 결정]` 이 문서는 작업 유형을 먼저 분류하고, 필요한 검증만 적용하며, 생성·검증·통합 책임과 증거를 분리하는 정본이다. 역할 이름은 작업마다 필요한 임시 책임을 뜻하며 Custom Agent TOML이나 상시 실행 에이전트를 만들라는 뜻이 아니다.

## 작업 유형 분류

저장소를 변경하는 작업은 아래 유형을 고르고 [작업 카드](#공통-판정과-작업-카드)에 범위와 완료 조건을 기록한다. 읽기 전용 질문·조사는 변경 파이프라인을 시작하지 않는다. 교육적 소급 감사 판정을 저장소에 기록하는 작업은 아래 학습 콘텐츠 유형에 해당한다.

| 유형 | 해당하는 변경 | 적용 파이프라인 |
| --- | --- | --- |
| 학습 콘텐츠 포함 기능 | 교안, 확인 문제, 객관식, Code Quest, 코딩테스트, 웹과제 brief·starter·solution, 기준답안·대표오답·학습자 피드백 또는 학습 목표를 추가·변경하거나 기존 콘텐츠 소급 감사·커버리지 판정을 기록 | 학습 콘텐츠 파이프라인 |
| 일반 제품 기능·코드 | 학습 내용은 바꾸지 않고 UI, 라우팅, 저장소, 평가 엔진, 설치·업데이트, 접근성, 성능, 보안, 버그를 변경 | 일반 제품 기능 파이프라인 |
| 문서·운영 규칙 | Markdown, ADR, `AGENTS.md`, 운영 절차만 변경하고 제품·콘텐츠·테스트·빌드·CI는 변경하지 않음. 학습 콘텐츠 소급 감사·커버리지 증거는 제외 | 문서 파이프라인 |

콘텐츠와 코드를 함께 바꾸면 학습 콘텐츠 포함 기능으로 분류한다. 소급 감사 결과가 Markdown만 바꾸더라도 교육적 판정과 MVP 커버리지를 만들므로 학습 콘텐츠 파이프라인을 사용한다. 한 PR에서 독립적으로 검증할 수 있는 변경은 분리하되, 콘텐츠와 그 콘텐츠를 실행하는 데 반드시 필요한 코드를 억지로 나누지 않는다. 분류가 애매하면 학습 목표·평가 계약·제품 동작에 미치는 영향을 먼저 확인하고 그 위험에 필요한 검증을 선택한다. 결과를 크게 바꾸는 미결정만 bam에게 반환한다.

## 읽기 전용 총괄과 임시 역할 운영

`[확정 결정]` [`DEC-ORCHESTRATION-01`](roadmap.md#2026-09-02-확정-운영-결정)에 따라 새 작업의 총괄 orchestrator는 조정 전용이며 프로젝트 파일을 직접 수정하지 않는다. 총괄은 작업 유형을 분류하고 작업 카드의 내용, 경로 소유권 표와 단계 순서를 작업 상태에서 정한 뒤 필요한 역할만 임시 하위 에이전트에게 위임한다. 카드 자체를 저장소에 기록해야 하면 허용 경로를 받은 제품·설계 문서 담당에게 맡긴다. 역할 이름은 매 작업에서 잠시 부여하는 책임이며 Custom Agent TOML이나 상시 실행 에이전트를 만들라는 뜻이 아니다.

총괄은 다음 책임만 가진다.

1. 실제 정본·코드·Git 상태를 읽고 작업 범위, 선행 결정과 완료 조건을 고정한다.
2. 문서·학습 문서 관리·시각 자산·콘텐츠/문제·제품 코드·테스트·Git의 쓰기 경로를 역할별로 나누고 선행 관계를 기록한다.
3. 같은 파일이나 겹치는 경로를 수정할 역할은 병렬 실행하지 않는다. 한 역할의 인계와 총괄 검토가 끝난 뒤 다음 역할에 소유권을 넘긴다.
4. 각 보고를 그대로 승인하지 않고 해당 역할의 실제 diff·관련 원문·명령 증거를 독립 대조한다. 반환 수정은 바뀐 경로와 무효화된 증거를 다시 확인하며 전체 diff·Git 상태는 최종 통합에서 확인한다.
5. `FAIL` 또는 필수 조건의 `BLOCKED`이면 직접 고치지 않고 원인에 해당하는 역할·단계로 반환한다. 이미 승인된 범위의 결함 수정·재검증은 다시 승인받지 않고 진행하며, 새로운 권한·범위·사람의 결정이 필요한 경우만 bam에게 올린다. 영향을 받지 않는 작업은 계속 진행한다.

총괄은 문서·콘텐츠·이미지·코드·테스트를 작성하거나 수정하지 않고, Git 상태를 바꾸는 명령도 실행하지 않는다. 읽기 전용 조사나 검토가 가능하다는 이유로 작성자·검증자·Git 담당을 겸하지 않는다.

## 공통 검증과 재검증

`[확정 결정]` [`DEC-CHANGE-VALIDATION-01`](roadmap.md#2026-09-14-확정-운영-결정)에 따라 변경 파일과 직접 영향받는 공통 기능·의존관계의 검사만 선정한다. 이미 통과했고 대상과 의존 코드가 바뀌지 않은 다른 주제는 실제 diff나 관련 hash로 유효성을 확인해 기존 증거를 재사용한다. 매번 전체 파일 hash나 전 과목 재감사를 요구하지 않는다. 통합 단계도 선정한 변경 범위의 실행·재사용 증거로 완료할 수 있으며 매 작업 `npm run check`·전체 테스트·빌드를 강제하지 않는다.

Spring 콘텐츠만 추가하면 새 문항·목표·정답·경로·연결 등 해당 변경 범위를 검사하고 무관한 HTML·CSS·JavaScript·Java 주제를 재실행하지 않는다. 공유 라우팅·저장·채점을 바꿨다면 직접 영향받는 대표 흐름을 추가한다. 공통 코드라는 이유만으로 전면 회귀로 넓히지 않는다. 전체 명령은 사용자가 명시적으로 요청했거나 실제 변경 영향이 전 범위임을 구체적으로 확인한 경우에만 그 범위에 맞게 실행하고 근거를 기록한다. 다른 작성 가이드나 과거 개별 작업 설계의 전체 gate 표현을 매 변경의 재실행 의무로 사용하지 않으며 이 변경 범위 선정 계약을 우선한다. 과거 실행 기록·설치형 MVP의 전체 제품 수용 범위는 유지한다.

실패 수정이나 후속 변경으로 무효화된 증거만 재확인하고 최초 실패·수정·재검증 이력은 보존한다. 문서 전용 변경과 검증 후 결과 기록만 바뀐 경우는 변경 diff·링크·규칙 충돌만 확인하고 제품 테스트·빌드를 실행하지 않는다. 실제 실행 명령·결과, 재사용한 증거와 유효성 근거, 미실행 범위를 구분해 인계하며 미실행을 신규 PASS로 쓰지 않는다.

승인된 작업 범위와 현재 권한 안에서 안전한 로컬 fixture·복제본을 사용하는 검사 및 그 실패 수정·재검증은 추가 승인을 요구하지 않는다. 명령이 기존 작업물을 생성·삭제한다면 안전한 복제본에서 실행한다. 보안 도구의 차단을 우회하거나 새 외부 전송·유료 실행·Git 권한으로 확대하지 않는다. `[현재 사실]` PR에서는 현재 CI가 `npm run check`를 실행한다. 이 CI 정의는 유지하며 매 로컬 작업의 전체 검사 반복 근거로 사용하지 않는다.

## 설계 정본 선행

`[확정 결정]` 구현 전에 대상 제품 경계의 설계 정본에서 현재 상태, 목표와 마이그레이션을 확인한다. 기존 정본이 질문에 답하지 못하고 사용자 흐름·데이터·실행·보안·배포 중 둘 이상에 영향을 주는 새 경계라면 `docs/designs/`에 설계를 추가한다. 함수·파일별 해설이나 기존 규칙 복사를 이유로 새 문서를 만들지 않는다.

설계 정본은 최소한 다음을 포함한다.

```text
상태와 근거: 현재 사실 | 확정 결정 | 대체됨 | 제안 | 추론 | 확인 필요
사용자 문제와 MVP 필요성:
현재 구조와 유지할 불변식:
목표 사용자 흐름과 상태:
콘텐츠·데이터·실행·저장 계약:
오프라인·접근성·모바일·안전 경계:
ID·URL·진도·파일 마이그레이션:
비범위와 실패 시 되돌릴 단계:
자동 검증·실제 사용 검증·사람 판단:
남은 결정과 결정자:
```

확정되지 않은 기술·저장소·branch를 구현 전제로 삼지 않는다. 목표 설계를 작성했다는 사실과 구현 완료를 분리한다.

학습 콘텐츠 작업은 다시 세 성격으로 나눈다.

- **새 경험**: 새 콘텐츠 추가, 학습 목표·힌트 수준·문제 계약·평가 행동을 의미 있게 바꾼다. A/E/C/T 경험 카드와 새 경험 gate가 필요하다.
- **유지보수**: 오탈자·사실 오류·깨진 출처·기존 기준답안·테스트 결함을 기존 학습 목표 안에서 고친다. 결함 근거와 기존 경험을 바꾸지 않는다는 영향 기록으로 경험 카드를 대신할 수 있다. 수정이 학습 행동이나 난이도를 바꾸면 새 경험으로 재분류한다.
- **소급 감사**: `DEC-MVP-01`의 release 차단 기존 콘텐츠를 [`DEC-CONTENT-01`](roadmap.md#2026-08-30-확정-제품-결정)과 [`learning-content-design.md`](learning-content-design.md#기존-콘텐츠-소급-감사)의 깊이에 따라 지도화·판정한다. 감사 자체는 콘텐츠 수정이 아니며, `REVISE`나 `MERGE/RETIRE` 결과는 별도 작업으로 반환한다.

## 공통 판정과 작업 카드

각 검토 단계는 다음 중 하나로 판정한다.

- `PASS`: 해당 단계에 선언한 필수 범위와 통과 조건을 증거로 확인했다. 중간 단계 PASS는 작업 전체 완료가 아니다.
- `FAIL`: 재현 가능한 결함이 있어 지정한 이전 단계로 돌려보낸다.
- `BLOCKED`: 필수 완료 조건에 필요한 정보·환경·권한·사람의 결정이 부족하다. 충족하지 못한 필수 조건을 추측으로 PASS 처리하지 않는다.
- `N/A`: 개별 검사에 적용할 계약이 없어 이유를 기록한다. 필수 검사를 실행하지 못한 상태를 N/A로 바꾸지 않는다. 선택 관찰의 미실행 한계는 별도로 기록한다.

변경 작업은 범위·허용/금지 경로·역할별 소유권·사용자 관찰 가능 완료 조건·검증 범위를 먼저 정한다. 작은 변경은 해당 필드만 작업 상태에 기록하고, 여러 제품 경계·학습 경험·Git 게시가 포함된 작업은 아래 전체 카드를 사용한다. 카드의 간소화는 역할 분리나 필수 검증 면제를 뜻하지 않는다.

```text
작업 ID와 유형:
변경 성격: 새 경험 | 유지보수 | 소급 감사 | 해당 없음
MVP 필요성 또는 로드맵 단계:
현재·목표 설계 정본과 상태:
허용된 변경 경로:
변경 금지 경로:
임시 역할별 경로 소유권과 작업 순서:
겹치는 경로의 선행 인계 조건:
입력 정본과 ADR:
사용자 관찰 가능 완료 조건:
접근성·승인된 대상 플랫폼·오프라인·데이터 영향:
담당 역할과 독립 검증자:
작업자·검증자별 focused 명령과 smoke 범위:
project_integrator의 선정한 변경 범위 검증·증거 재사용과 실행 위치:
Git 담당의 변경 권한과 단계별 허용 범위:
bam의 판단이 필요한 항목:
```

새 경험 작업은 [`learning-content-design.md`](learning-content-design.md)의 경험 카드를 추가한다. 유지보수는 재현 가능한 결함, 보존할 학습 목표와 영향 검증을 기록한다. 소급 감사는 고정한 manifest 범위, 깊이별 매핑·판정과 실행 증거를 기록한다. 필수 값이 빠졌고 결과가 크게 달라지면 구현하거나 PASS로 지도화하지 않고 `BLOCKED`로 보고한다.

Git 기준선과 PR이 생기기 전에는 총괄이 정한 역할별 작업 카드와 인계 결과를 제품·설계 문서 담당이 하나의 `docs/work-items/<work-id>.md`에 보존한다. PR 흐름이 활성화된 뒤에는 같은 내용을 PR 본문·리뷰에 누적하고, merge 때 장기 상태·결정·학습 커버리지만 해당 정본에 반영한다. 원시 로그를 여러 문서에 복제하지 않는다.

## 역할과 금지 사항

| 역할 | 책임 | 해서는 안 되는 일 |
| --- | --- | --- |
| 총괄 orchestrator | 작업 분류, 카드 범위·경로 소유권·순서 결정, 필요한 임시 역할 위임, 실제 파일·diff·명령 증거 대조와 단계 전환을 담당한다. | 작업 카드를 포함한 프로젝트 파일·자산·테스트 또는 Git 상태를 직접 바꾸거나 보고만 믿고 PASS하거나 실패 산출물을 대신 고치지 않는다. |
| 제품·설계 문서 담당 | 제품 목표, 아키텍처, 경계별 설계와 운영 정본을 근거에 맞게 편집한다. | bam의 학습 교안을 대신 생성·개작하거나 제품 구현·검증·Git 작업을 겸하지 않는다. |
| 문서 검토자 | 쓰기 없이 제품·설계 문서 diff의 정본 중복, 링크·앵커, 용어·규칙 충돌과 실제 상태 근거를 focused 범위로 확인한다. | 문서를 고치거나 정책을 대신 선택하거나 `project_integrator`의 통합 판정을 대신하지 않는다. |
| 학습 문서 관리자 (`learning_document_manager`) | bam이 작성한 학습 교안을 원문과 출처를 보존해 반입·정리하고, ID·링크·상태 표기·schema 연결을 확인해 독립 검증으로 넘긴다. | bam의 명시적 요청 없이 교육적 설명, 예시, 학습 순서나 결론을 새로 만들거나 의미가 달라지게 고쳐 쓰지 않는다. 자신의 관리 결과를 승인하지 않는다. |
| 시각 자산 담당 | 승인된 시각 요구에 따라 지정된 자산 경로의 이미지와 필요한 자산 메타데이터를 만들고 크기·형식·출처·대체 텍스트 후보를 인계한다. | 제품 코드나 소유하지 않은 manifest를 함께 수정하거나 UI 반영·접근성 완료를 스스로 승인하지 않는다. |
| 콘텐츠 생성자 | bam의 교안과 승인된 경험 카드에 맞춰 확인 문제, 객관식, Code Quest, 코딩테스트, 웹과제 brief·starter·solution, 기준답안·대표오답과 검증 후보를 작성한다. 교안 자체의 생성·재구성은 bam이 명시적으로 승인한 내용·경로에 한정한다. | 승인 범위 밖 교안을 생성·개작하거나 자신의 산출물을 최종 승인하거나 검증자 판정을 대신하지 않는다. |
| 제품 구현자 | 확정된 요구사항을 현재 아키텍처와 기술 경계 안에서 제품 코드로 구현하고 관련 기존 focused 검사를 실행한다. | 테스트 파일을 함께 작성하거나 범위를 몰래 넓히거나 실패한 검증을 완료로 보고하지 않는다. |
| 테스트 작성자 | 승인된 요구·계약으로부터 제품 구현과 독립된 기대값을 세우고 지정된 테스트 경로만 작성·수정하며 focused 검사를 실행한다. | 제품 코드·콘텐츠를 고치거나 자신이 작성한 테스트를 최종 검증하거나 구현 결과에 맞춰 기대값을 낮추지 않는다. |
| `content_validator` | 쓰기 없이 파일과 출처를 독립적으로 읽어 교육 목표, 정확성, A/E/C/T, 중복, 힌트, 계약 일치를 판정한다. | 검토 중 파일을 수정하거나 자신이 생성한 콘텐츠를 최종 승인하지 않는다. 실행 성공을 추측하지 않는다. |
| `test_engineer` | 쓰기 없이 승인된 요구·콘텐츠와 테스트의 범위·독립 기대값을 감사하고 필요한 focused 명령·브라우저 검증을 수행한다. | 테스트를 작성·수정하거나 제품·콘텐츠를 고치거나 학습 목표를 다시 정의하지 않는다. 테스트 개수만으로 충분성을 판단하지 않는다. |
| `project_integrator` | 쓰기 없이 앞 단계 PASS, 전체 diff, 경로 소유권, 문서 정합성과 증거 완전성을 확인하고 [공통 검증과 재검증](#공통-검증과-재검증)에 따라 통합 판정한다. | 실패한 산출물을 대신 수정하거나 선정한 필수 검증을 근거 없이 누락하거나 merge를 단독 승인하지 않는다. |
| Git 담당 | 작업 카드에 허용된 시점과 범위에서만 브랜치, commit, push와 PR을 수행하고 결과 식별자를 인계한다. | 통합 PASS 전 commit·push·PR을 수행하거나 bam의 명시적 승인 없이 merge하거나 검증 실패를 우회하지 않는다. |
| bam | 학습 교안의 저자이며 MVP 범위, 교육적 애매함, 위험 수용, 정책 예외, 우선순위와 최종 merge를 판단한다. | 자동 실패를 근거 없이 PASS로 바꾸는 역할로 사용하지 않는다. 예외라면 이유와 만료 조건을 기록한다. |

같은 작업 묶음에서 산출물을 작성하거나 관리한 제품·설계 문서 담당, 학습 문서 관리자, 시각 자산 담당, 콘텐츠 생성자, 제품 구현자와 테스트 작성자는 `content_validator`, `test_engineer` 또는 `project_integrator`를 겸할 수 없다. 제품·설계 문서 담당과 문서 검토자, 테스트 작성자와 읽기 전용 `test_engineer`도 각각 분리한다. 학습 콘텐츠의 세 검증 역할은 서로 분리하며, 총괄 orchestrator는 어느 쓰기·검증 역할도 대신하지 않는다. 독립 역할은 가능한 순서로 배치하며 순차 확보도 불가능하면 해당 검증 단계를 `BLOCKED`로 둔다. 독립성이 제한됐다는 기록으로 PASS를 대신하지 않는다.

## 사람이 이해하기 쉬운 코드 기준

[`DEC-CODE-QUALITY-01`](roadmap.md#2026-09-04-확정-운영-결정)에 따라 모든 새 코드와 실제로 수정하는 코드는 다음 관찰 가능한 기준으로 구현·검토한다. “클린 코드”는 특정 패턴 수나 파일 크기 하나로 판정하지 않고, 요구를 모르는 다음 작업자가 변경 이유와 영향 범위를 추적할 수 있는지로 판단한다.

| 기준 | 통과 증거 |
| --- | --- |
| 역할과 의도를 드러내는 이름 | 이름만으로 값·함수·모듈의 제품 역할을 구분하고, 약어나 포괄적 이름은 해당 영역에서 이미 합의된 경우에만 사용한다. |
| 응집된 책임 | 한 모듈·함수가 하나의 변경 이유를 중심으로 동작하며, 서로 다른 부작용이나 정책이 섞이면 호출 경계가 보인다. 단순히 줄 수를 줄이거나 늘리기 위한 분할은 하지 않는다. |
| 명시적 계약 | 입력·출력, 실패·오류, 저장·네트워크·DOM·프로세스 같은 부작용과 비동기 수명주기를 코드·타입·테스트에서 확인할 수 있다. |
| 재사용 우선순위 | 요구에 맞는 기존 프로젝트 패턴이나 표준 기능을 먼저 사용하고, 새 helper·계층·의존성은 기존 방식으로 해결할 수 없는 이유를 변경 근거에 남긴다. |
| 이유를 설명하는 주석 | 보안·호환성·제품 규칙처럼 코드만으로 알기 어려운 **왜**와 제약만 설명한다. 동작을 그대로 번역하거나 나쁜 이름·큰 책임을 주석으로 덮지 않는다. |
| 읽을 수 있는 작은 diff와 검증 | 요구와 직접 관련된 변경만 포함하고, 검토자가 변경 전후 행동을 따라갈 수 있으며 영향 범위의 focused 검사·수동 확인과 미실행 범위가 인계된다. |

다음은 비목표이며 통과 근거로 인정하지 않는다.

- 확인된 사용처 없이 미래 확장을 위해 계층·인터페이스·팩토리·설정 선택지를 미리 추가하는 일
- 구현 하나만 감싸며 교체·격리·테스트 가치가 없는 추상화
- 작은 중복보다 이해 비용을 키우는 과도한 분할이나 DRY 강박
- 짧지만 실행 순서·상태·오류를 해석하기 어려운 영리한 축약
- 설명 주석으로 모호한 이름, 뒤섞인 책임 또는 숨은 부작용을 정당화하는 일
- “클린 코드”, React·TypeScript 도입 또는 기술 현대화를 이유로 검증된 현재 구현을 전면 재작성하는 일

제품 구현자는 변경 근거와 focused 증거를 인계하고, 테스트 작성자와 `test_engineer`는 명시된 계약과 대표 실패를 검증하며, `project_integrator`는 작은 diff·기존 패턴 재사용·불필요한 추상화 여부를 전체 변경에서 확인한다. 기준을 충족하려면 제품 범위나 아키텍처를 바꿔야 할 때는 구현에서 결정하지 않고 기능 요구사항 확정 단계로 반환한다.

## 학습 콘텐츠가 포함된 기능

```text
bam의 학습 교안·목표 입력과 접근 방식 설계
→ 학습 문서 관리·콘텐츠 생성
→ 필요한 제품 구현·테스트 작성
→ content_validator
→ test_engineer
→ project_integrator
→ 기능 브랜치·PR
→ dev
```

[`DEC-LESSON-AUTHORSHIP-01`](roadmap.md#2026-09-02-확정-운영-결정)에 따라 학습 교안의 본문과 교육적 결론은 bam이 작성한다. bam이 생성을 명시적으로 요청하지 않는 한 에이전트가 교안 저자를 대신하지 않는다. 명시적으로 승인된 생성·재구성 범위와 그 완료에 필요한 수정은 다시 묻지 않고 지정 작성자가 수행하며, 관리 역할과 분리하고 원문·출처를 보존한다. 학습 문서 관리자는 ID·링크·상태·schema 연결을 맡고 교육 내용 보완은 권한을 받은 작성자에게 반환한다. 새 문제의 A/E/C/T 초안은 콘텐츠 생성자가 bam의 교안과 확정 범위 안에서 작성하며, 그 범위를 넘어서는 교안 보충이나 교육적 미결정은 bam에게 반환한다.

상위 순서의 제작 구간은 필요한 임시 역할만 부른다. 콘텐츠 실행에 제품 코드나 시각 자산이 꼭 필요하면 콘텐츠 생성자는 문제와 명시적으로 승인된 파생 교안을, 제품 구현자는 UI·평가·저장 코드를, 시각 자산 담당은 지정된 자산을, 테스트 작성자는 독립 기대값의 테스트를 각자 소유한 경로에 작성한다. 겹치는 경로가 있으면 총괄이 순차 인계한다. `content_validator`는 콘텐츠만 독립 판정하고, `test_engineer`는 콘텐츠 PASS 뒤 결합된 콘텐츠·코드·테스트를 읽기 전용으로 실행 검증한다.

소급 감사만 하는 작업은 새 콘텐츠를 만들지 않으므로 `콘텐츠 생성·필요 구현` 단계에서 읽기 전용 inventory와 감사 증거 묶음만 준비한다. 이 생략이 독립 검증을 면제하지 않는다. 감사 작성자는 자신의 지도를 최종 승인할 수 없고, 변경 필요 판정은 같은 감사 안에서 고치지 않고 별도의 새 경험 또는 유지보수 작업으로 설계 단계에 반환한다.

| 단계 | 입력 자료 | 담당·수행 작업 | 통과 조건 | 실패 시 반환 | 다음 역할에 넘길 증거 | 사람이 판단할 내용 |
| --- | --- | --- | --- | --- | --- | --- |
| 학습 목표·접근 방식 설계 | bam의 학습 교안·요구, 제품 범위, 로드맵, 기존 문제·커버리지, 출처 또는 유지보수 결함 | bam이 교안과 교육 범위를 제공·결정한다. 제품·설계 문서 담당은 MVP 이유와 제품 완료 행동을 기록하고, 콘텐츠 생성자는 그 범위 안에서 문제용 A/E/C/T·사다리·독립성 초안을 만든다. 소급 감사면 release manifest와 감사 깊이·단위를 고정한다. | 새 경험은 기존 문제로 대체할 수 없는 이유가 있고 교안 내용을 임의 보충하지 않는다. 유지보수는 재현 근거와 목표 비변경 근거가 있다. 소급 감사는 대상 ID 누락을 확인할 수 있고 범위가 한 작업으로 검증 가능하다. | 제품 범위는 제품·설계 문서 담당, 교육적 내용은 bam, 문제 설계·감사 범위는 콘텐츠 생성자 | 작업 카드, 경험 카드·결함 기록 또는 감사 범위, 비교 대상과 출처, 미결정 목록 | MVP 포함, 교육 범위와 교안 내용, 변경 성격이 애매한 경우 |
| 학습 문서 관리·콘텐츠 생성·필요 구현 | 승인된 bam 교안, 카드·유지보수 결함 기록 또는 소급 감사 범위, 콘텐츠 계약, 형식별 가이드, 아키텍처·ADR, 출처 | 학습 문서 관리자는 교안을 보존·연결하고, 콘텐츠 생성자는 문제·기준답안·대표오답·검증 후보와 명시적으로 승인된 파생 교안을, 제품 구현자는 필요한 지원 코드를, 시각 자산 담당은 필요한 자산을 경로별로 분리 작성한다. 소급 감사는 콘텐츠를 고치지 않고 깊이별 지도·항목 판정·근거만 작성한다. | 교안 원문과 출처가 보존되고 새 경험은 카드와 ID가 연결되며 유지보수는 목표가 보존된다. 소급 감사는 모든 대상 ID와 판정 근거가 있으며 변경 필요 항목을 별도 작업으로 반환한다. | 교안 반입 결함은 학습 문서 관리자, 문제 결함은 콘텐츠 생성자, 코드 결함은 제품 구현자, 자산 결함은 시각 자산 담당, 범위 결함은 앞 설계 | 역할별 변경 파일 또는 읽기 전용 감사 목록, ID 연결, focused 명령·결과, 가정과 한계 | 원문 의미를 바꾸는 편집, 감사의 교육적 판정, 구현으로 학습 범위가 달라지는 선택 |

| `content_validator` | 카드·결함 기록 또는 소급 감사 지도, 변경 파일, 출처, 기존 커버리지와 자체 검사 결과 | 독립 검증자가 정확성·출처·난이도·중복·A/E/C/T, 기존 목표 보존 또는 깊이별 감사 판정의 근거를 읽기 전용으로 확인 | 새 경험은 반복·중복 차이가 설명되고, 유지보수는 목표가 의도치 않게 바뀌지 않았다. 소급 감사는 누락 ID·근거 없는 KEEP·잘못된 L/T 판정이 없으며 검증하지 못한 사실이 표시된다. | 콘텐츠 결함은 생성, 목표·필요성·분류·감사 결함은 설계 | PASS/FAIL/BLOCKED, 확인 파일·출처, 항목별 근거, 정확한 실패 위치 | 교육적 독립성, 유지보수 범위, 감사 판정 또는 사실 근거가 불충분한 경우 |
| `test_engineer` | 콘텐츠 PASS. 새 경험·유지보수는 결합된 diff·기준답안·대표오답·테스트 계약, 소급 감사는 지도·기존 콘텐츠 snapshot·현재 검증 계약 | 쓰기 없이 실행 콘텐츠의 스키마·공개 평가·기준답안·대표오답과 필요한 브라우저 흐름을 focused 범위로 확인한다. 비실행 교안·객관식은 출처·정답 판정·교안 연결과 계약 검사를 감사하고 적용할 실행 계약이 없으면 `N/A` 이유를 확인한다. audit-only는 새 테스트 diff를 요구하지 않고 기존 증거가 현재 판정을 실제로 지지하는지 재실행·감사한다. | 새 경험·유지보수는 요구된 focused 실행이 통과하고 테스트가 의도한 실패를 잡는다. 소급 감사는 적용 가능한 기존 실행이 재현되고 비실행 범위는 근거 검증 또는 명시적 `N/A`가 있으며, 모든 경로에서 미실행 범위가 기록된다. | 콘텐츠 결함은 콘텐츠 생성자, 테스트 결함은 테스트 작성자, 제품 코드 결함은 제품 구현자, 감사 증거 결함은 감사 설계, 설명 영향은 `content_validator`부터 | 환경, 정확한 명령·`N/A` 이유, 통과 수, 실패 재현 입력, 브라우저 범위, 남은 위험 | 자동화할 수 없는 교육·시각·사용성·자가평가 관찰 |
| `project_integrator` | 두 PASS, 전체 diff, 문서·ADR, Git 상태, 검증 증거 | 쓰기 없이 범위 밖 변경·경로 소유권·규칙 충돌·누락 링크·ID 영향·접근성·모바일·데이터·안전 회귀를 확인하고 [공통 검증과 재검증](#공통-검증과-재검증)에 따라 선정한 변경 범위 검증과 필요한 대표 흐름의 실행·재사용 증거를 확인한다. | 선정한 변경 범위의 실행·재사용 증거가 완전하고 PR 단위가 작고 되돌릴 수 있고 미결정이 merge를 막지 않음 | 결함 성격에 맞는 가장 이른 역할·단계 | 통합 판정, 실행 명령·결과와 재사용·미실행 범위, 문서/링크 확인, PR 체크리스트와 남은 위험 | 예외 수용, 미결정의 merge 차단 여부 |
| 기능 브랜치·PR → `dev` | 통합 PASS, 허용된 Git 작업, `codex/<feature>` 브랜치 | Git 담당이 한국어 커밋·PR 설명에 새 경험의 A/E/C/T, 유지보수 결함 또는 소급 감사 범위·판정 근거, 검증 증거와 위험을 남기고 `dev` 대상 작은 PR에서 CI·리뷰를 받는다. merge는 bam의 명시적 승인 뒤에만 수행한다. | 선정한 로컬 변경 범위 검증, 정의된 CI, 독립 리뷰와 bam 승인이 모두 확인되고 merge SHA가 남음 | CI 실패는 해당 생성·구현·테스트 역할, 감사·증거 누락은 설계/통합 | PR URL, CI 결과, 승인과 merge SHA | 최종 merge와 정책 예외 |

브랜치는 작업 카드가 명시하고 총괄의 기준선 검토가 끝났을 때 Git 담당이 작업 격리를 위해 먼저 만들 수 있다. commit·push·PR은 통합 PASS 뒤, merge는 CI·리뷰와 bam의 명시적 승인 뒤에만 수행한다.

## 문서와 운영 규칙 변경

```text
문서 수정
→ 중복·링크·규칙 충돌 검증
→ project_integrator
→ 기능 브랜치·PR
→ dev
```

bam이 작성한 학습 교안의 반입·정리·연결은 Markdown만 바뀌어도 학습 콘텐츠 파이프라인을 사용한다. 이 문서 파이프라인의 `문서 수정`은 제품·설계·운영 정본에만 해당한다.

| 단계 | 입력 자료 | 담당·수행 작업 | 통과 조건 | 실패 시 반환 | 다음 역할에 넘길 증거 | 사람이 판단할 내용 |
| --- | --- | --- | --- | --- | --- | --- |
| 문서 수정 | [`docs/README.md`](README.md), 해당 정본, 실제 코드·Git 근거, 최신 지시 | 제품·설계 문서 담당이 현재 사실·확정 결정·대체됨·제안·추론·확인 필요를 구분하고 정본 한 곳만 수정 | 범위 밖 학습 교안·제품·테스트·CI를 바꾸지 않고 존재하지 않는 성과를 주장하지 않음 | 제품·설계 문서 담당 | 변경 문서, 근거 파일·명령, 의도와 미결정 | 정책 채택·폐기, 제품 범위 |
| 중복·링크·규칙 충돌 검증 | 문서 diff, 문서 지도, AGENTS, ADR, 로컬 링크 | 독립 문서 검토 역할이 쓰기 없이 변경 범위의 로컬 링크·앵커, 용어, 역할·파이프라인, 정본 중복과 실제 상태 충돌을 focused 검사로 확인 | 깨진 링크 0, 같은 규칙의 상충 정의 0, 정본 밖 복사 최소화, 미해결 충돌 명시 | 제품·설계 문서 담당 | 링크 검사 결과, 중복·충돌 검색 범위, 확인 필요 목록 | 서로 다른 정책 중 어느 것을 정본으로 채택할지 |
| `project_integrator` | 문서 검증 PASS, 전체 diff·Git 상태·검증 증거 | 쓰기 없이 범위와 경로 소유권을 대조하고 [공통 검증과 재검증](#공통-검증과-재검증)에 따라 변경 문서 diff·링크·규칙 충돌과 PR 준비를 확인한다. | 변경 문서의 범위·링크·규칙 정합성이 통과하고 merge 차단 미결정이 없음 | 문서 결함은 제품·설계 문서 담당, 검증 증거 결함은 문서 검토 역할 | 통합 판정, 문서 확인·재사용 근거와 미실행 범위·남은 위험 | 적용 불가 검사와 운영 예외 수용 |
| 기능 브랜치·PR → `dev` | 통합 PASS와 허용된 Git 작업 | Git 담당이 `codex/<feature>` PR에서 문서 영향과 미결정을 설명하고 CI·리뷰를 받으며 bam의 명시적 승인 뒤에만 merge한다. | 적용 가능한 CI와 리뷰가 통과하고 bam이 운영 규칙과 merge를 승인 | 해당 실패 역할·단계로 반환 | PR·CI·승인·merge SHA | 운영 규칙의 최종 채택과 merge |

문서 전용 변경은 변경 diff·링크·규칙 충돌 확인으로 완료하며 제품 테스트·빌드를 실행하지 않는다. 선정한 필수 문서 검증을 실제로 수행할 수 없다면 PASS로 바꾸지 않고 `BLOCKED`와 부족한 근거를 명시한다.

## 역할별 최소 인계 형식

```text
상태: PASS | FAIL | BLOCKED
작업 ID·유형·담당 역할:
확인하거나 변경한 파일:
수행 내용과 범위 밖으로 남긴 내용:
실행한 정확한 명령·환경·결과:
수동으로 확인한 흐름과 viewport/입력:
학습 경험 또는 요구사항 충족 근거:
실패 위치·재현 입력·돌아갈 단계:
가정, 미실행 범위와 남은 위험:
bam의 판단이 필요한 항목:
다음 역할이 할 일:
```

원시 로그 전체 대신 재현 가능한 핵심 증거를 남긴다. 실행하지 않은 테스트를 실행 PASS로 기록하지 않는다. 단계별 PASS·검사별 N/A와 필수 조건의 BLOCKED는 [공통 판정](#공통-판정과-작업-카드)을 따른다.

## Definition of Done

### 공통

- 승인된 사용자 범위의 구현·콘텐츠·연결·필요 검증·결함 수정·인계가 끝나야 작업 완료다. 중간 산출물이나 단계 PASS만으로 완료하지 않으며, 요청한 완료 조건을 모두 만족하는 가장 단순한 결과를 만든다.
- 작업 카드의 범위와 실제 diff가 일치하고 기존 사용자 변경을 손상하지 않는다.
- 총괄이 역할별 경로 소유권과 순차 인계를 실제 diff에 대조했고 겹치는 경로를 동시에 수정한 기록이 없다.
- 대상 제품 경계의 현재·목표·마이그레이션·검증이 정본에 있고 목표를 현재 구현으로 표현하지 않는다.
- 현재 사실·제안·미결정을 구분하고 관련 정본·ADR·링크가 최신이다.
- 실패·빈 상태·취소·저장 장애와 접근성 영향이 필요한 수준으로 검증된다. 실제 플랫폼별 구현·검사는 승인된 대상에 한정하며 전체 모바일 지원 목표를 개별 작업의 gate로 확대하지 않는다.
- [공통 검증과 재검증](#공통-검증과-재검증)에 따라 선정한 변경 범위의 실행·재사용 증거를 확인했고 필요한 대표 흐름·환경·미실행 범위·남은 위험이 인계된다.
- 커밋·PR·CI·merge를 실제 확인하지 않았다면 완료 성과로 표현하지 않는다.

### 학습 콘텐츠 변경 조건

- 새 경험은 MVP 이유와 경험 카드가 있고 새 A, 새 E, 의미 있는 C 또는 T 확인 기회 중 하나 이상의 설계 근거가 있다.
- bam이 제공한 교안 원문·출처가 보존되고 학습 문서 관리로 교육적 의미를 임의 변경하지 않았다.
- 유지보수는 재현 가능한 결함, 보존할 기존 학습 목표와 영향 기록이 있다.
- 소급 감사는 release 대상 ID를 빠짐없이 지도화하고 정해진 깊이의 A/E/C/T·L단계·필요한 반복·중복 판정과 적용 가능한 실행 증거 또는 명시적 `N/A` 이유가 있으며, 변경 필요 항목을 같은 작업에서 고치지 않고 반환한다.
- 새 경험은 기존 콘텐츠와의 반복·중복 판정이 있고 모든 변경은 출처 기록을 유지한다.
- 안정 ID·순서·파일·교안·개념 연결과 형식별 계약이 유효하다.
- 기준답안은 공개·독립 사례를 통과하고 대표오답은 의도한 사례에서 실패한다.
- 테스트 작성자가 콘텐츠·제품 작성자와 분리된 기대값을 제공하고, 작성·관리 역할과 분리된 `content_validator`, `test_engineer`, `project_integrator`가 순서대로 PASS한다.

### 제품 코드 추가 조건

- 요구사항과 비범위가 고정되고 현재 아키텍처·ADR을 지킨다.
- [사람이 이해하기 쉬운 코드 기준](#사람이-이해하기-쉬운-코드-기준)을 변경 근거·작은 diff·focused 검증 증거로 확인한다.
- 제품 구현자와 분리된 테스트 작성자가 승인 계약에 근거한 테스트를 작성한다.
- 단위·영향 회귀·실제 브라우저 범위가 위험에 비례해 확인된다.
- 데이터 저장, 평가 안전, 오류 표현, 키보드와 좁은 화면을 손상하지 않는다.
- `test_engineer`와 `project_integrator`가 각각 PASS한다.

### 문서 변경 조건

- 정본이 하나이고 다른 문서는 링크한다.
- 제품·설계 문서 담당과 읽기 전용 문서 검토자·`project_integrator`가 분리되어 있다.
- [`docs/README.md`](README.md#설계-문서화-범위)의 커버리지와 대상 설계 상태가 실제 변경에 맞는다.
- 깨진 로컬 링크·앵커와 역할·파이프라인 용어 충돌이 없다.
- 코드·테스트·Git·CI에서 확인하지 않은 상태를 사실로 만들지 않는다.
- bam의 결정이 필요한 항목이 [`roadmap.md`](roadmap.md)에 한 번만 기록된다.

## Git·CI와의 연결

### 목표 흐름

`[확정 결정]` 저장소 운영 규칙은 `dev`를 통합 브랜치로, 이후 기능 브랜치를 `codex/<feature>`로, 한국어 커밋·PR 설명을 사용하도록 정한다. force push, `reset --hard`, `clean`은 사용하지 않는다. 0~3차의 역사적 특수 브랜치 규칙은 새 기능 브랜치 이름의 선례로 재사용하지 않는다.

`[확정 결정]` 총괄과 다른 작성·검증 역할은 읽기 전용 Git 조사만 수행한다. Git 상태를 바꾸는 작업은 작업 카드의 권한과 선행 gate를 확인한 Git 담당만 수행한다. commit·push·PR은 통합 PASS 전에는 허용하지 않고, merge는 CI·리뷰가 통과하더라도 bam의 명시적 승인 없이는 수행하지 않는다.

`[현재 사실]` 로컬 CI 정의는 `dev`·`main` 대상 PR과 `dev`·`codex/**` push에서 Node 22, `npm ci`, `npm run check`를 실행한다. 이 명령은 콘텐츠 검증, Node 테스트와 정적 빌드다. 실제 브라우저 smoke, 문서 링크, 역할 승인, 브랜치 크기는 현재 workflow가 강제하지 않으므로 증거 묶음과 리뷰에서 보완한다.

`[현재 사실]` 앞선 조사에서 원격·커밋이 없다고 확인한 대상은 첫 커밋 전 `codex/js-foundation`인 원본 로컬이었다. 2026-09-13 게시 요청 뒤 기존 GitHub 저장소의 `dev`·`main`과 원격 이력을 확인했다. 최신 게시 범위는 [`DEC-GIT-01`](roadmap.md#bam-결정-대기-목록), 기준 SHA와 로컬·원격 차이 및 실제 수행 결과는 [게시 작업 카드](work-items/2026-09-13-github-publication.md)를 따른다. 이번 별도 브랜치·Draft PR의 gate는 검증된 로컬 스냅샷과 게시 기록의 정합성을 확인하며, 원격에만 있는 기능의 통합·폐기 승인이나 merge PASS를 뜻하지 않는다.

## 현재 구현을 멈추지 않는 전환 원칙

`[확정 결정]` 전환 단계와 순서는 [`roadmap.md`의 D1·M0~M6](roadmap.md#설치형-오프라인-mvp-전환-로드맵)가 유일한 정본이다. 기존 파일 구조·스키마·런타임을 전면 재작성하지 않고 새 작업과 실제로 수정하는 기존 콘텐츠부터 새 카드와 역할 gate를 적용한다. [`DEC-CONTENT-01`](roadmap.md#2026-08-30-확정-제품-결정)의 전수 지도는 한 묶음에서 형식을 시범 검증한 뒤 release 차단 범위에 확장하고, 실제 차단 gap만 별도 작은 작업으로 보강한다. 기존 원격 이력의 발견과 이번 작업의 PR·CI·merge 완료를 구분하고 각각 확인한 결과만 기록한다.
