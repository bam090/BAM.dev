# 학습 콘텐츠 설계 기준

## 목적과 적용 범위

`[확정 결정]` [`DEC-LEARNING-01`](roadmap.md#2026-08-29-확정-제품-결정)에 따라 이 문서는 교안, 확인 문제, 객관식, Code Quest, 코딩테스트와 웹과제가 **어떤 새 학습 경험을 제공해야 하는지** 판단하는 정본이다. 교안 작성은 [`lesson-authoring.md`](lesson-authoring.md), 파일 형식과 실행 계약은 [`content-schema.md`](content-schema.md)와 형식별 작성 가이드가 담당한다.

새 콘텐츠는 문제 개수나 화면 수보다 다음 능력을 키워야 한다.

1. 중요한 조건과 단서를 찾는다.
2. 사용할 접근 방식과 자료 표현을 고른다.
3. 그 선택이 맞는 이유와 적용되지 않는 조건을 설명한다.
4. 입력에서 결과까지 데이터와 상태의 흐름을 추적한다.
5. 풀이 순서를 의사 코드와 실제 코드로 옮긴다.
6. 공개된 결과와 실패 근거로 자신의 판단을 수정한다.
7. 지원을 줄인 처음 보는 작은 문제에서도 풀이를 시작한다.

## BAM.dev 학습 경험 단위: A/E/C/T

Algorithm Bridge의 접근 원자(A), 순서 있는 접근 연결(E), 힌트 없는 전이(T)에 BAM.dev의 경계·상태·평가 콘텐츠에 필요한 조건 변화(C)를 더한다. 여기서 `T`는 학습 성과를 이미 입증했다는 뜻이 아니라, 전이를 관찰할 수 있도록 설계한 과제와 지원 조건을 뜻한다.

| 기호 | 이름 | 의미 | 새 경험으로 인정되는 예 |
| --- | --- | --- | --- |
| `A` | 접근 원자 | 다른 문제에도 재사용할 수 있는 한 가지 판단 또는 행동 | “현재 값에 필요한 짝을 계산한 뒤 이전 값 집합에서 찾는다.” |
| `E` | 접근 연결 | 앞 행동의 결과를 다음 행동의 입력으로 넘기는 순서 있는 조합 | “빈도를 만든 뒤, 빈도와 원래 순서를 기준으로 결과를 정렬한다.” |
| `C` | 조건 변화 | 같은 원자라도 상태·경계·불변식·선택 기준을 실제로 바꾸는 조건 | 중복 허용 때문에 `Set` 대신 개수를 가진 `Map`이 필요해짐 |
| `T` | 무힌트 전이 확인 기회 | 처음 보는 작은 문제에서 단서→선택→이유→흐름→구현 시작을 관찰할 수 있게 설계한 과제 | 새 소재·계약에서 접근 이름과 단계 힌트 없이 방법을 선택하도록 요구함 |

API나 자료구조 이름만으로 `A`를 정의하지 않는다. 좋은 접근 문장은 `입력 관찰 → 저장하거나 바꿀 값 → 다음 판단 → 결과 생성`의 실제 행동 순서가 보인다. `Map을 쓴다`, `BFS로 푼다`, `적절히 처리한다`만으로는 부족하다.

`C`는 단순한 숫자·이름·소재 교체가 아니다. 조건 때문에 저장 정보, 처리 순서, 종료 조건, 정답의 형태 또는 성립하는 접근이 달라져야 한다.

## 콘텐츠를 쓰기 전에 할 설계

`[확정 결정]` 새 콘텐츠를 만들거나 학습 목표·힌트 수준·문제 계약을 의미 있게 바꾸기 전에 대상 묶음의 학습 사다리와 문제별 경험 카드를 먼저 작성한다. 카드가 통과하지 못하면 새 경험 콘텐츠를 생성하지 않는다.

오탈자, 사실 오류, 깨진 출처, 기존 기준답안·테스트 결함을 같은 학습 목표 안에서 고치는 유지보수는 새 A/E/C/T를 요구하지 않는다. 대신 결함과 기존 경험을 보존한다는 영향 근거를 남기고 동일한 독립 콘텐츠·실행 검증을 받는다. 수정이 학습 행동이나 난이도를 바꾸면 새 경험으로 재분류한다.

### 접근 방식·조합 설계 순서

1. MVP 학습 목표와 선수 개념을 정한다.
2. 학습자가 문제에서 발견할 단서를 적는다.
3. 필요한 `A`를 실제 행동 문장으로 나눈다.
4. 두 개 이상의 `A`가 필요하면 결과가 전달되는 순서 `E`를 적는다.
5. 접근을 바꾸거나 오답을 만드는 의미 있는 조건 `C`를 적는다.
6. 어느 지원 수준에서 연습하고 어디에 `T` 확인 기회를 둘지 정한다.
7. 기존 콘텐츠와 아래 독립성 차원을 비교한다.
8. 필요한 A/E/C/T를 덮는 최소 콘텐츠만 남긴다.

여러 새 판단을 한 문제에 한꺼번에 넣어 첫 행동이 보이지 않게 하지 않는다. 반대로 한 문제에서 가까운 원자와 조건을 자연스럽게 함께 배울 수 있으면 문제 수를 늘리기 위해 나누지 않는다.

### 학습 경험 카드

작업마다 다음 값을 채운다. 설계 단계의 카드는 작업 증거 묶음에 두고, 통합된 콘텐츠의 요약은 아래 커버리지 등록부에 남긴다.

```text
작업 ID와 대상 콘텐츠 ID:
MVP에 필요한 이유:
선수 개념과 연결 교안:
학습자가 발견할 단서:
새 접근 원자 A:
다시 사용하는 접근 원자 A:
새 순서 연결 E:
의미 있는 조건 변화 C:
무힌트 전이 확인 기회 T:
사다리 단계와 제공할 지원:
학습자가 자신의 말로 설명할 문장:
기존 콘텐츠와의 독립성 비교:
잡아야 할 대표 오답·오개념:
필요한 공개 사례와 독립 검증 범위:
출처와 확인 날짜:
사람의 판단이 필요한 항목:
```

카드 항목 일부는 비어 있을 수 있지만 **새 A, 새 E, 의미 있는 C, 새 T 확인 기회 중 하나 이상**이 있어야 새 문제를 만들 수 있다. `다시 사용하는 A`만으로는 추가 근거가 아니다. `T`는 단지 힌트를 숨긴 문제가 아니라, 앞 단계에서 연습한 원자나 연결을 다른 계약에서 학습자가 스스로 선택하도록 요구하는 과제여야 한다. 실제 학습자 관찰이 없으면 이를 전이 성과라고 보고하지 않는다.

## 지원을 줄이는 학습 사다리

`[확정 결정]` 모든 주제에 문제를 정확히 다섯 개 만들라는 뜻이 아니다. 한 콘텐츠가 가까운 두 단계를 함께 다룰 수도 있고, 이미 검증된 단계는 건너뛸 수 있다.

| 단계 | 학습자가 하는 일 | BAM.dev에서 가능한 형태 | 지원 원칙 |
| --- | --- | --- | --- |
| L0 관찰 | 작은 값과 실행 흐름을 손으로 따라간다. | 교안 예제·실행 흐름·확인 질문 | 정답 코드보다 개념과 관찰 지점을 먼저 보여 준다. 문제 수로 세지 않는다. |
| L1 한 행동 | 한 접근 원자로 작은 결과를 만든다. | 짧은 실습·객관식·Code Quest | 생각 질문과 작은 힌트를 제공한다. |
| L2 행동+조건 | 같은 원자에 경계·중복·상태·원본 보존 같은 조건을 적용한다. | Code Quest·조건형 확인 문제 | 접근 방식은 접거나 뒤에 두고, 필요한 힌트만 단계적으로 제공한다. |
| L3 접근 조합 | A의 결과를 B로 넘기는 순서를 스스로 나눈다. | 지원을 줄인 Code Quest·코딩테스트·웹과제 일부 | 질문은 줄 수 있지만 전체 조합이나 정답 순서를 먼저 말하지 않는다. |
| L4 전이 확인 기회 | 새 계약에서 단서→선택→이유→흐름→의사 코드→구현을 시작한다. | 힌트를 줄인 Code Quest·코딩테스트·여러 요구사항의 웹과제 | 풀이 힌트는 시도 전 제공하지 않고, 구현 뒤 비교·회고 근거를 제공한다. 실제 수행 여부는 별도 관찰이 필요하다. |

Code Quest나 코딩테스트라는 기능 이름, 또는 하나의 문제에서 “테스트 실행”과 “제출” 버튼이 다르다는 사실만으로 단계가 달라지지 않는다. 학습자가 받는 정보와 스스로 해야 하는 판단이 실제로 달라져야 한다.

## 새 학습 경험 판정

`[확정 결정]` 새 문제는 다음 중 하나 이상의 설계 근거를 구체적으로 설명할 때만 추가한다.

- 아직 다루지 않은 `A`를 처음 연습한다.
- 이미 배운 원자를 새로운 순서 `E`로 연결한다.
- 접근 선택이나 상태 흐름을 바꾸는 `C`를 연습한다.
- 같은 접근 계열을 지원이 줄어든 새 계약에서 스스로 선택하게 하는 `T` 확인 기회를 만든다.

다음은 추가 근거가 아니다.

- 제목, 인물, 이야기, 상수나 배열 값만 바꾼다.
- 입출력과 판단 순서가 같은데 문장만 다르게 쓴다.
- 이미 잡는 대표 오답과 같은 오답만 다시 잡는다.
- 같은 힌트와 같은 실패 설명을 제공한다.
- 난이도나 콘텐츠 수 목표를 맞추기 위해 추가한다.

판단 근거가 부족하면 `PASS`로 추측하지 않고 `BLOCKED`로 둔다. 새로운 경험인지 교육적으로 애매한 경우 bam이 최종 판단한다.

## 필요한 반복과 중복의 구분

같은 접근을 다시 쓰는 것은 학습 전이를 위해 필요할 수 있다. 아래 여섯 차원을 기존 콘텐츠와 비교한다.

1. 소재와 맥락
2. 목표와 반환·표현 결과
3. 입력·출력 구조
4. 제약과 추가 조건
5. 접근 조합과 결과 생성 흐름
6. 질문·힌트·피드백을 포함한 지원 수준

### 필요한 반복

다음 중 하나가 있으며 경험 카드에 관찰 가능한 차이를 설명하면 필요한 반복이다.

- 같은 원자를 다른 자료 표현이나 결과 형태로 회상한다.
- 경계·중복·동점·도달 불가·원본 보존 때문에 판단이나 구현이 달라진다.
- 익힌 원자를 다른 원자와 새 순서로 연결한다.
- 흔한 오개념 하나를 의도적으로 드러내고 수정하게 한다.
- 시간 간격이나 과정 경계를 두고 힌트를 줄여 독립 전이를 확인한다.

### 중복 문제

다음에 해당하면 새 콘텐츠로 추가하지 않고 기존 콘텐츠를 보강하거나 후보를 폐기한다.

- 목표·입출력·제약·처리 순서·지원 수준이 사실상 같다.
- 식별자·소재·상수·출력 문구만 바꾸면 기존 기준 답안을 거의 그대로 쓸 수 있다.
- 기존 테스트를 그대로 복사해도 새 대표 오답이나 경계가 추가되지 않는다.
- 기존 문제보다 새 학습 행동을 설명할 수 없다.

핵심 알고리즘 골격이 같다는 이유만으로 중복으로 판정하지 않는다. 반대로 소재가 다르다는 이유만으로 독립 문제라고 판정하지 않는다.

## 기존 콘텐츠 소급 감사

`[확정 결정]` [`DEC-CONTENT-01`](roadmap.md#2026-08-30-확정-제품-결정)에 따라 새 경험과 학습 행동·목표·힌트·평가 계약을 의미 있게 바꾸는 작업에는 위 경험 카드를 즉시 적용한다. M6 전에는 [`DEC-MVP-01`](roadmap.md#bam-결정-대기-목록)이 release 차단 범위로 정한 기존 콘텐츠를 하나도 빠뜨리지 않고 지도화한다. MVP 과정·콘텐츠 ID와 과정별 관찰 가능한 핵심 완료 행동이 확정되지 않았으면 권장안이나 모든 `curriculum.objectives`를 차단 범위로 추측하지 않고 전체 완료 판정을 `BLOCKED`로 둔다.

소급 감사는 현재 상태와 빈칸을 드러내는 작업이지 기존 콘텐츠의 PASS 선언, 전면 재작성, 스키마 필드 추가 또는 자동 삭제가 아니다. 순수 오탈자·사실 오류·출처·기준답안·테스트 결함은 기존 학습 목표를 보존한다는 결함·영향 기록으로 대신한다. release 범위 밖 콘텐츠와 `sample`·`planned` 과정은 정식 승격하거나 학습 행동을 의미 있게 바꿀 때 심층 적용한다.

### 감사 깊이

모든 대상은 전수 지도에 들어가고, 콘텐츠가 학습자에게 독립 활동으로 보이는 정도와 현재 위험에 따라 더 깊게 감사한다.

| 깊이 | 대상 | 반드시 남길 판단 | 강제하지 않는 것 |
| --- | --- | --- | --- |
| 전수 지도 | release 차단 교안과 안정 ID가 있는 모든 독립 콘텐츠 | 기준일의 실제 manifest·ID, 목표·concept, 선수 관계·다음 실습, L0~L4, A/E/C/T 기여 또는 빈칸 | 파일마다 별도 경험 카드 작성, 감사만으로 PASS 처리 |
| 교안 묶음 감사 | 교안과 안정 ID 없는 본문 확인 문제 | 교안 목표의 A/E/C/T, 확인 문제의 L0/L1 관찰·오개념 역할, 다음 독립 실습으로 이어지는 사다리와 불필요한 반복 | 본문 질문마다 안정 ID·완전한 카드·Quest 하나씩 추가 |
| 항목별 판정 | 안정 ID가 있는 객관식·Code Quest·코딩테스트·Web Project | 각 항목의 커버리지 기여, 필요한 반복 또는 중복, 지원 단계와 `KEEP`·`REVISE`·`MERGE/RETIRE`·`NEEDS_DECISION`·`OUT_OF_SCOPE` 판정 | 모든 항목에 새 A·E·C·T를 하나씩 꾸며 넣기 |
| 심층 감사 | 전수 지도 대상 중 release 차단으로 지정된 알고리즘 과정 전체와 실제 풀이 흐름상 연결된 문제, Code Quest·코딩테스트·Web Project | 실제 접근 행동·조합·조건, 여섯 독립성 차원, starter·힌트·피드백 감소, T 확인 기회와 대표 오개념 | 선언된 `lessonId`만 보고 연결이 맞다고 추측, 기능 이름으로 L단계 결정 |

객관식은 독립 문항별 역할을 판정하되, 새 경험을 주장하지 않는 회상·오개념 확인은 L0/L1의 필요한 형성 반복일 수 있다. 반대로 직접 코드를 작성하는 문제는 독립 문제로 유지할 학습 행동을 문제별로 설명해야 한다. 알고리즘 감사는 메타데이터 연결만 보지 않고 기준 풀이의 실제 처리 흐름과 가장 가까운 교안·접근을 교차 확인한다.

소급 감사에서 기존 콘텐츠를 의미 있게 바꾸기로 결정하면 그 수정은 별도의 새 경험 또는 유지보수 작업으로 다시 시작한다. 새 경험 수정은 완전한 경험 카드가 필요하다. `MERGE/RETIRE`도 삭제 권한이 아니며 안정 ID·기존 진도·URL·리비전의 이관 또는 보존 방안을 설계하고 bam의 판단을 받아야 한다.

### 판정 의미

| 판정 | 의미 | 다음 단계 |
| --- | --- | --- |
| `KEEP` | 새 경험 또는 필요한 반복 역할과 현재 증거를 설명할 수 있음 | 커버리지 근거에 연결하고 유지 |
| `REVISE` | MVP 목표에 필요하지만 연결·지원·내용·평가 보강이 필요함 | 별도 작업 카드로 설계 단계부터 재시작 |
| `MERGE/RETIRE` | 의미상 중복으로 독립 항목을 유지할 근거가 부족함 | 즉시 삭제하지 않고 이관·진도 영향을 bam에게 제안 |
| `NEEDS_DECISION` | 항목의 교육적 독립성·처분에 사람 판단이나 추가 근거가 필요함 | bam 결정 또는 증거 작업으로 반환. 미해결이면 M6 전체 PASS 불가 |
| `OUT_OF_SCOPE` | 현재 release 차단 범위 밖임 | MVP 커버리지로 세지 않고 승격·의미 변경 때 재검토 |

항목 판정 `NEEDS_DECISION`은 파이프라인 단계 상태 `BLOCKED`와 다르다. 감사자가 미결정 항목을 정확히 발견·기록한 batch 자체는 검증을 통과할 수 있지만, 해당 항목을 해결하거나 release 범위에서 제외하기 전에는 전체 소급 감사와 M6를 PASS할 수 없다.

### MVP 차단과 이연 기준

다음은 M6 전에 해결하거나 bam이 명시적으로 범위에서 제외해야 한다.

- `DEC-MVP-01`에서 bam이 승인한 과정별 핵심 완료 행동인데 직접 구현하거나 지원을 줄여 적용할 기회가 전혀 없다.
- 실제 풀이 접근과 연결 교안·concept가 명백히 어긋난다.
- 학습자에게 독립 문제로 제공하면서 새 경험이나 필요한 반복 역할을 설명할 수 없다.
- starter·힌트·문구가 접근을 제공하는데도 L3·L4 또는 T라고 표현한다.
- 의미상 중복인데 별도 항목으로 유지할 교육적·시간적·지원 수준 근거가 없다.
- release 대상 ID가 감사 묶음이나 적용 가능한 검증 증거에 연결되지 않았다.

모든 concept에 L0~L4를 하나씩 만들거나 모든 교안에 Quest를 하나씩 붙이는 것은 완료 조건이 아니다. MVP 완료 행동을 막지 않는 추가 연습, 더 긴 시간 간격의 전이와 선택 과정 확장은 이유와 우선순위를 남겨 P2로 이연할 수 있고 MVP 커버리지로 미리 세지 않는다.

### 소급 감사 완료 증거

- 감사 기준일의 release manifest와 대상 ID 목록이 고정되고 모든 ID가 정확히 한 개 이상의 묶음에 연결된다.
- 묶음마다 A/E/C/T 기여·빈칸, L단계, 선수·다음 실습과 지원 수준이 기록된다.
- 안정 ID 콘텐츠의 항목별 판정과 심층 대상의 실제 접근·중복 비교가 있다.
- T는 확인 기회로만 기록하고 실제 학습자 관찰 전에는 전이 성과라고 표현하지 않는다.
- 실행 콘텐츠는 기준답안·대표오답·공개 평가를 실제 실행하고, 비실행 교안·객관식은 출처·정답 판정·교안 연결과 계약을 검증한다. 적용할 실행 계약이 없으면 `N/A`와 이유를 남긴다.
- [`development-workflow.md`](development-workflow.md)의 독립 `content_validator`, `test_engineer`, `project_integrator`가 설계 근거·적용 가능한 실행 또는 `N/A` 근거·ID 및 전체 정합성을 순서대로 PASS한다.
- release 차단 gap이 별도 작업에서 수정·재검증되거나 `DEC-MVP-01`과 release snapshot의 명시적 갱신으로 범위에서 제외되고, 비차단 이연 항목은 MVP 커버리지와 분리된다.

### 감사 batch와 전체 집계

M2의 한 묶음 시범과 이후 batch PASS를 전체 감사 PASS로 바꾸지 않는다.

- 전체 집계는 기준일, `DEC-MVP-01`의 핵심 완료 행동과 release 대상 ID를 가진 umbrella manifest를 사용한다.
- 각 batch는 고유 ID, umbrella의 담당 부분집합, 감사 깊이, 기준 콘텐츠 revision과 증거 위치를 선언한다.
- 여러 깊이에서 같은 ID를 볼 수 있지만 최종 항목 판정의 주 담당 batch는 하나만 둔다. 의도한 교차 검토는 참조로 연결하고 상충 판정을 남기지 않는다.
- 모든 batch의 담당 ID 합집합은 umbrella 대상과 정확히 같아야 하며 누락·범위 밖 ID와 소유자 없는 중복 판정은 0이어야 한다.
- batch PASS는 그 부분집합의 감사 품질만 뜻한다. 최종 `project_integrator`가 전체 합집합, 미해결 `NEEDS_DECISION`, 차단 gap과 이연 분리를 별도로 PASS해야 전체 감사가 완료된다.
- M2에서 형식을 시범 검증한 뒤 나머지 batch는 M3~M5와 병행할 수 있지만 M6 진입 전 전체 집계 PASS가 필요하다.

## 생성·검증 책임

`[확정 결정]` 콘텐츠 생성 역할은 자신의 결과를 최종 승인할 수 없다. 역할별 책임·독립성·금지 사항, 입력·통과·반환·증거와 bam의 판단 지점은 [`development-workflow.md`](development-workflow.md)가 유일한 정본이다.

## Algorithm Bridge에서 가져온 것과 바꾼 것

`[추론]` Algorithm Bridge는 학습 성과를 입증한 외부 연구 결과가 아니라, 이 설계에 참고한 로컬 프로젝트의 문서화된 운영 모델이다.

채택한 것은 접근 원자·순서 연결·무힌트 전이, L0~L4 지원 감소, 문제 수보다 학습 근거 우선, 다차원 중복 판정, 생성·콘텐츠 검증·실행 검증 분리와 증거 인계다.

BAM.dev에 맞게 조건 변화 `C`, 브라우저 공개 평가, 안정 ID·스키마, 접근성·모바일, 기능 브랜치·PR·CI와 `project_integrator`를 추가했다. Java·IntelliJ 파일 구조, 특정 책의 문제·별 등급·고정 슬롯 수, 주간 스터디 일정, 제공 Solution만 실행하는 테스트와 Git 작업을 하지 않는 규칙은 적용하지 않는다.
