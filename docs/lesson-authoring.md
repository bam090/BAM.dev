# 학습 교안 작성 계약

이 문서는 bam이 직접 작성하는 BAM.dev 교안의 집필 안내이자 제출 교안이 충족해야 할 단위, 필수 의미 구조, 예제·출처·연결 실습과 완료 조건의 정본이다. 이 계약은 에이전트에게 교안 생성 권한을 부여하지 않는다. 어떤 학습 경험을 추가할지는 [`learning-content-design.md`](learning-content-design.md), ID와 데이터 형식은 [`content-schema.md`](content-schema.md), 관리·검증 책임은 [`development-workflow.md`](development-workflow.md)가 담당한다.

`[확정 결정]` 교안은 정답을 읽게 하는 문서가 아니라, 학습자가 개념을 자신의 말로 설명하고 다음의 적절한 코드 실습을 직접 시작할 수 있게 만드는 설계된 학습 경로다. 분량, 코드 블록 수 또는 문제 수를 목표로 삼지 않는다. 새 경험의 필요성과 A/E/C/T 정본은 [`DEC-LEARNING-01`](roadmap.md#2026-08-29-확정-제품-결정) 및 [`learning-content-design.md`](learning-content-design.md)다.

## 저작과 관리 책임 경계

`[확정 결정]` [`DEC-LESSON-AUTHORSHIP-01`](roadmap.md#2026-09-02-확정-운영-결정)에 따라 학습 교안의 교육적 내용은 bam이 작성한다. 임시 `learning_document_manager`는 제출된 교안을 생성하거나, 설명·학습 목표·예제·오개념·힌트·정답을 대신 작성하거나, 자신의 판단으로 원문을 대체하지 않는다. 이 역할은 제품 목표·기능·UI·아키텍처의 정본을 작성하는 제품·설계 문서 담당과도 별개다.

`learning_document_manager`는 다음 관리 작업만 수행한다.

- bam이 제출한 원문을 보존하고 출처, 제출자, 확인 날짜와 관리 상태를 기록한다.
- 지정된 목적지와 파일 경로, 안정 ID, 필수 metadata, 교안·개념·실습 연결, Markdown 형식을 대조한다.
- 누락·충돌·모호한 항목은 근거와 위치를 적어 bam에게 반환하고 내용을 대신 채우지 않는다.
- 관리 점검을 통과한 자료와 점검 증거를 작성자와 분리된 `content_validator`, `test_engineer`, `project_integrator`에게 순서대로 인계한다.

교육적 의미를 바꾸는 보충·재작성은 bam이 명시적으로 승인한 범위에서 지정 작성자가 수행하며, 문서 관리 수정과 역할을 분리한다. 이미 승인한 생성·재구성과 그 완료에 필요한 수정은 다시 승인받지 않고 진행한다. 승인 범위 밖 보충이나 결과를 크게 바꾸는 교육적 미결정만 bam에게 반환한다. 관리 점검 통과는 내용 검증 PASS나 제품 통합 완료를 뜻하지 않는다. 상태와 인계 증거의 상세 정본은 [`development-workflow.md`](development-workflow.md)다.

## 작성 전 교안 보충 카드

bam은 새 교안을 만들거나 기존 교안의 학습 목표를 의미 있게 바꾸기 전에 학습 경험 카드를 먼저 만들고, 교안에만 필요한 값을 다음 보충 카드에 기록한다. A/E/C/T, MVP 필요성, 자기 언어 설명과 대표 오개념은 경험 카드 한 곳에만 쓰고 이 카드에서 복사하지 않는다. 학습 목표가 바뀌지 않는 오탈자·출처·표현 수정은 유지보수 결함과 영향 범위 기록으로 두 카드를 대신할 수 있다. `learning_document_manager`는 두 카드와 제출 교안의 존재·연결·형식을 확인하지만 빠진 내용을 작성하지 않는다.

```text
작업 ID와 경험 카드 ID 또는 유지보수 결함 ID:
courseId / languageId / lessonId / order:
교안 제목과 한 문장 핵심 질문:
선수 교안·conceptId:
새로 선언할 conceptId:
curriculum objectives와 관찰 가능한 완료 행동:
검증할 최소 예제와 실행 환경:
표준 의미 구조를 채우는 내용 계획:
연결할 Code Quest·코딩테스트·웹과제 또는 주제 묶음의 연결 계획:
공식·권위 출처와 확인 날짜:
접근성·모바일·오프라인 영향:
bam의 판단이 필요한 항목:
```

`lessonId`와 `conceptId`를 먼저 정하고 제목이나 파일 경로를 나중에 맞추지 않는다. 연결된 경험 카드가 MVP 필요성과 기존 콘텐츠와의 차이를, 보충 카드가 관찰 가능한 완료 행동과 교안 구성을 설명하지 못하면 집필을 시작하지 않고 `BLOCKED`로 둔다.

## 한 교안의 범위

한 교안은 다음 조건을 만족하는 가장 작은 의미 단위다.

- 하나의 핵심 질문에 답한다.
- 서로 연결되는 소수의 개념을 한 흐름으로 설명한다.
- 학습자가 최소 한 가지 선택 단서와 적용 경계를 말할 수 있다.
- 다음 Code Quest, 코딩테스트 또는 주제 묶음의 가장 가까운 코드 실습을 정답 없이 시작할 수 있다.

여러 개념이 같은 입력·상태 흐름을 공유하면 함께 다룰 수 있다. 반대로 제목만 하나일 뿐 서로 다른 선수 지식과 판단을 요구하면 교안을 나눈다.

### 승인된 HTML 파생 교안의 작은 단위

`[확정 결정]` [`DEC-HTML-CONCEPT-LESSONS-01`](roadmap.md#2026-09-13-확정-제품-결정)은 실제 밤위키 HTML 교안을 필요한 개념별로 재편하고 목표·요약·핵심 질문·직접답을 함께 맞추라는 bam의 명시적 요청이다. 이번 범위에서만 원문 기반의 교육 내용 재구성을 허용하며 전역 저작 권한을 에이전트에 넘기지 않는다. 기존 제품 교안과 밤위키 원문은 보존하고 새 파생 파일의 실제 계보·변경 구간을 남긴다.

짧은 문서가 목적이므로 아래 11개 표준 제목을 채우기 위해 분량을 늘리지 않는다. 이번 HTML 파생 문서는 학습 후 능력·한줄 요약, 필요한 선수와 관찰, 개념·작은 예제·실수와 적용 경계, 자신의 말로 답할 핵심 질문과 접힌 직접답, 다음 실습과 출처의 **의미**를 유지하면서 가까운 절을 합칠 수 있다. 요소/속성처럼 함께 이해하는 관계와 종합 점검을 문서 수 때문에 다시 나누지 않는다. 일반 신규 교안의 표준 계약은 유지한다.

새 ID별 원문 구간·질문·답·목표·요약·개념·실습 매핑을 먼저 검토한다. 경험 카드에서 파일 분할을 새 접근으로 포장하지 않고 실제 추가되는 판단·조건·지원 변화와 기존 경험 재사용을 구분한다. 화면·ID·진도·파생 출처 형식과 완료 검증은 [HTML 전환 계약](designs/lesson-review.md#html-개념-문서-전환), 세부 카드와 독립 판정은 [작업 카드](work-items/2026-09-13-html-concept-lessons.md)를 따른다.

### 승인된 CSS 파생 교안의 작은 단위

`[확정 결정]` [`DEC-CSS-CONCEPT-LESSONS-01`](roadmap.md#2026-09-13-확정-제품-결정)은 위 HTML의 작은 파생 교안 계약을 실제 밤위키 CSS 승인 원문에 이어 적용하는 명시적 요청이다. 이번 CSS 범위에서 원문에 근거한 단위별 목표·요약·핵심 질문·직접답과 선수·실습 연결을 함께 재구성하며 전역 저작 권한은 바꾸지 않는다. 비교해야 선택할 수 있는 속성·배치 관계와 종합 진단은 함께 두고, 표준 제목 수를 채우기 위한 분량을 추가하지 않는다.

파일 분할과 기존 내용 재사용을 새 경험으로 세지 않는다. 기존 제품 교안과 원문을 비교한 실제 조건·진단 연결·자기 설명 지원의 차이는 [CSS 경험 카드와 단위 매핑](work-items/2026-09-13-css-concept-lessons.md)에 한 번만 기록한다. 학습 문서 관리자는 작성자가 인계한 단위별 metadata·출처·ID·링크를 조립하고 교육 내용 보완은 작성자에게 반환한다. 밤위키 원문·기존 제품 CSS 본문·문항·실습은 보존하고 파생본만 수정한다. 단, Flex 문항의 글쓰기 조건 한 줄 보완은 [CSS 전환 계약](designs/lesson-review.md#css-개념-문서-전환)의 예외를 따른다.

### 승인된 JavaScript·Java 파생 교안의 작은 단위

`[확정 결정]` [`DEC-JS-JAVA-CONCEPT-REVIEW-01`](roadmap.md#2026-09-14-확정-제품-결정)은 승인된 공개 밤위키 JS·Java 원문에 앞선 작은 파생 교안 계약을 적용하고 객관식을 추가하는 명시적 요청이다. 지정 작성자는 이번 범위의 목표·요약·핵심 질문·직접답·선수·예제·오개념·실습 연결을 원문에 근거해 재구성한다. 필요한 비교쌍과 종합 흐름은 함께 유지하며 표준 제목·문서·문항 개수를 채우기 위해 내용을 늘리지 않는다. 문항 추가·보완은 사람이 대상·행동·판단 결과를 바로 파악할 수 있는 [문항 작성 기준](designs/lesson-review.md#객관식-문항-작성과-검토-기준)을 따른다.

새 단위의 직접답은 해당 질문에 바로 답하고 기존 접힘·수동 완료 표시를 재사용한다. 기존 JS runtime은 이미 독립된 작은 범위여서 본문·ID·활성을 보존했고 새 위키 파생본으로 복제하지 않았다. `면접 답변 예시` 형식과 `answerHeading` 없는 기존 metadata도 이번 범위에서 유지했으므로 모든 기존 교안의 자기 확인 UI 완료를 뜻하지 않는다. 기존 다른 JS·Java 본문과 기존 문항 객체도 보존한다. 이번 파생 교안·문항은 현재 JSON과 본문에 반영됐다. 목표·요약·질문·직접답의 실제 문구는 metadata와 본문이 정본이며, 단위별 원문 SHA·범위·제품 보완·새 문항 A/E/C와 재사용 매핑은 [작업 카드](work-items/2026-09-14-js-java-concepts-and-review.md#단위와-문항-연결)에 한 번만 기록한다. 독립 내용·문서·데스크톱 실행과 수정 후 최종 통합·빌드·보존 검사 PASS 및 한계도 그 카드에서 구분한다. 작성자·관리자·세 독립 검증 역할은 유지하며 명시적으로 승인된 재구성을 다시 묻는 선행 gate를 만들지 않는다.

### 승인된 Spring·Spring Boot 새 교안의 작은 단위

`[확정 결정]` [`DEC-CSS-SPRING-FOUNDATIONS-01`](roadmap.md#2026-09-14-확정-제품-결정)은 Spring 핵심과 Spring Boot를 함께 다루는 정적 학습문서·객관식의 새 작성을 승인한다. 지정 작성자는 이번 범위에서 공식 자료를 확인하여 목표·요약·질문·직접답·선수·예제·오개념·관련 문제를 작성한다. 밤위키 원문을 찾지 못한 Spring 자료는 원문 반입으로 표시하지 않으며 기존 `bam-authored` 분류와 본문 출처에 승인된 에이전트 새 저작의 성격을 남긴다.

앞선 작은 개념 문서와 같은 읽기 경험을 적용하되 **새 저작**이라는 출처 차이를 보존한다. 한 핵심 질문에 답하는 분량으로 작성하고 필수 의미를 유지하면서 가까운 절을 합칠 수 있다. 아래 11개 표준 제목이나 문서 수를 맞추기 위해 내용을 늘리지 않는다. `학습 목표`·선수·관찰·개념과 예제·실수와 적용 경계·자기 설명·`핵심 질문 답`·실제 관련 문제·공식 출처는 확인 가능해야 한다. 실행 환경이 없는 코드를 실행 PASS로 표현하거나 존재하지 않는 과제로 연결하지 않는다.

단위·문항별 새 A/E/C 근거, 기존 Java 지식 재사용, 지원 수준과 대표 오개념은 작성자 계획을 [작업 카드](work-items/2026-09-14-css-quiz-spring-foundations.md)에 연결한다. 관리자는 metadata·ID·출처·링크와 실제 본문 발췌를 조립하고 교육 보완은 작성자에게 반환한다. 전역 저작 권한과 독립 검증 역할은 유지한다.

명시적 `answerHeading`이 있는 새 저작은 기존 확인 문제·면접 답변 예시 형식 대신 학습 목표와 실제 유일한 직접답 절을 검사한다. 필수 ID·목표·본문·출처·개념 연결 검사는 유지하고, `answerHeading`이 없는 기존 교안에는 종전 확인 문제·답변 예시 계약을 적용한다. 출처 종류를 바꾸거나 위키 반입 필드를 만들어 검사 분기를 피하지 않는다.

후속 [`DEC-SPRING-SECURITY-JPA-01`](roadmap.md#2026-09-14-확정-제품-결정)의 Security·JPA 새 교안도 같은 작은 단위·출처·직접답 계약을 적용한다. 작성자 경험·교안 보충 계획과 독립 검증은 [해당 작업 카드](work-items/2026-09-14-spring-security-jpa.md)에 기록한다.

## 메타데이터와 Markdown의 정본

`[현재 사실]` 현재 `content/curriculum.json`의 `objectives`와 각 Markdown의 `학습 목표`가 같은 내용을 두 곳에 보관할 수 있다. 화면과 검증을 바꾸기 전에 한쪽을 삭제하면 현재 학습 흐름이 달라질 수 있다.

`[확정 결정]` 목표 상태에서는 다음처럼 분리한다.

| 정보 | 정본 |
| --- | --- |
| ID, 과정, 언어, 순서, 제목, 요약, 예상 시간, 핵심 질문, 목표, concept ID | `content/curriculum.json` |
| 개념 설명, 관찰, 예제, 흐름, 반례, 연습, 회고와 출처 맥락 | 교안 Markdown |
| 새 경험과 반복·중복 판정 | 학습 경험 카드와 커버리지 등록부 |

`[확정 결정]` 전환 기간에는 메타데이터가 화면에 직접 표시되도록 구현되기 전까지 새·변경 교안이 Markdown의 정확한 `## 학습 목표` 절을 유지하고 `content_validator`가 `curriculum.json`의 `objectives`와 의미 일치를 확인한다. 목표 상태에서는 renderer가 metadata 목표를 같은 위치에 표시하는 구현과 migration이 검증된 뒤 Markdown의 중복 목표 본문을 제거한다. 그 전에는 목표 정본 분리를 완료 사실로 표현하지 않는다.

## 교안 제목

`[확정 결정]` 제목만 보고 실제 배울 핵심 개념을 알아볼 수 있게 쓴다. 필요한 개념명이나 대표 API를 드러내고, 익숙하지 않은 말에는 짧고 쉬운 설명을 붙인다. 이미 내용이 분명한 제목은 유지하며 모든 제목을 같은 형식으로 맞추거나 본문의 개념을 전부 나열하지 않는다.

제목 표현만 다듬을 때는 학습 목표와 본문을 유지하고, `lessonId`·`conceptId`·파일 경로·slug·route·학습 진도를 바꾸지 않는다. 이번 승인 범위와 구·신 제목은 [학습문서 제목 정리](work-items/2026-09-14-lesson-title-clarity.md)에 기록한다.

## 필수 의미 구조

일반 신규 교안과 학습 목표를 바꾸는 교안은 탐색·검증을 위해 아래 표준 `##` 제목을 순서대로 사용한다. 명시적으로 승인된 작은 파생 교안과 이번 Spring 새 교안은 해당 [단위 계약](#한-교안의-범위)에 따라 필수 의미를 보존하면서 가까운 절을 합칠 수 있다. [`DEC-CONTENT-01`](roadmap.md#2026-08-30-확정-제품-결정)의 소급 감사만으로 기존 교안을 일괄 개명하지 않는다. 감사에서 학습 행동을 바꾸는 `REVISE`가 확정된 교안은 별도 작업에서 해당 계약을 적용한다. 언어 특성에 맞게 절의 관찰 대상을 바꾼다.

1. **`## 왜 배우는가`** — 실제 코드나 화면에서 생기는 문제와 핵심 질문을 먼저 제시한다.
2. **`## 현재 위치와 선수 개념`** — 과정·주제·앞 교안과의 연결을 알려 준다.
3. **`## 학습 목표`** — 전환 기간에는 metadata 목표와 같은 의미의 관찰 가능한 행동을 표시한다. 목표 상태에서는 renderer가 metadata에서 이 절을 만든다.
4. **`## 먼저 관찰하기`** — 작은 입력, 화면 또는 코드에서 학습자가 먼저 찾아야 할 차이를 묻는다.
5. **`## 핵심 개념`** — 쉬운 말, 정확한 용어, 선택 단서와 비적용 조건을 함께 설명한다.
6. **`## 실행 흐름`** — `입력·이벤트 → 저장하거나 바꾸는 상태 → 판단 → 결과`를 단계별로 추적한다.
7. **`## 직접 따라 하기`** — 정답 전체가 아닌 한두 행동을 실제 작성 단위로 구현한다.
8. **`## 자주 하는 실수`** — 증상, 원인, 다시 관찰할 지점을 연결한다.
9. **`## 자신의 말로 설명하기`** — 핵심 질문에 학습자가 말이나 글로 답하게 한다.
10. **`## 다음 실습`** — Code Quest, 코딩테스트와 웹과제 중 실제 연결 대상을 안정 ID로 안내한다.
11. **`## 출처`** — 공식·권위 자료, 확인 날짜와 프로젝트가 새로 작성한 설명의 경계를 남긴다.

섹션은 내용 없는 형식 채우기가 되어서는 안 된다. 예를 들어 선언형 HTML의 `실행 흐름`은 DOM 의미 관계와 사용자·브라우저가 정보를 해석하는 흐름을, CSS는 cascade 입력에서 계산 스타일과 화면 결과로 이어지는 흐름을 설명한다.

## 설명과 예제 규칙

- 정확한 용어를 먼저 쉬운 말로 설명한 뒤 코드 용어와 연결한다.
- API·태그·자료구조 이름만 나열하지 않고 어떤 단서 때문에 선택하는지 설명한다.
- 좋은 경우뿐 아니라 사용하면 안 되는 조건과 대표 반례를 하나 이상 보여 준다.
- 코드 예제는 교안의 개념만 드러내는 최소 크기로 만들고, 연결 Quest의 전체 답안을 재현하지 않는다.
- 예제 결과는 실제로 실행하거나 관찰한 환경과 범위를 기록한다. 실행하지 않은 결과를 지어내지 않는다.
- HTML은 의미 구조·키보드·레이블을, CSS는 최종 캐스케이드·좁은 화면·초점 표시를, JavaScript는 입력·상태·부작용·오류 경계를 함께 다룬다.
- 알고리즘은 자료구조 이름보다 단서, 보존할 정보, 반복 불변식과 결과 생성 순서를 먼저 설명한다.
- Java는 현재 실행 가능한 범위를 과장하지 않고, 컴파일·테스트를 실제 수행하지 않았다면 예시라고만 표시한다. Java 교안의 소스·표준 API는 [`DEC-JAVA-VERSION-02`](roadmap.md#2026-09-04-확정-제품-결정)의 정식 Java 25 기준을 따르고 preview 기능을 사용하지 않는다.
- Spring Boot 교안은 [`DEC-SPRING-BOOT-01`](roadmap.md#2026-09-04-확정-제품-결정)에 따라 정적 콘텐츠로 작성한다. 실제 Spring Boot 실행을 앱 본체·교안·Java 코딩테스트 runner에 포함하지 않고, 승인된 외부 웹과제와 연결한다.

## 힌트와 정답 경계

교안은 문제의 정답을 먼저 노출하지 않는다.

1. 관찰 질문으로 시작한다.
2. 필요한 개념과 선택 기준을 설명한다.
3. 작은 부분 구현을 함께 해 본다.
4. 연결 Quest에서는 `개념 → 관찰 → 구현` 순서로 요청할 때만 힌트를 공개한다.
5. 전이 확인용 코딩테스트·Quest·웹과제는 첫 시도 전에 접근 이름과 전체 순서를 제공하지 않는다.

면접 답변, 완성 코드, 전체 풀이가 필요하면 학습자가 먼저 자신의 설명이나 시도를 남긴 뒤 비교할 수 있는 별도 구역으로 둔다. 현재 화면이 특정 Markdown 제목 문자열에 의존한다면 해당 결합을 구현 사실로 기록하고 구조화 필드로 옮기기 전까지 제목을 임의 변경하지 않는다.

## 교안과 실습의 연결

`[확정 결정]` 목표 학습 흐름은 다음과 같다.

```text
교안에서 관찰·설명
→ Code Quest에서 가까운 개념·조건을 직접 작성
→ 별도 코딩테스트에서 단서를 골라 접근을 조합하고 지원을 줄임
→ 웹과제에서 여러 파일·요구사항을 실제 작업 폴더에 적용
```

이 흐름은 기능 이름이 난이도 단계를 자동 결정한다는 뜻이 아니다. Code Quest에도 지원을 줄인 경험이 있을 수 있고, 코딩테스트도 필요한 선수 학습과 공개 피드백을 제공한다. 모든 교안에 네 단계를 억지로 하나씩 만들지 않고 모든 개별 교안에 Quest 하나를 강제하지도 않는다. 여러 교안이 한 주제의 Code Quest, 코딩테스트나 웹과제로 모일 수 있으며, `다음 실습`은 실제로 연결된 가장 가까운 실습과 그 범위를 설명한다. 연결하지 않는 단계는 선수 지식·과제 크기·실행 경계를 이유로 설명한다.

## 완료 조건

교안은 다음을 모두 통과해야 한다.

- 경험 카드·교안 보충 카드와 Markdown의 목표·범위가 일치한다.
- 전환 기간에는 정확한 `## 학습 목표` 절과 `curriculum.json`의 `objectives`가 의미상 일치한다.
- 안정 ID, 순서, 파일 경로와 concept 연결이 유효하다.
- 핵심 질문, 선택 단서, 적용·비적용 조건과 실행 흐름이 확인된다.
- 승인 범위의 필수 예제·주장 결과를 실제 환경에서 검증했고 미실행 범위를 적었다. 적용할 실행 계약이 없는 검사는 N/A 이유를 남기며, 필수 검사의 미실행이나 제품 UI 검증을 예제 실행 완료로 표현하지 않는다.
- 대표 오개념이 정답 문구가 아니라 원인과 재관찰 지점을 설명한다.
- 연결 실습이 같은 전체 답안을 복사하지 않고 다음 지원 단계로 이어진다.
- 공식·권위 출처와 확인 날짜가 있으며 원문 복제와 프로젝트 설명을 구분한다.
- 공식 자료는 유지하되 문서당 링크를 최대 3개로 제한한다. 핵심 주제를 직접 뒷받침하는 기존 공식 출처를 우선한다.
- 키보드, 좁은 화면과 상태 안내를 방해하는 표현·구조가 없다.
- 작성자와 분리된 `content_validator`, `test_engineer`, `project_integrator`가 정해진 순서로 판정한다.

기존 교안 전체가 이 계약을 이미 통과했다고 간주하지 않는다. 소급 감사의 단위·깊이·판정은 [`learning-content-design.md`의 기존 콘텐츠 소급 감사](learning-content-design.md#기존-콘텐츠-소급-감사)를 따르며, 교안 묶음 지도만으로 새·변경 교안의 위 완료 조건을 통과했다고 표현하지 않는다.

## 문체와 구성 규칙

`[확정 결정]` 2026-09-26 bam이 파일럿 교안(`content/lessons/javascript/pilot-async-await.md`, `content/lessons/algorithm/pilot-tree.md`, `content/lessons/algorithm/pilot-tree-java.md`)을 보고 승인한 학습자 본문의 문체다. 새로 쓰거나 다시 쓰는 교안의 학습자용 본문에 적용한다. 위 [필수 의미 구조](#필수-의미-구조)의 표준 제목 목록과 이 절의 구성 규칙은 교안 형식 개편 때 하나로 맞추며 그 전까지 기존 교안을 이 절만으로 일괄 수정하지 않는다.

### 쉼표

쉼표는 꼭 필요할 때만 쓴다. 쉼표가 없으면 뜻이 헷갈리거나 문장을 잘못 끊어 읽게 되는 곳이 꼭 필요한 경우다. 특히 `~고,` `~며,` `~지만,` `~므로,` `~면,`처럼 연결어미마다 쉼표를 붙이면 사람이 쓴 글보다 기계가 쓴 글처럼 읽힌다. 문장이 길어서 쉼표가 필요해 보이면 먼저 문장을 둘로 나눌 수 있는지 본다. 짧은 항목을 나열할 때는 가운뎃점(`·`)을 쓸 수 있다.

| 쓰지 않는다 | 이렇게 쓴다 |
| --- | --- |
| await는 결과가 올 때까지 그 async 함수만 잠시 멈추고, 나중에 도착하는 실패도 await하는 자리에서 받습니다. | await는 결과가 올 때까지 그 async 함수만 잠시 멈추고 나중에 도착하는 실패도 await하는 자리에서 받습니다. |
| 회원 목록, 게시글, 검색 결과처럼 | 회원 목록·게시글·검색 결과처럼 |

코드 블록·출력 결과·표의 값 안에 있는 쉼표는 이 규칙의 대상이 아니다.

### 줄바꿈

한 문장이 끝나면 줄을 바꾼다. 한 줄에 두 문장을 이어 쓰지 않는다. 읽는 사람의 시선이 늘 줄의 왼쪽 끝에서 문장을 시작하게 하려는 것이다. 문단은 빈 줄로 나누고 한 문단은 보통 1~4문장으로 둔다. 앱 렌더러는 문단 안의 줄바꿈을 그대로 화면에 표시한다.

쓰지 않는다:

```text
await는 프로그램 전체가 아니라 그 async 함수 하나만 멈춥니다. 결과와 실패는 둘 다 나중에 도착하므로 기다리는 자리에서 받습니다.
```

이렇게 쓴다:

```text
await는 프로그램 전체가 아니라 그 async 함수 하나만 멈춥니다.
결과와 실패는 둘 다 나중에 도착하므로 기다리는 자리에서 받습니다.
```

### 말투와 문장

- 학습자용 본문은 `~합니다`로 쓴다. 규칙 문서·운영 문서의 `~한다`체를 교안에 섞지 않는다.
- 작성자에게 하는 말을 본문에 넣지 않는다. `~라고 설명하지 않는다` `~라고 단정하지 않는다` 같은 검수용 부정문, 승인·검증 상태, 역할 분담 설명은 교안에 쓰지 않는다.
- 본문은 무엇인지를 긍정문으로 설명한다. 흔한 실수는 따로 긴 절을 두지 않고 본문의 한 단계로 한 번만 보여 준다.
- 용어는 현상을 먼저 보여 준 뒤 이름을 붙인다. 아직 설명하지 않은 용어로 다음 개념을 설명하지 않는다.
- 그림·코드에 없는 것을 말하지 않는다. 글자로 그린 트리에서 `동그라미 하나하나가 노드`라고 쓰지 않는다.

### 구성

- 교안은 가볍게 읽히게 쓴다. 개념을 익히는 데 오래 머물게 하지 않고 체득은 객관식·Code Quest·코딩테스트·웹과제에 맡긴다.
- 개념은 `무엇인지 → 종류 → 사용법 → 활용` 순서가 보이게 설명한다.
- `○○란` 절은 첫 문장에서 그 개념을 한 문장으로 정의한다. 이어서 왜 필요한지와 제목·정의에 나온 용어(예: 비동기·Promise)의 뜻을 설명한 뒤 `예를 들어`로 문서 전체에서 쓸 예시 장면을 연다. 개념과 연결이 드러나지 않는 장면으로 절을 시작하지 않는다.
- 소제목은 명사형으로 통일한다. 예: `트리란` · `트리의 용어` · `트리의 종류` · `Java로 트리 구현` · `트리 순회` · `트리 순회의 활용` · `async·await 사용법`. `어디에 쓰나요` `사용하는 방법` 같은 질문형·서술형 제목은 쓰지 않는다. 구현 절은 언어를 드러낸다.
- 예시 하나를 처음부터 끝까지 이어서 쓴다. 절마다 새 소재를 만들지 않는다.
- 코드는 `예상해 보기 → 출력 → 이유` 순서로 보여 준다. 출력은 실제로 실행해 확인한 것만 쓰고 실행 환경이 결과를 바꾸면(예: 브라우저와 Node의 콘솔 표시) 그 차이를 한 줄로 알린다.
- 그림을 보면서 읽어야 하는 표는 그림 바로 아래에 둔다. 앞에서 보여 준 그림이 멀어졌다면 그림을 한 번 더 넣는다.
- 본문 흐름에 꼭 필요하지 않은 보충 설명은 접히는 토글로 넣는다. 문법은 Obsidian 접히는 콜아웃과 같다.

```text
> [!question]- 사이클이란?
> 사이클은 간선을 따라가다가 출발한 노드로 다시 돌아오는 길입니다.
```

`-`는 접힌 상태로 시작하고 `+`는 펼친 상태로 시작한다.
- 예상 학습·풀이 시간(`약 N분`)을 본문이나 화면에 표시하지 않는다. 학습 속도는 사람마다 달라 학습자에게 부담을 줄 수 있다.

### 문서 나누기와 합치기

`[확정 결정]` 2026-09-30 bam이 CSS 위치 지정 파일럿을 승인하며 정한 기준이다.

- 한 문서는 학습자의 한 질문에 답한다. 같은 속성·같은 질문을 다루고 예시 하나로 끝까지 설명할 수 있으면 한 문서로 합친다. 질문이 다르거나 새 예시가 필요하면 나눈다. 예: `relative`·`absolute`·`fixed`·`sticky`·`z-index`는 "요소를 어디에 놓고 겹치면 무엇이 앞에 보이는가"라는 한 질문이라 한 문서이고 Flexbox와 Grid는 질문과 예시가 달라 따로 둔다.
- 합친 이유는 `## 학습 목표` 목록에서 드러낸다. 목표는 3~4개 목록으로 쓰고 본문의 주제마다 하나씩 둔다.
- 화면에 보이지 않는 내용은 쓰지 않는다. 학습 목표가 있는 교안에는 `## 한줄 요약` 절을 두지 않는다. 메타데이터 `summary`는 목록 카드와 요약 창에만 쓴다.
- 문서 첫머리의 학습 목표는 무엇을 얻을지 보여 주고 문서 끝의 `## 핵심 질문 답`은 이해했는지 확인한다. 그 앞의 `## 정리`는 요점 3줄 목록으로 둔다.
- 여러 주제를 합친 문서는 주제가 바뀌는 곳에 구분선 `---`을 한 줄 둔다. 구분선은 절 구분선보다 굵게 표시된다. 문서 끝의 정리·이어서 연습하기·공식 자료·핵심 질문 답 앞에는 두지 않는다.
- 합칠 때 받는 문서가 기존 `id`·`slug`·완료 기록을 이어받고 합쳐진 문서는 `archivedFromCatalog: true`로 목록에서만 숨긴다. 합쳐진 문서의 객관식은 ID·소유·풀이 기록을 그대로 두고 개념 발췌(`review-concepts.json`)의 `documentLessonId`를 받는 문서로 옮긴다. 문서 끝의 문제 버튼은 개념마다 하나씩 둔다.

### 읽는 흐름

- 절과 절 사이에 다음 절로 넘어가는 문장을 둔다. 예: `이제 예제 트리를 Java 코드로 옮겨 보겠습니다.` · `그렇다면 실제로는 어떤 순회를 골라야 할까요?`
- 문장끼리는 `그래서` · `반면` · `그런데` · `~기 때문입니다`처럼 이유와 대비를 드러내는 말로 잇는다. 짧은 단정문만 연달아 쓰지 않는다.
- 이어지는 문서는 첫 문장의 정의 바로 뒤에서 앞 문서에서 한 일을 한 문장으로 불러온다. 예: `앞 문서에서는 Node를 직접 만들어 트리를 연결했습니다.`

### 비교와 시각화

- 방법이 두 가지 이상이면 같은 예시로 나란히 비교한다. 비교표에는 방향·쓰는 도구·잘 맞는 문제처럼 선택에 필요한 기준을 둔다. 예: 트리 순회의 DFS·BFS 비교.
- 구조·순서·상태 변화를 설명하는 개념은 그림을 먼저 보여 준 뒤 글로 풀어 준다. 트리·그래프·스택·큐처럼 모양이 있는 개념은 핵심 절마다 그림 하나를 기준으로 삼는다.
- 반복마다 상태가 바뀌는 과정은 단계별 표로 보여 준다. 예: 레벨 순회에서 노드를 꺼낼 때마다 바뀌는 큐.
- 교안 그림은 `content/assets/<과정>/` 아래 PNG로 둔다. 흰 배경 카드로 만들어 밝은·어두운 테마에서 같은 모양으로 보이게 하고 그림이 전하는 내용을 대체 텍스트로 쓴다.
- 그림이 실제 동작을 보여 준다면 그 동작을 직접 확인한 뒤 그린다. 예: `TreeMap`에 14·9·11을 넣은 뒤 실제 루트가 11인지 확인.
