# 학습 문서와 객관식 복습

## 범위와 현재 기준

`[확정 결정]` [2026-09-12 독립 학습 결정](../roadmap.md#2026-09-12-확정-제품-결정)에 따라 이 정본은 **홈의 학습문서·객관식 독립 선택과 키워드→문제→해설→개념→문서 왕복·자율 재도전**의 제품 경계를 다룬다. 밤위키는 검증할 제작 재료이며 앱 사용의 필수 환경이 아니다. 과정의 첫 목표·확장 순서와 남은 선택은 [로드맵](../roadmap.md#학습문서객관식의-우선-완성-순서), 필드 계약은 [콘텐츠 스키마](../content-schema.md#독립-학습문서객관식-목표-계약)가 담당한다.

`[현재 사실]` 앞선 [설계 작업](../work-items/2026-09-12-independent-review-design.md)은 설계만 수행하고 독립 문서·통합 검증을 마쳤다. `[확정 결정]` 이후 bam의 구현 시작 요청에 따라 [R1 첫 사용 작업](../work-items/2026-09-12-independent-review-first-use.md)의 제한된 범위를 구현한다. R1 당시 요청만으로 후속 R2/R3·대량 콘텐츠·설치·배포를 승인한 것으로 보지 않는다. 이후 2026-09-14 후속 요청에 따라 R2의 [보기·채점 첫 확장](#보기-방식과-채점-방식의-첫-확장)을 별도 제한 범위로 진행한다. 2026-09-09 작업에서 “설계만 수행하던 제한 해제”라고 기록한 것은 그 작업의 구현 이력이다. R1은 새 명시적 요청으로 시작하며 그 과거 이력을 구현 승인으로 재사용하지 않는다. 밤위키 폴더·템플릿·수집·예약 설정·새 의존성·배포는 변경하지 않는다. 설계의 날짜별 조사·검증 증거는 [설계 작업 카드](../work-items/2026-09-12-independent-review-design.md)에 둔다.

## R1 첫 사용 구현 계약

`[확정 결정]` 설계 검토 뒤 bam이 구현 시작을 요청했다. [첫 사용 작업 카드](../work-items/2026-09-12-independent-review-first-use.md)의 범위는 홈·독립 목록·한 문제씩 개별 채점·관련 개념·같은 탭 문서 왕복과 중단 복구다. 아래 전체 목표 가운데 이 범위만 먼저 적용하고 미구현 후속 기능을 완료로 표시하지 않는다.

- `#/`는 소개와 두 큰 서비스 선택, `#/learn`은 문서 독립 목록, `#/review`는 문제 독립 목록이다. 기존 깊은 URL과 다른 제품의 콘텐츠·진도는 보존한다.
- 과목·키워드 검색과 현재 위치·저장 상태를 간단히 표시한다. 필수 설정 단계 없이 한 문제씩·개별 채점으로 시작한다. R1 당시의 dark 유지 범위는 최신 [시안 채택 계약](#채택-시안의-홈목록읽기-계약)으로 대체한다.
- 첫 완결 검증 재료는 기존 JS 반입 문서 3개·13문항이다. 기능 연결 전에 필요한 기존 개념·원문 그대로의 승인 발췌·문서 참조를 접수·검증한다. 학습 설명이나 문제를 새로 쓰지 않는다.
- 관련 개념은 승인 발췌의 오버레이로 열고 ‘학습문서에서 자세히 보기’는 같은 탭으로 이동한다. 유효한 문제 유입 토큰이 있는 문서에서만 문제 복귀를 제공한다. 직접 문서 진입에는 제공하지 않는다.
- 진행 중 선택·채점·해설·현재 문항·스크롤·초점은 저장소 뒤에서 유지하며 동일 origin의 새로고침·재실행·문서 왕복을 검증한다. 기존 완료 시도와 다른 제품 저장 데이터를 초기화하지 않는다.
- 전체 보기·전체 채점·모름·헷갈림·생애 최초 기록·복합문항 재분류·대량 반입은 후속 R2/R3에 남긴다. 새 React·Java runner·의존성·설치·배포·Git 작업을 포함하지 않는다.

### R1 route와 복구 경계

- 홈 `#/`, 독립 목록 `#/learn`·`#/review`를 추가하고 기존 교안·복습 깊은 URL은 보존한다. 기존 복습 route에 `?concept=<기존 conceptId>`를 붙여 키워드 범위를 선택한다. 해당 단원·언어와 실제 개념 연결이 맞아야 한다.
- 기존 문서 route의 `?review=<session-token>&section=<heading>`은 문제에서 생성한 문서 왕복 문맥이다. 로컬 활성 세션의 `returnContext`가 토큰·대상 문서 ID와 일치할 때만 문제 복귀를 표시한다. query가 있다는 이유만으로 복귀를 허용하지 않는다. 직접 문서 진입에는 기존 보관 세션이 있어도 복귀가 없다.
- `section`은 허용된 문서의 실제 heading으로 해석한다. 문서 이동 후 해당 절을 찾고, 문제 복귀 시 저장한 선택·채점·해설·문항·스크롤·초점을 회복한다. 같은 탭 문서 새로고침에도 유효 복귀 문맥은 유지한다.
- `bam.dev.review-session.v1`은 별도 저장소 뒤에 활성 세션 하나를 둔다. 기존 progress 키와 완료 기록은 보존하며 `recordAttempted`도 복구해 결과 시도를 중복 저장하지 않는다. 콘텐츠 서명이 달라졌으면 예전 채점 상태를 현재 콘텐츠에 조용히 적용하지 않는다.

필드·원문 발췌의 정확한 계약은 [R1 콘텐츠·진행 세션 계약](../content-schema.md#r1-개념-발췌와-진행-세션-계약)과 [발췌 접수 기록](../content-reviews/2026-09-12-review-excerpts.md)에 연결한다. `[현재 사실]` 이 범위는 구현됐고 독립 콘텐츠·실행 검증을 통과했다. 전체 통합 gate와 미실행 범위는 [R1 작업 카드](../work-items/2026-09-12-independent-review-first-use.md#독립-검증과-실행-증거)에 남기며 전체 목표·설치형 MVP 완료와 구분한다.

## 보기 방식과 채점 방식의 첫 확장

`[확정 결정]` `DEC-KEYWORD-REVIEW-01`·`DEC-REVIEW-GRADING-01`과 2026-09-14 후속 구현 지시에 따라 R2 가운데 **하나씩/전부 보기와 개별/전체 채점**을 먼저 완성한다. `[현재 사실]` 제품 코드와 작성자 focused 검사를 반영했고 반환 수정 후 독립 데스크톱 검증·최종 통합·빌드·보존 검사를 통과했다. 실패·수정 이력과 검증 한계는 [작업 카드](../work-items/2026-09-14-review-display-and-grading.md)에 구분한다. 문항·보기·정답·해설·학습 목표를 바꾸지 않는 일반 제품 기능이다.

- **바로 시작:** 기본값은 하나씩 보기·개별 채점이다. 문제 화면에서 두 방식을 각각 바꿀 수 있고 필수 설정 화면은 추가하지 않는다. 전부 보기는 현재 선택한 언어·단원·키워드 또는 오답 범위의 같은 문제카드를 세로로 보여 주며 범위 제목과 전체 문항 수를 표시한다.
- **같은 풀이 유지:** 방식 전환은 같은 세션·고정 문항 순서·보기 선택·채점·해설 펼침을 유지한다. 다른 시도나 완료 기록을 만들지 않는다. 기존 `mode: all/incorrect`는 문제 범위이며 새 보기 방식과 혼용하지 않는다.
- **개별 채점:** 선택한 카드만 채점한다. 하나씩 보기에서는 기존 채점 후 다음 문항으로 가는 순차 흐름을 유지하고, 전부 보기에서는 각 카드의 정답 확인을 제공하고 카드마다 이전·다음 버튼을 반복하지 않는다.
- **전체 채점:** 선택한 보기가 있고 아직 채점하지 않은 문항만 함께 채점한다. 미응답과 이미 채점한 문항은 제외하며 `n개 채점, 미응답 m개 남음`을 알린다. 하나씩+전체 채점에서는 채점 전에도 이전·다음으로 이동해 여러 답을 모을 수 있다. 모든 문항이 채점된 뒤 사용자가 결과 보기를 선택할 때 기존 전체 결과·완료 저장 흐름을 사용하며 동일 결과는 한 번만 기록한다. 전부 보기의 긴 목록 끝에도 전체 채점과 결과 보기 동작을 둔다. 채점 후에는 사용한 채점 위치에서 결과 안내가 보이도록 초점과 스크롤을 맞춘다.
- **문서 왕복:** 전부 보기에서도 동작한 실제 카드의 문항 ID로 개념·문서·복귀 문맥을 만든다. 문서에서 돌아오거나 새로고침하면 보기·채점 방식, 현재 문항, 카드 스크롤과 초점을 복구한다. 직접 연 문서에는 문제 복귀를 만들지 않는다.
- **표현과 안전:** 동일 카드 렌더러를 재사용하고 하나씩/전부 보기 모두 같은 문항 ID 접미사의 고유 DOM ID·radio 그룹을 사용한다. 명시적 문항 식별자로 선택과 해설이 다른 카드에 적용되지 않게 한다. 구버전 저장의 초점 ID가 없어지면 현재 카드의 같은 역할 조작 또는 제목으로 안전하게 이동하며 선택·채점을 버리지 않는다. 기존 키보드 흐름·semantic token·텍스트 상태 안내·코드 escape·콘텐츠 서명·유효 복귀 토큰·감지한 탭 충돌·저장 실패 안내를 유지한다. 기존 정적 데이터와 저장소 인터페이스로 동작하며 외부 요청과 의존성을 추가하지 않는다.

저장 필드는 [v1 보기·채점 확장 계약](../content-schema.md#보기채점-방식의-v1-확장)을 따른다. 이번 구현·실제 화면 확인은 데스크톱 웹에 한정한다. 모름·헷갈림·즉시 문항 재도전·문제별 최초/최근/버전 이력·v2 콘텐츠와 저장·모바일·새 문항·Java 실행·설치·Git 게시·밤위키 변경은 후속 범위다. 기존 전체 목표의 모름 응답과 제출 ledger 계약을 이번 기능의 선행 조건으로 만들지 않는다.

완료는 네 조합의 전환에서 같은 선택·채점·해설을 유지하고, 미응답/채점 완료 제외와 중복 완료 저장 방지, 전부 보기의 카드별 radio·개념 연결, 비첫 문항의 문서 왕복·새로고침·키보드 초점과 legacy v1 복구를 확인한 뒤 판단한다. 테스트 작성, 독립 `test_engineer`, `project_integrator`의 최종 통합 gate를 분리하며 결과와 미실행 범위는 작업 카드에 기록한다.

### 문제 묶음 완료 후 다음 키워드

`[확정 결정]` 2026-09-14 사용자 정정에 따라 **정답 확인 후 같은 문제 화면의 다음 문제 버튼으로 바로 이동**한다. `[대체됨]` 앞선 결과 화면을 반드시 거쳐 다음 키워드를 선택하는 계약은 이 흐름으로 대체한다. 기존 문항·선택지·정답·해설·학습 목표를 바꾸지 않는 일반 제품 기능이며 아래는 구현·검증 계약이다.

- **문제 화면에서 이동:** 같은 묶음 안의 **다음 문제**는 기존 순서·채점 방식의 이동 조건을 유지한다. 묶음 끝에서 모든 문항을 채점했고 다음 후보가 있으면 같은 화면의 **다음 문제**를 누를 때 현재 완료 결과를 한 번 저장하고 다음 묶음 첫 문제로 바로 이동한다. 성공 경로에서 중간 결과 화면을 렌더링하거나 그 제목으로 초점을 옮기거나 추가 확인 클릭을 요구하지 않는다. 정답·오답 모두 채점 뒤 사용자가 선택해서 이동하며 자동으로 넘기지 않는다. 일반 범위 표시는 **선택한 범위 복습**, 오답 범위는 **오답 다시 풀기**를 유지한다.
- **전부 보기와 끝 상태:** 전부 보기에서도 현재 묶음의 모든 문항을 채점한 뒤 후보가 있으면 **다음 문제**로 직접 이동할 수 있다. 미채점 문항이 남으면 다음 묶음으로 건너뛰지 않는다. 다음 후보가 없으면 **결과 보기** 또는 문제 목록을 안내하고, 실제 목록의 마지막일 때만 마지막 묶음이라고 표시한다. 명시적인 결과 확인·최근 완료 결과·재도전과 실패 상태 확인용 결과 화면은 유지하되 다음 문제 이동의 필수 경유지로 삼지 않는다.
- **후보와 주제:** 기존 다음 후보 계산과 객관식 목록의 검증된 카드·중복 제거·정적 순서를 재사용한다. 현재 범위에 대응하는 카드 다음의 같은 주제 실제 묶음만 고르고 처음으로 순환하지 않는다. 공유 개념은 기존 정규화 규칙을 따르며 실행 언어가 Java여도 Java·Spring·알고리즘을 섞지 않는다. 대응 카드·주제를 확정할 수 없는 단원 전체·언어 전체·임의 깊은 범위와 문항 없는 후보에는 다음 이동을 만들거나 마지막이라고 단정하지 않는다. 기존 카드명·문항 수로 다음 범위를 알 수 있게 하고 기존 URL을 그대로 연다.
- **저장·복귀 보존:** 직접 이동에도 완료 확정·`recordAttempted`·기존 저장소 계약을 적용해 현재 결과를 한 번만 기록한다. 감지된 다른 탭 충돌이나 결과·활성 세션의 실제 저장 실패가 있으면 상태와 안내를 유지하고 이동하지 않는다. 기존 메모리 저장은 경고와 함께 허용하고 영속 저장으로 표현하지 않는다. 정상 저장 후 사용자가 선택한 새 범위로 활성 세션 하나를 교체하며 이전 완료는 기존 최근 이력에 남긴다. 안정 ID·v1 저장 키·서명·유효 복귀 토큰·새로고침·문서 왕복과 선택·해설·위치 복구에는 마이그레이션이 없다.
- **완료 기준:** HTML 한 문항 키워드에서 채점→같은 화면의 다음 문제→다음 실제 키워드 첫 문항이 중간 결과 화면 없이 동작하고 현재 완료는 한 번만 기록돼야 한다. 여러 문항의 내부 이동, 전부 보기의 모두 채점 조건, 마지막/대응 없는 범위, 정오와 무관한 사용자 선택, 저장 실패·탭 충돌 차단과 메모리 경고를 변경 범위에서 확인한다. 기존 semantic token·네이티브 키보드 조작과 다음 문제 제목으로의 초점을 유지한다. 독립 `test_engineer`·`project_integrator`가 실제 실행·재사용·미실행 증거로 판정하며 데스크톱 웹·기존 로컬 데이터에 한정한다. 새 콘텐츠·외부 요청·의존성·모바일·전체 과목 재검사·Git 게시·밤위키 변경은 포함하지 않는다.

## 주제 탐색과 문서 읽기 개선

`[확정 결정]` [2026-09-13 사용자 피드백](../roadmap.md#2026-09-13-확정-제품-결정)에 따라 R1의 표시·탐색을 아래처럼 개선한다. 개선 전에는 B 배지와 제품명이 분리되고 목록에서 모든 카드를 먼저 보여 주며, 반입 문서의 학습 목표·요약과 출처가 상단·본문에 중복됐다. `[현재 사실]` 아래 표시·탐색 변경은 제품 코드에 반영됐다. 독립 실행·통합의 실제 판정과 검증 한계는 [이번 작업 카드](../work-items/2026-09-13-learning-navigation-polish.md)를 따른다.

- 브랜드는 `BAM.dev` 한 개의 홈 링크로 표시한다. 기존 실습 화면의 shell에도 같은 이름과 이동 목적을 적용한다.
- 문서·문제 목록은 **키워드 검색 → 큰 주제 선택 → 문서 또는 문제 묶음 카드** 순서다. 검색과 주제가 모두 없는 첫 화면에는 주제를 고르는 안내를 보여 주고 전체 카드를 나열하지 않는다. 주제 없이 검색하면 전체에서 찾고, 주제를 선택하면 검색을 그 범위에 적용한다. 사용자가 직접 전체를 선택한 경우에는 전체 목록을 볼 수 있다.
- 큰 주제는 HTML·CSS·JavaScript·Java·Spring·알고리즘·CS·TypeScript·React의 맥락으로 구분한다. 실제 콘텐츠가 있는 주제만 문서·문항 수와 진입을 제공한다. Java는 현재 정적 문서·객관식 주제로 제공하며 과거 샘플 표시는 이력으로 남긴다. 두 JavaScript 과정은 같은 언어 주제로 묶고, JavaScript로 작성된 알고리즘은 별도 주제로 유지한다. Spring은 후속 정적 입문 묶음으로 제공하며 CS·TypeScript·React 등 미제공 주제는 ‘준비 중’으로 구분한다.
- `[대체됨]` 이 작업에서는 제목·소개 → 한줄 요약 또는 핵심 질문 → 학습 목표 → 객관식 복습 링크 순서로 원문과 메타 목표를 모았다. 목표·요약의 최신 역할과 중복 없는 표시 위치는 아래 [시안 채택 계약](#채택-시안의-홈목록읽기-계약)으로 대체한다. 원문·앵커 보존 원칙은 유지한다.
- 문서 상단의 원문 출처 UI를 제거하고 문서 목록 하단에 ‘일부 학습문서는 밤위키 학습자료를 바탕으로 작성했습니다.’를 작게 안내한다. 전체 기존 교안이 밤위키 반입 자료라는 오해를 만들지 않으며 제작용 출처·반입일·해시는 데이터에 보존한다.
- 본문의 큰 개념 제목(`h2`) 앞에는 문단 사이보다 넉넉한 여백과 구분을 둔다. 코드·표 내부 줄바꿈이나 원문 문장·순서를 고치지 않는다.

이는 **일반 제품 기능** 변경이다. 교안·문항·목표의 교육 문장과 의미, 정답·해설·답안의 공개 시점, 관련 개념 지원 수준은 유지한다. 선두 절 추출은 정확한 heading 경계에 한정하고 같은 이름이 코드 블록 안이나 후반 본문에 있다고 옮기지 않는다. 옮긴 절에도 기존 heading ID를 보존하여 개념 오버레이에서 문서로 이동하는 앵커를 깨뜨리지 않는다. 기존 lesson/course/concept ID·깊은 URL·풀이 세션·진도·저장 키에는 마이그레이션이 없다. 주제는 목록 표시용 묶음이며 콘텐츠 과정 ID를 바꾸지 않는다.

검색·주제 선택·초기화는 키보드로 조작할 수 있고 선택 상태와 준비 중 상태는 글자로도 구분한다. 기존 focus 표시를 유지하며 320px·390px·데스크톱에서 주제가 줄바꿈되고 코드·표의 가로 스크롤은 내부에 한정된다. 정적 로컬 콘텐츠만 사용하고 새 의존성·네트워크 읽기·팔레트·React 이관을 추가하지 않는다. 밤위키 원문과 설정, 공개 금지 자산은 변경·반입하지 않는다.

완료 조건은 두 목록의 초기/선택/검색/빈 결과, JS 묶음과 알고리즘 분리, 문서 상단의 목표·요약 1회 표시와 원문 일치, heading·답안 공개 경계·문제 왕복 보존, 실제 키보드·좁은 화면 확인이다. 독립 검증 뒤 안전한 복제본의 전체 gate를 수행한다. 기존 승인 내용을 넘어 교육적 의미 변경이 필요하면 구현에서 결정하지 않고 bam에게 반환한다.

## 문서 하단 자기 확인과 완료 표시

`[현재 사실]` 개선 전 문서 하단은 실제 `lesson.essentialQuestion` 대신 일반 완료 안내를 표시하고, `## 면접 답변 예시`를 학습 완료 때만 열었다. `[확정 결정]` [자기 확인 흐름 요청](../roadmap.md#2026-09-13-확정-제품-결정)에 따라 질문·비교 자료·완료 동작을 아래처럼 분리한다. 제품 구현·검증 상태는 [자기 확인 작업 카드](../work-items/2026-09-13-lesson-self-check.md)를 따른다.

- 모든 기존 교안 하단에 완료 여부와 무관하게 해당 `lesson.essentialQuestion`을 표시하고 ‘먼저 자신의 말로 답해 보세요.’로 안내한다.
- 반입 3교안의 정확한 `## 핵심 정리` 절은 원문 내용·heading ID를 유지한 채 하단의 접힌 영역으로 옮긴다. ‘아래를 누르면 핵심 정리를 펼쳐 자신의 답과 비교할 수 있습니다.’와 ‘핵심 질문 답 확인하기’로 자료의 성격을 알린다.
- 기존 31교안의 정확한 `## 면접 답변 예시` 절은 완료 잠금 없이 접힌 영역으로 옮긴다. ‘아래를 누르면 확인 문제의 답변 예시를 펼쳐 자신의 설명과 비교할 수 있습니다.’와 ‘답변 예시 확인하기’를 사용한다. 여러 확인 문제의 답을 핵심 질문 전용 직접답으로 표현하지 않는다. 두 절이 모두 없으면 빈 펼침 버튼이나 새 답변을 만들지 않고 자신의 설명과 완료 선택만 제공한다.
- 펼침은 네이티브 `details`를 사용한다. 완료 기록이 있어도 문서 새 진입에는 접힘으로 시작하며, 답변 열람은 진도·정답·숙달을 저장하지 않는다. 같은 화면에서 완료를 변경해 다시 렌더링할 때만 현재 펼침 상태를 보존한다. 단, 문제의 명시적인 `section` 이동 대상이 접힌 영역 안에 있으면 그 영역만 열고 기존 앵커 스크롤·초점을 수행한다. 기존 `js.control-flow`의 ‘핵심 정리’ 연결도 이 예외로 보존한다.
- ‘학습 완료로 표시’는 별도 영역의 동작이다. 답변 열람을 강제 선행 조건으로 잠그지 않고 사용자가 자신의 판단으로 선택하며 저장 상태와 ‘완료 표시 해제’를 제공한다. 완료 변경은 답변을 자동으로 열거나 닫지 않는다. 저장 실패를 성공으로 안내하지 않는다.

이는 기존 자료의 표시 순서와 자기 확인 동작을 명료하게 하는 **일반 제품 UI 변경**이다. 교육 문장·문항·학습 목표를 생성·수정하거나 새 A/E/C/T 경험·학습 성과를 주장하지 않는다. 정확한 절 경계와 코드 블록을 구분하고 원문 문장·코드·기존 heading ID를 보존한다. 기존 문서·개념 ID, 문제에서의 문서 왕복·풀이 상태, `completedLessonIds`·저장 키에는 마이그레이션이 없다.

`[대체됨]` 앞선 [주제 탐색·읽기 개선](#주제-탐색과-문서-읽기-개선)의 답안 공개 시점 보존은 그 작업의 이력이다. 이번 요청에서는 **완료가 답변 공개를 제어하던 연결만** 위 독립 펼침으로 대체한다. 객관식 채점·해설 공개와 개념 오버레이 계약을 바꾸지 않는다.

완료 조건은 기존 질문 표시, 원문 자료의 정확한 이동·앵커, 초기 접힘·열람 무저장, 완료·해제와 펼침의 독립성, 재렌더링 유지·재진입 접힘, 기존 진도·문제 복귀 보존이다. 키보드로 펼침·완료를 조작하고 초점·저장 실패·320px·390px의 긴 질문과 답변을 확인한다. 정적 로컬 콘텐츠를 재사용하며 밤위키 원문·설정·공개 금지 자산·새 의존성·설치·배포는 변경하지 않는다. 미결정은 없다.

## HTML 개념 문서 전환

`[현재 사실]` 기존 제품 HTML 5교안은 `bam-authored` 자료이며, 밤위키의 현재 HTML 승인 교안 5개를 반입한 파일이 아니다. 위 자기 확인 UI는 모든 과목에 있지만 레거시 HTML에서 펼치는 여러 확인 문제의 답변은 문서 핵심 질문의 직접답과 다르다. `[확정 결정]` [`DEC-HTML-CONCEPT-LESSONS-01`](../roadmap.md#2026-09-13-확정-제품-결정)에 따라 실제 밤위키 HTML 교안을 바탕으로 필요한 개념만 나누고, 각 문서의 질문과 직접답까지 함께 완성한다. `[현재 사실]` 파생 문서·명시적 직접답·활성/보관 목록·실제 개념 매핑과 왕복 지원을 코드·콘텐츠에 반영했다. 독립 콘텐츠·UI·통합 판정과 확정 매핑은 [HTML 작업 카드](../work-items/2026-09-13-html-concept-lessons.md)에서 구분하며 구현 존재만으로 검증 완료를 뜻하지 않는다.

- **범위:** 하나의 핵심 질문으로 설명할 수 있는 가장 작은 의미 단위를 고른다. 요소와 속성, 비교해야 이해되는 선택쌍과 같은 판단 흐름은 함께 두며 종합 점검도 목적이 있으면 유지한다. 제목 수·분량·문서 개수를 맞추기 위한 분할은 하지 않는다. 원문 구간·선수 개념·예제·적용 경계가 새 목표와 맞는지 매핑으로 확인한다.
- **읽기:** 제목 아래는 학습 후 할 수 있는 능력, 한줄 요약은 핵심 개념이다. 본문 끝에는 해당 문서의 `essentialQuestion`과 명시적 `answerHeading`이 가리키는 **직접답**을 연결한다. ‘핵심 질문 답 확인하기’를 누르면 접힌 답이 열리고 자신의 답과 비교한다. 질문과 무관한 여러 면접 답안을 직접답으로 표시하지 않는다. 기존 `details`·목차·section 이동과 독립된 수동 완료·완료 해제를 재사용한다.
- **목록과 순서:** 신규 문서는 같은 HTML 과정에 추가하고 기본 목록에는 활성 문서를 보여 준다. 기존 5교안은 `archivedFromCatalog: true`로 기본 카드 목록에서 제외하되 원래 ID·slug·본문·깊은 URL을 그대로 연다. 읽기 번호와 이전·다음은 현재 문서와 같은 활성/보관 묶음에서 계산한다. 내부 `order`와 사용자에게 보이는 읽기 위치는 구분한다.
- **객관식:** 문항의 기존 소유 교안과 ID·문구·정답·해설을 유지한다. 검증한 개념 매핑이 있는 경우에만 새 문서에서 원래 키워드 풀이 범위로 연결하고, 없으면 관련 문제가 아직 준비 중임을 안내한다. 문항 수나 없는 문제를 만들지 않는다. 개념 오버레이는 매핑된 새 문서의 실제 절과 발췌를 보여 주며 문제의 기존 소유 교안과 상세 문서의 차이는 [데이터 계약](../content-schema.md#html-파생-교안의-전환-계약)으로 검증한다.
- **왕복과 진도:** 기존 문제에서 저장된 복귀 문맥과 URL은 계속 유효하다. 새 문서 복귀는 문항→개념→상세 문서의 실제 연결과 기존 token을 검증할 때만 허용한다. 선택·채점·해설·현재 위치·완료 시도 서명은 보존한다. 이전 5교안의 완료를 새 ID로 복사하거나 새 문서 열람·답 열람을 완료로 저장하지 않는다. 저장 키·기존 완료/오답/실습 기록을 초기화하지 않는다.

출처에는 실제 `wiki/학습자료/밤데브 학습문서/` 상대 경로와 원문 전체 SHA를 남기고, 원문 재편·목표·질문·답 보완은 `derived`로 구분한다. 원문 frontmatter·Obsidian 전용 링크·관리 문구의 제외와 파생 경계는 검토 기록에 남긴다. 제품에는 개인 절대 경로·비공개 기록·공개 금지 자산을 넣지 않으며 밤위키는 읽기 전용이다. CSS·JavaScript 등 다른 과목, 원래 문항·Quest·Web Project, 새 의존성·설치·배포·Git은 변경하지 않는다.

완료는 원문별 범위 누락·잘못된 합침/분할 없음, 목표·요약·질문·직접답 대응, 실제 개념·문항·절 참조, 새/기존 URL과 진도·왕복 보존을 독립 검증한 뒤 판단한다. 답 펼치기·완료·복귀를 키보드와 320px 화면에서 확인하고 원시 HTML 비실행과 정적 로컬 동작을 유지한다. 학습 경험 카드·공식 출처를 검토한 `content_validator`, focused 실행·UI를 확인한 `test_engineer`, 안전한 복제본의 전체 gate를 확인한 `project_integrator`를 분리한다. 원문에 기록된 과거 검증을 이번 제품·학습 성과의 PASS로 재사용하지 않는다.

## CSS 개념 문서 전환

`[확정 결정]` [`DEC-CSS-CONCEPT-LESSONS-01`](../roadmap.md#2026-09-13-확정-제품-결정)의 “css문서도 분리” 요청은 위 [HTML 전환 계약](#html-개념-문서-전환)을 CSS에 이어 적용한다. 필요한 개념 단위와 함께 비교할 관계를 구분하고 목표·요약·핵심 질문·직접답·실제 문항 연결을 함께 재구성한다. 기존 제품 CSS 6교안과 밤위키의 승인 CSS 원문 7개는 서로 다른 자료이므로 기존 교안의 출처나 본문을 위키 원문으로 덮어쓰지 않는다. 고정한 단위·출처·연결과 실제 진행 상태는 [CSS 작업 카드](../work-items/2026-09-13-css-concept-lessons.md)가 담당한다.

`[현재 사실]` 새 CSS 본문·metadata·개념 연결을 반영하고 관리 콘텐츠 검사를 통과했다. 독립 콘텐츠·문서 검토와 focused/대표 데스크톱 흐름은 통과했다. 수정 후 최종 통합 gate·정적 빌드·보존 검사도 통과했다. 별도 CSS 예제 계산 실행·reduced-motion 환경 전환은 도구/보안 정책 제한으로 미검증이다. 정확한 범위와 증거는 [CSS 작업 카드](../work-items/2026-09-13-css-concept-lessons.md#독립-실행-범위와-미실행-한계)에 남긴다.

HTML에서 구현한 `archivedFromCatalog`·`answerHeading`·`documentLessonId`와 활성/보관 목록·자기 확인·문제 왕복을 그대로 재사용한다. 새 CSS 문서는 같은 과정에 새 ID로 추가하고 기존 6교안은 보관 표시만 추가하여 URL·본문·순서·완료 기록과 기존 문항·실습 소유 관계를 보존한다. 원문의 선수·예제·오개념을 빠뜨리지 않고 질문에 직접 답할 수 있는 분량으로 나누며 비교쌍·진단 순서·종합 예제를 문서 수를 맞추려고 쪼개지 않는다. 상단은 최신 [목록과 읽기](#목록과-읽기)에 따라 목표·요약을 한 학습 목표 영역에 표시하고 선수 개념을 첫 구분선 위에 둔다.

문항 연결은 새 문서의 실제 범위에 맞는 기존 CSS 개념만 매핑한다. 문항이 없는 개념은 준비 중으로 표시하고 새 문항·해설·Quest·Web Project를 만들지 않는다. 보존의 유일한 예외는 `quiz-css-flex-axis`의 코드에 `writing-mode: horizontal-tb;` 한 줄을 넣어 기존 정답 판단에 필요한 글쓰기 조건을 명시하는 유지보수다. 이 코드가 포함된 진행 세션의 서명 변경은 기존 콘텐츠 변경 안내로 안전하게 처리하고 나머지 문항·완료 기록을 초기화하지 않는다. 학습문서에서 객관식으로 이동할 때 CSS 주제를 유지하는 [서비스 주제 연결](#탐색-사이드바의-상태와-복귀)과 유효한 문제 복귀 토큰의 우선순위도 보존한다. 새 완료 ID는 사용자가 직접 표시할 때만 기록하며 저장 키·기존 진도·풀이 세션을 이관하거나 초기화하지 않는다.

원본은 읽기 전용이고 새 파일만 `derived`로 기록한다. 앱은 교안 코드를 텍스트로 표시하며 자동 실행하지 않는다. 외부 요청·의존성·디자인 자산을 추가하지 않는다. 이번 제품 작업과 확인은 데스크톱 웹에 한정한다. 원문에 있는 반응형·접근성 개념은 유지하되 모바일 제품 구현·모바일 테스트를 추가하라는 뜻이 아니다. 작성자 focused 검사, 독립 콘텐츠 검증, 독립 테스트 감사·필요한 웹 확인 뒤 [공통 검증과 재검증](../development-workflow.md#공통-검증과-재검증)에 따라 최종 통합 gate를 수행한다. Git 게시·병합·배포는 이번 범위에 포함하지 않는다.

## JavaScript·Java 개념 문서와 객관식 전환

`[확정 결정]` [`DEC-JS-JAVA-CONCEPT-REVIEW-01`](../roadmap.md#2026-09-14-확정-제품-결정)에 따라 승인된 밤위키 JavaScript·Java 교안을 필요한 개념 단위로 재구성하고 문서별 목표·요약·핵심 질문·직접답·실제 객관식 연결을 함께 완성한다. 현재 범위·단위 계보·문항별 경험·구현 및 독립 판정은 [작업 카드](../work-items/2026-09-14-js-java-concepts-and-review.md)에 둔다. 아래 계약의 작은 교안·문항·공유 상세 문서·카드/CTA 연결은 구현됐다. 독립 내용·문서 검토, 콘텐츠 검사·테스트 작성 focused와 독립 데스크톱 실행을 통과했다. 수정 후 최종 통합·정적 빌드·보존 검사도 통과했으며 실패·수정 이력과 검증 한계는 작업 카드에 기록한다.

- **단위와 읽기:** 한 문서에서 한 핵심 판단을 연습한다. 배열/객체 선택, 반환/출력, 얕은 복사/공유, 비교쌍과 종합 흐름은 필요한 관계를 유지한다. 기존 학습 목표 통합 영역·첫 구분선 위 선수·접힌 직접답·수동 완료/해제를 재사용한다. 목표·질문·직접답이 다른 개념을 가리키거나 질문에 답하지 않는 자료를 직접답으로 표시하면 반환한다.
- **활성/보관:** JS 신규 단위와 기존 runtime을 활성으로 두고 나머지 기존 JS·Java 교안은 보관한다. 기존 ID·본문·내부 순서·깊은 URL·완료는 보존하고 새 단위에 완료를 복사하지 않는다. runtime은 새 위키 파생본으로 복제하지 않았고 `면접 답변 예시`와 `answerHeading` 없는 기존 metadata를 유지했다. 이 문서까지 새 직접답 UI로 통일했다고 표현하지 않는다.
- **문항 제공:** 기존 JS·Java 문항 객체를 보존하고 필요한 판단만 추가한다. 기존 문제로 충족하는 판단은 재사용한다. 문제 자체에서 대상·행동·판단 형태와 필요한 타입·코드·조건을 이해할 수 있어야 하고 각 보기 이유가 같은 조건을 기준으로 정오를 설명해야 한다. 정확한 문항 수보다 [문항 작성 기준](#객관식-문항-작성과-검토-기준)과 경험 차이를 우선한다.
- **공유 상세 문서:** 문항 소유 교안은 유지한다. 상세 문서만 다른 과정에 있는 경우 두 과정이 언어 카테고리이고 같은 언어일 때만 허용한다. 같은 JavaScript라도 알고리즘과는 공유하지 않는다. 상세 교안의 concept·heading·발췌, 문항의 소유·언어와 존재 검증은 [데이터 계약](../content-schema.md#javascriptjava-파생-교안과-공유-상세-문서)을 따른다.
- **중복 없는 탐색:** 언어 내 해당 concept의 모든 문항이 같은 상세 문서·주제로 연결된 경우에만 목록과 문서 CTA를 한 개념 카드로 합친다. 기존 v1 언어+개념 route로 해당 문항 전체를 선택하며 소유별 깊은 URL도 유효하다. 조건을 확인할 수 없는 묶음은 기존 소유별 탐색을 유지한다. 이는 전부 보기 화면·전체 채점·v2 복합 개념 저장을 추가하는 작업이 아니다.
- **왕복과 기록:** 기존 토큰·세션·문항·대상 문서의 유효성 검사를 유지한다. 직접 문서에 문제 복귀 버튼을 만들지 않는다. 새 문항으로 풀이 범위의 집합 서명이 바뀌면 기존 콘텐츠 변경 안내·복구 안전 계약을 적용하며, 기존 문항 객체와 완료 이력 보존을 활성 세션의 무조건 보존으로 과장하지 않는다.
- **Java 제공 상태:** 정적 문서·객관식 제공과 연결을 반영해 Java 언어·과정은 현재 `available`이다. 위 표와 과거 탐색 개선의 Java 샘플 표시는 해당 시점의 이력이며, 새 표시를 Java runner·Spring·설치 지원·MVP release 완료로 해석하지 않는다.

이번 대상은 데스크톱 웹이며 새 디자인·모바일 구현·외부 요청·의존성·Git 작업을 추가하지 않는다. HTML·CSS·알고리즘·Quest·코딩테스트·웹과제·저장 키와 밤위키 원문·설정·비공개 기록은 보존한다. 원문/공식 근거·손 추적으로 내용과 정답을 확인하고 대표 JS 코드를 로컬에서 실행한다. Java 코드는 정식 Java 25·preview 없음 기준으로 읽기 검토하며 실행 계약이 없는 정적 범위는 N/A를 명시한다. 미실행 결과를 컴파일·실행 PASS로 기록하지 않는다. 독립 `content_validator` → `test_engineer` → `project_integrator`와 [공통 검증](../development-workflow.md#공통-검증과-재검증)을 거쳐 실제 최종 상태를 판정한다.

## 알고리즘 Java 전환과 기초 문서 분리

`[확정 결정]` 2026-09-14의 최신 ‘알고리즘 문서는 자바 기준으로 수정’ 요청에 따라 알고리즘의 활성 14문서를 **정식 Java 25·preview 없음** 기준으로 통일한다. 기존 ‘리스트·조건문·딕셔너리·스택과 큐’는 **리스트·조건문**, **딕셔너리**, **스택과 큐** 세 묶음으로 나눈다. 앞선 JavaScript 예제를 유지한다는 계획은 이 결정으로 대체한다. 확인된 Java 원문 3개는 참고 자료로 구분하고, 나머지 기존 제품 교안 10개는 작성 권한 범위에서 Java로 전환한다. 자료 개수와 최종 교안 수를 같은 단위로 세지 않는다.

- **학습 범위:** 기존 알고리즘 목표·문제 해결 예제를 보존하면서 언어별 표현·API·전제를 Java에 맞춘다. 세 기초 문서는 기존 목표를 나눈 유지보수이며 문서 수 증가 자체를 새 A/E/C/T 경험으로 주장하지 않는다. 각 목표·요약·핵심 질문·직접답과 실제 선수 개념을 일치시키고 `answerHeading: "핵심 질문 답"`과 기존 수동 완료 UI를 사용한다. 스택·큐는 `Deque`·`ArrayDeque` 객체 생성부터 넣기·다음 값 확인·꺼내기·빈 상태 확인까지 자주 쓰는 메서드와 빈 구조의 결과를 설명한다. 새 객관식·Quest·다른 과목의 교육 내용은 추가하지 않는다.
- **ID·순서·진도:** 새 `algo-list-conditions` / `list-and-conditions`, `algo-dictionary` / `dictionary`를 order 1·2로 둔다. 스택·큐는 `js-10-stack-queue` / `stack-and-queue`와 완료 기록을 유지하고 order 3으로 옮긴다. Java 해시는 새 `algo-hash-map-set` ID로 기존 `algorithm/hash-map-set` 경로를 사용한다. 이 해시를 제외한 기존 알고리즘 11교안의 ID·slug·완료 기록은 유지하며 전체 순서는 1~14로 맞춘다. 새 두 기초 문서와 새 Java 해시에 기존 완료를 복사하지 않는다.
- **JavaScript Quest 호환:** 기존 `js-09-hash-map-set`의 JavaScript 본문·ID·개념 소유는 JavaScript 과정의 보관 교안으로 유지한다. HEAD 원문을 `content/lessons/javascript/hash-map-set-reference.md`에 바이트 그대로 복제하고 JavaScript 과정의 기존 순서 뒤에 추가한다. 네 JavaScript 해시 Quest는 기존 코드·ID·`lessonId`·개념·풀이 기록을 유지한다. 기존 해시 완료는 이 보관본에 남고, 원래 알고리즘 URL은 새 Java 문서와 그 완료 상태를 표시한다. 알고리즘 과정과 교안의 `languageId`를 `java`로 맞추되 `categoryId: algorithm`과 저장 키는 유지한다.
- **승인된 시각화:** 사용자가 승인한 스택·큐 이미지 두 장의 로컬 PNG 복사본을 각각 개념 설명 뒤·코드 앞에 배치하고 의미를 전달하는 대체 텍스트를 제공한다. 현재 Markdown의 이미지 미지원에는 프로젝트에 반입한 안전한 PNG 경로만 허용하는 최소 이미지 블록 렌더링을 추가한다. 외부 URI·Obsidian 절대 경로를 이미지 소스나 제품 출처로 노출하지 않고 승인된 번들 자산만 사용한다. 원본 이미지·밤위키 문서·설정은 보존하며 그 밖의 이미지는 후보 승인 전에 반입하지 않는다.
- **정적 실행 경계:** 교안과 이미지는 번들 Markdown·JSON·PNG로 제공하며 외부 링크를 열지 않아도 읽을 수 있어야 한다. 출처는 실제 자료와 복제·변환 범위에 따라 기록한다. 공식 API 확인과 예제의 임시 개발 검증에는 Java 25를 사용하되, 이는 앱의 시스템 JDK 의존이나 Java runner·실행 기능·새 제품 의존성을 추가하는 결정이 아니다.
- **완료 기준:** 변경한 14문서의 Java API·타입·조건·예제 결과, 목표·질문·직접답, 언어·선수·개념·메타데이터 대응을 확인한다. 실제 문서 링크·연속 순서·기존 경로·완료 보존과 직접 영향받는 네 JavaScript Quest의 정적 연결을 검사한다. 이미지 두 장의 올바른 배치·대체 텍스트·로컬 경로 제한은 변경된 렌더링 범위에서 확인한다. 변경 없는 공통 UI와 다른 과목은 관련 diff를 대조해 검증 증거를 재사용하고 독립 내용·테스트·통합 판정으로 완료를 확인한다. 데스크톱 웹에 한정하며 모바일·전체 과목 재검사·Git 게시를 추가하지 않는다.

## CSS 객관식과 Spring·Spring Boot 기초 확장

`[확정 결정]` [`DEC-CSS-SPRING-FOUNDATIONS-01`](../roadmap.md#2026-09-14-확정-제품-결정)에 따라 기존 CSS 개념 문서에 필요한 객관식을 추가하고, Spring 핵심과 Spring Boot를 함께 다루는 작은 정적 학습문서·객관식 묶음을 만든다. 앞선 CSS 전환의 새 문항 제외는 그 작업의 범위이며 이번 추가를 막는 규칙이 아니다. 단위별 교육 범위·경험 근거와 실제 작성·검증 상태는 [작업 카드](../work-items/2026-09-14-css-quiz-spring-foundations.md)에 기록한다. 본문·문항·metadata·발췌와 주제 표시를 반영했고 관리 연결 검사를 마쳤다. 독립 내용·문서·대표 데스크톱 검증과 수정 후 전체 gate·정적 빌드·보존 검사를 통과했다. 최초 실패·수정 이력과 실제 검증 한계는 작업 카드에서 구분한다.

- **학습 흐름:** 기존 학습 목표·요약, 첫 구분선 위 선수, 핵심 질문·접힌 직접답·수동 완료 표시를 재사용한다. Spring은 공식 자료를 근거로 새로 작성하며 짧은 문서에서도 개념·관찰·작은 예제·오개념·적용 경계를 보존한다. 객관식은 [문항 작성 기준](#객관식-문항-작성과-검토-기준)에 맞춰 대상·행동·필요 조건을 문항 안에 제시하고 실제 문서로 설명 가능한 판단만 추가한다.
- **별도 주제:** Spring을 Java와 구분되는 `Spring · Spring Boot` 주제로 제공한다. 주제 순서는 HTML→CSS→JavaScript→Java→Spring→알고리즘→전체를 사용하고 나머지 준비 중 주제를 유지한다. 과정·카테고리는 Spring, 예제 언어는 Java로 연결하는 [데이터 계약](../content-schema.md#css-객관식과-spring-정적-콘텐츠)을 따른다. 문서·문항 수와 검색·서비스 사이드바 이동은 과정의 주제를 따르므로 Java 문제와 Spring 문제가 서로의 주제 수에 섞이지 않아야 한다. 기존 언어 전체 URL은 Java 언어의 전체 문항을 선택하는 호환 계약을 유지한다.
- **문제 왕복:** CSS의 기존 문항 객체와 소유 관계를 유지하고 새 문항만 추가한다. Spring 문항은 새 Spring 교안이 소유하고 같은 문서의 실제 개념·heading·발췌로 연결한다. 문서 CTA는 실제 문항만 열며 기존 하나씩/전부 보기·개별/전체 채점과 유효 토큰 왕복을 재사용한다. 두 채점 방식을 제공하므로 목록의 고정 `개별 채점` 안내는 제거한다. Spring 범위의 풀이 header와 문서 제목은 과정명을 사용하고 코드 언어는 Java로 유지한다. Spring 교안 범위의 최근 풀이 제목도 `과정명 · 문서명`으로 저장해 홈·목록에서 같은 주제를 알아볼 수 있게 한다. 이전 Java 제목으로 저장된 Spring 세션은 title만 맞추고 서명·선택·채점·viewport와 저장 키를 보존한다. 다른 과정과 Java 언어 전체 범위의 제목·선택 계약은 보존한다.
- **보존·실행:** 기존 본문·ID·URL·완료 이력·저장 키를 변경하지 않는다. 새 문항이 포함되는 범위의 활성 세션은 문항 집합 서명이 달라질 수 있으므로 기존 콘텐츠 변경 안내·복구 안전 계약을 적용한다. 정적 예제는 정식 Java 25·preview 없음 기준으로 작성하며 앱에서 Spring·Spring Boot를 컴파일하거나 실행하지 않는다. 실제 Spring 실행 과제·빌드·의존성·서버·DB는 별도 외부 웹과제 결정을 따른다. Java 코딩테스트 로컬 runner는 이 과제와 별개이며 `DEC-JAVA-RUNNER-01`의 계약과 구현 승인을 따른다.

이번 대상은 데스크톱 웹이다. 번들된 Markdown·JSON과 기존 저장소로 읽기·채점이 가능해야 하며 공식 출처 링크를 열지 않아도 풀이와 문서 왕복이 완료돼야 한다. Java 컬렉션 로드 실패는 과정이 참조하는 언어로 판정해 Spring 주제에도 실제 실패를 표시한다. 실제 링크·직접답·보기·키보드 초점과 CSS/Spring 주제 분리, 기존 기록 보존을 필요한 focused 검사와 대표 웹 흐름에서 확인한다. Spring 실행 검증·모바일·설치·Git 게시를 이번 완료 조건으로 확대하지 않는다. 작성자·관리자 뒤 독립 `content_validator` → `test_engineer` → `project_integrator`를 거쳐 최종 상태를 판정한다.

## Spring Security·JPA 정적 학습 확장

`[확정 결정]` [`DEC-SPRING-SECURITY-JPA-01`](../roadmap.md#2026-09-14-확정-제품-결정)에 따라 공식 문서를 근거로 Spring Security와 JPA·Spring Data JPA의 작은 개념 문서·객관식을 추가한다. 보안·영속성의 책임을 초보자가 설명하고 주어진 조건에 적용하는 후속 학습이며, 마지막에는 DB 회원 조회와 Security 연결을 정적으로 다룬다. 기존 Spring 입문 작업의 제외 범위는 당시 이력이다. 이번 단위·경험·출처와 실제 작성·검증 상태는 [작업 카드](../work-items/2026-09-14-spring-security-jpa.md)에서 구분한다.

- **현재와 목표:** 기존 Spring 핵심·Boot 정적 과정 뒤에 Security·JPA를 구분되는 학습 묶음으로 작성하고 연결했다. 독립 내용·실행·통합 판정은 작업 카드의 증거를 따른다. 새 화면이나 별도 카테고리 없이 `courseId: spring`, `languageId: java`와 기존 목록·문서·복습 흐름을 사용한다. 단위·수량은 작성자의 경험 계획과 실제 콘텐츠로 확정하며 수량을 교육 목표로 삼지 않는다.
- **읽기와 복습:** 한 핵심 질문에 답하는 목표·선수·관찰·작은 예제·적용 경계·자기 설명·접힌 직접답과 실제 관련 문항을 제공한다. 공식 문서의 번역·복제 대신 승인된 새 저작으로 기록한다. 같은 문서의 실제 heading·본문 발췌를 연결하고 하나씩/전부 보기·개별/전체 채점·유효 세션 왕복·수동 완료 표시를 보존한다.
- **데이터와 보존:** [기존 Spring 스키마 계약](../content-schema.md#css-객관식과-spring-정적-콘텐츠)을 그대로 적용한다. Security는 `spring-security-<key>` / `security-<key>` / `spring.security-<key>`, JPA는 `spring-jpa-<key>` / `jpa-<key>` / `spring.jpa-<key>`의 교안 ID·slug·conceptId를 사용한다. 기존 Spring 입문 묶음 뒤에 Security order 21~32, JPA order 33~46을 부여하고 Java 퀴즈 컬렉션에 새 객체만 추가한다. 기존 ID·URL·저장 키·문항 객체·완료 이력을 유지하며 변경된 문항 집합은 기존 서명 안내를 따른다. 기존 첫 Spring 문서의 범위 안내 문단과 Spring 과정의 `description` 한 필드만 최신 범위에 맞게 수정한다.
- **실행과 대상:** 데스크톱 웹의 번들 Markdown·JSON 읽기·객관식 범위다. 출처 링크를 열지 않아도 학습 흐름이 완료돼야 한다. Java 25의 정적 자료이며 Spring Security 의존성·로그인 기능·DB·JPA 실행 환경을 앱에 추가하지 않는다. 실제 Spring 실행은 승인된 외부 웹과제, Java runner는 기존 별도 gate를 따른다. 모바일·설치·Git 게시로 완료 범위를 넓히지 않는다.
- **검증과 반환:** 공식 출처·정답/오답·A/E/C/T는 독립 내용 검토, ID·순서·선수·직접답·문항·발췌·보존은 focused 계약 검사로 확인한다. 새 데이터에 필요한 대표 데스크톱 탐색·왕복·키보드 흐름을 확인하고 변경 없는 UI 증거는 hash와 영향 범위를 대조해 재사용 여부를 판정한다. 교육 결함은 작성자, 연결 결함은 관리자, 테스트 결함은 테스트 작성자에게 반환하며 독립 내용→실행→최종 통합 순서를 유지한다.

### 목록과 읽기

`[확정 결정]` 2026-09-13 HTML 첫 문서 확인 뒤 bam의 후속 요청에 따라 공통 읽기 UI의 데스크톱 배치와 목표 표시를 아래처럼 조정한다. 이 후속 변경은 최소 focused 검사와 사용자 화면 확인을 우선하며, 모바일 추가 작업·모바일 검사·전체 gate 반복은 보류한다. 사용자가 결과를 확인·승인한 뒤 GitHub에 게시한다. 아래는 구현 계약이며 앞선 시안·사이드바 검증을 이번 수정의 완료 증거로 재사용하지 않는다.

- 두 목록의 순서는 검색 → 큰 주제 → 선택 또는 검색 결과 카드다. 기존 전체 콘텐츠·샘플·준비 중 판정, 검색·초기화·주제 묶음·단원과 키워드 링크를 재사용한다. 시안에 없는 주제와 기존 깊은 URL을 제거하지 않는다.
- 읽기 제목 아래에는 **학습 목표** 영역 하나에 현재 원문의 선두 목표·기존에 표시하던 메타 목표·한줄 요약을 모은다. 목표와 요약의 내용·순서는 유지하고, 동일 문구만 한 번 표시한다. 이전의 제목 아래 능력 영역과 별도 요약 상자를 이 하나의 영역으로 대체하며 서로 다른 문장을 합치거나 삭제·재작성하지 않는다.
- HTML 두 번째 문서 확인 뒤의 후속 요청에 따라 정확한 `## 먼저 확인할 개념` 절은 내용·링크·기존 앵커를 보존한 채 학습 목표 아래, 첫 구분선 위의 문서 상단 영역으로 옮긴다. 첫 구분선 다음에는 본문이 바로 시작하며, `먼저 알아둘 세 가지`·`먼저 관찰하기` 등 실제 설명 절과 나머지 본문은 그대로 둔다. 공통 읽기 UI의 표시 이동이며 원문은 수정하지 않는다.
- 이는 현재 원문 목표·요약의 **표시 위치**만 바꾸는 계약이다. `lesson.summary`·`objectives`·본문 파일을 자동 개작하거나 새 목표·요약을 생성하지 않는다. 정확한 선두 절이 없는 문서는 기존 목표·요약 필드를 그대로 사용하는 fallback을 명시적으로 구현·검증하며, 내용이 없다면 없는 문장을 만들지 않는다. 목업의 승인된 JavaScript 표본 문장을 다른 교안에 대량 적용하지 않는다.
- 데스크톱의 전역 사이드바는 왼쪽, **이 문서에서** 목차는 본문 오른쪽 sticky 영역에 둔다. 문서의 실제 heading과 기존 ID를 유지하며 목표·요약의 기존 앵커는 같은 학습 목표 영역에 도달한다. 개념에서 들어온 `section`과 브라우저 깊은 링크도 보존한다. 목차는 키보드로 사용할 수 있고 기존 좁은 화면의 본문 위 배치를 유지한다. 접힌 답 자료의 목차·깊은 링크는 기존 공개 계약대로 해당 영역만 연다.
- 한줄 요약·개념 본문·하단 핵심 질문은 각 역할을 구분하고 개념 절 사이 여백을 넉넉하게 둔다. 코드·표·교육 문장의 줄바꿈과 순서는 임의로 바꾸지 않는다. 목록 하단의 기존 밤위키 안내와 데이터의 제작 출처는 유지한다.

### 탐색 사이드바의 상태와 복귀

`[확정 결정]` 2026-09-13 승인된 [탐색 시안](visual-design.md#승인된-탐색-시안-적용)은 목록을 거치지 않는 문서 바로 이동과 읽던 위치 복귀를 제공한다. UI 배치는 시각 정본이 담당하며 아래는 구현 전 상태 계약이다.

- 같은 앱 실행 중 학습문서·객관식 각각의 마지막 주제와 유효한 읽기/목록 route를 기억하되, 학습문서에서 객관식으로 전환할 때는 아래 후속 주제 연결 규칙을 우선한다. 서비스 버튼으로 문서에 복귀할 때만 메모리에 기억한 `scrollY`와 답 펼침 상태를 복원한다. 직접 링크·최근 문서 링크는 기존 문서 진입 흐름을 따르며, 처음 진입하거나 경로가 더 이상 유효하지 않으면 해당 서비스의 기본 목록으로 간다. 주제 변경은 그 주제의 실제 목록을 열며 홈의 두 독립 진입은 유지한다.
- `[확정 결정]` 후속 요청에 따라 학습문서 목록·문서에서 서비스 메뉴의 **객관식 문제**를 누르면 현재 학습문서의 구체 주제를 객관식 목록에 선택하고 이전 검색어는 비운다. HTML뿐 아니라 같은 주제 분류의 다른 과목에도 적용한다. 다만 유효한 문제 복귀 토큰을 가진 문서에서는 원래 풀던 문제 복귀가 우선이며 풀이·선택·답변·토큰을 보존한다. 주제가 `null`·`all`이면 기존 서비스 복귀를 유지한다. 구체 주제를 선택한 뒤에는 로딩·불러오기 실패·문제 자료 없음에도 그 주제를 유지하고 기존 목록의 로딩·오류·빈 결과 안내를 사용하며 과거 다른 주제로 바꾸지 않는다. 객관식→학습문서 복귀·홈 진입은 기존대로이며 새 저장 키·URL 스키마·의존성은 추가하지 않는다.
- 최근 본 문서는 실제로 연 문서 ID를 중복 없이 최대 2개 기억하고 클릭하면 기존 문서 URL로 연다. 문서를 열거나 검색했다고 학습 완료·문제 시도·진도를 기록하지 않는다. 탐색 상태는 기존 진도·활성 풀이 세션과 분리된 메모리 상태로 시작하며 새 저장 키·새로고침 영속화·데이터 마이그레이션은 추가하지 않는다.
- 통합 검색·바로가기·주제 목록은 기존 실제 콘텐츠·안정 ID·활성/보관 판정을 사용한다. 기존 보관 문서의 깊은 URL은 계속 열리지만 활성 바로가기·검색에 다시 편입하지 않는다. 없는 주제·문항·개념 연결을 만들지 않는다.
- 사이드바의 일반 문서 이동과 최근 문서 링크는 문제 유입 토큰을 새로 만들거나 다른 문서로 전달하지 않는다. 기존 문제→개념→문서 경유의 `review`·`section` 문맥과 세션 검증만 문제 복귀를 허용한다. 서비스 복귀도 기존 검증을 건너뛰지 않으며 선택·채점·해설·문항 위치·완료 기록·초안과 저장 실패 안내를 보존한다.

완료 조건은 실제 검색 결과/빈 결과, 현재 문서를 포함한 바로가기·전체 목록, 최근 문서 중복 제거·순서, 두 서비스의 주제·route·문서 읽기 상태 복귀와 기존 문제 왕복 토큰 보존이다. 제품·콘텐츠·테스트 작성과 독립 검증 역할은 [사이드바 작업 카드](../work-items/2026-09-13-service-sidebar.md)에서 구분한다. 최소 focused 검사와 데스크톱 키보드·화면 확인 뒤 최종 `project_integrator`만 안전한 복제본에서 전체 `npm run check`를 1회 실행한다. 작업자·검증자의 전체 suite 반복, 모바일 추가 작업·검사와 추가 콘텐츠 재감사는 하지 않는다.

### 보존할 풀이·저장·검증 경계

문서 하단의 실제 질문·비교 자료 종류에 맞는 답 보기·수동 완료·완료 해제는 위 [자기 확인 계약](#문서-하단-자기-확인과-완료-표시)을 유지한다. 객관식은 시안 채택 당시의 한 문제씩 개별 채점을 기본값으로 유지하며 [보기·채점 첫 확장](#보기-방식과-채점-방식의-첫-확장)에서 방식 선택을 추가한다. 같은 화면 정답 이유와 선택한 오답 이유·나머지 보기 펼침을 유지하고, 선택·정오·저장 오류를 색만으로 표현하지 않는다. 관련 개념은 기존 **모달 오버레이**와 키보드 초점 복구를 유지하며 시안의 간이 인라인 패널로 바꾸지 않는다. 같은 탭 문서 왕복·조건부 복귀·새로고침·진행 중 세션·완료 기록·저장 키와 서명 검증에는 마이그레이션이 없다.

시안 채택 작업은 일반 제품 UI이며 CSS 교안 분할은 위 [별도 후속 작업](#css-개념-문서-전환)이다. 교육 콘텐츠·확인 문제·답안·개념 발췌·ID·과정 순서·학습자 코드·밤위키 폴더·템플릿·수집·예약·비공개 기록·공개 금지 디자인 자산을 변경하거나 반입하지 않는다. 외부 이미지·원격 폰트·새 의존성·React 이관·Java runner·설치·배포·Git 기준선 변경은 포함하지 않는다.

완료는 홈 문구·독립 진입, 두 목록의 실제 범위·검색·준비 중, 중복 없는 목표·요약과 원문·앵커 보존, 목차·자기 확인·모달 왕복·진도 보존, light/dark의 정상·선택·오류·focus 대비, 키보드와 320px·1024px의 긴 문서·문항·메뉴 표시를 확인한 뒤 판단한다. 외부 요청 없이 로컬 자산으로 동작해야 하며 theme 저장 실패에도 현재 선택과 기존 풀이가 유지돼야 한다. focused 검사와 독립 실제 UI 검증 후 통합 복제본에서 전체 `npm run check`를 한 번 수행하고 미실행 범위는 작업 카드에 남긴다.

## 목표 화면 흐름

이 절의 세부 배치·기본값·기록 정책은 `[제안]`이다. 홈의 두 독립 서비스, 두 보기 모드와 개별/전체 채점 선택, 같은 화면 해설, 개념 오버레이와 문서 왕복, 헷갈림·모름·자율 재도전은 확정 요구다. 전체 채점이 첫 기능 완성을 지연하면 개별 채점을 먼저 완성할 수 있다. 전체 채점은 R1 당시에는 미포함이었고 현재 [보기·채점 첫 확장](#보기-방식과-채점-방식의-첫-확장)에서 구현한다. 이 절의 모름·헷갈림·시도 이력·모바일 제안까지 이번 구현으로 포함하지 않는다.

```text
BAM.dev 소개·서비스 선택
  ├─ 학습문서로 이동 → 과목·키워드 목록 → 학습문서 (문제 복귀 없음)
  └─ 객관식 문제 풀기 → 과목·키워드 목록 → 문제 바로 시작
                           하나씩 보기 / 키워드 문제 전부 보기
                              ↓ 같은 문제카드
                       선택·모름 → 정답 확인
                              ↓
                 정답 이유 + 선택한 오답의 이유
                              ↓
            관련 개념 → 개념별 오버레이 → 학습문서의 해당 절
                              ↑                  ↓
                    선택·채점·해설·위치를 보존해 문제로 돌아가기

문서 메뉴 → 학습문서                     (문제 복귀 버튼 없음)
결과·문제 목록 → 사용자가 다시 볼 문제 선택 → 새로운 시도
```

| 화면·행동 | 제안 계약 |
| --- | --- |
| 시작·선택 | 홈에서 학습문서 또는 객관식 서비스를 선택하고 각 독립 목록에서 과목·키워드를 찾는다. 문서를 먼저 읽게 하지 않는다. 사용자가 과정과 키워드를 고른다. ‘오늘의 복습’이나 수업 일정으로 시작을 강제하지 않는다. 기존 언어·단원 route는 유지하고 신규 키워드 범위는 검증된 ID로 해석한다. |
| 키워드 문제 목록 | 과목·키워드 중심으로 단순하게 구성하고 키워드명·짧은 설명·문항 수·상태·현재 위치를 보여 준다. 단계·카테고리·진도 줄을 중복으로 쌓지 않는다. 선택 키워드가 연결된 복합문항도 포함하고 같은 문항 ID는 한 번만 세며 연결 개념을 함께 표시한다. 한 키워드의 여러 문항은 노트 수와 1:1로 맞추지 않는다. |
| 보기 모드 | 하나씩은 한 카드와 이전·다음/번호 이동, 전부 보기는 같은 카드를 세로로 배치한다. 모드 변경은 새 시도가 아니며 선택·채점·현재 카드가 유지된다. 전부 보기에서 채점 직후 카드가 필터 결과에서 사라지지 않도록 시작한 문항 범위를 고정한다. |
| 선택·모름 | 보기와 ‘모르겠어요’는 서로 배타적인 응답이다. 아직 제출하지 않은 선택은 초안이고 점수에 넣지 않는다. ‘모르겠어요’를 선택한 뒤 정답 확인으로 확정하는 방식을 제안한다. |
| 채점 | 개별/전체 채점 선택은 확정이다. 기본은 카드별 ‘정답 확인’으로 제안하고 전체 채점은 미채점 카드 중 보기 또는 모름을 명시한 항목만 제출한다. 이미 채점한 카드는 제외하고 미응답은 모름으로 바꾸지 않으며 ‘답한 n개 채점, 미응답 m개 남음’으로 알린다. 방식 전환은 초안·채점·해설을 유지한다. 중복 클릭·재로딩으로 동일 제출을 여러 시도로 저장하지 않는다. |
| 같은 화면 해설 | 정답 이유와 선택한 오답 이유를 즉시 펼친다. 정답이면 선택한 오답 영역은 없고, 모름이면 정답 이유를 보여 준다. 다른 오답의 해설은 접어 두고 원하는 때 펼친다. |
| 관련 개념 | 채점 전후 모두 열 수 있다. 복합문항에서는 개념별 제목·짧은 설명·문서 연결을 구분한다. 채점 전 개념·문서 열람은 학습 지원 사용으로 기록하며 독립 숙달로 과대평가하지 않는다. |
| 헷갈림 | 정오와 독립적인 토글로 표시한다. 제출 이후에도 현재 표시를 해제할 수 있지만 과거 제출 당시 표시를 바꾸지 않는다. |
| 재도전 | 해설 직후에는 다른 카드 상태를 유지하고 해당 문항만 새 초안으로 연다. 그동안 해당 문항은 현재 회차 집계에서 미제출이며 이전 답·해설은 과거 기록에서 확인한다. 새 제출은 이전 시도를 참조한다. 나중에 목록의 새 범위를 시작하는 동작과 구분한다. 예약·강제 반복·좋아요·싫어요는 넣지 않는다. |
| 결과 | ‘정답 C / 답한 A’, ‘전체 N중 A문제 풀이’를 먼저 보여 주고 오답/모름/헷갈림과 다음 행동을 연결한다. 총범위 점수 C/N과 최초·최근 통계는 접은 상세에서 확인하도록 제안한다. 다음에 볼 개념은 관련 링크이며 한 번 정답이나 복합문항 오답만으로 숙달·미숙을 단정하지 않는다. |

하나씩 보기·개별 채점을 기본으로 바로 시작하게 하고 보기·채점 방식 전환은 화면에서 필요할 때 바꾸도록 제안한다. 첫 진입에 필터·모드·채점 방식을 모두 고르게 하는 설정 단계를 만들지 않는다. 모바일에서는 탐색 영역을 접어 문제 본문과 주동작을 확보하고 빈 목록에는 필터 초기화를 제공한다.

### 화면 예시

교육 내용을 새로 만든 예제가 아니라 배치와 상태를 확인하는 구조 예시다. 대괄호 내용은 실제 검증 콘텐츠로 채울 자리다.

```text
JavaScript / [선택한 키워드]     하나씩 보기 | 전부 보기
전체 · 안 푼 · 푼 · 오답 · 정답       □ 헷갈림  □ 모름

문제 2 / 5   [단일 또는 복합] [행동 유형] [난이도]
[필요한 타입·코드·조건이 포함된 문제 본문]
○ A [보기]   ● B [선택한 보기]   ○ C [보기]   ○ D [보기]
○ 모르겠어요         □ 헷갈렸어요        [정답 확인]

오답 · 정답 A
정답인 이유: [A의 검증된 해설]
내가 고른 B가 틀린 이유: [B의 검증된 해설]
[다른 보기 해설 펼치기] [관련 개념] [다시 풀기]

관련 개념 오버레이                          [닫기]
[개념 1] [검증된 짧은 설명] [학습문서에서 자세히 보기]
[개념 2] [검증된 짧은 설명] [학습문서에서 자세히 보기]
```

Code Quest 참고 프로젝트는 그대로 답습하지 않고 [사용자 편의 기준](../product-scope.md#첫-학습-서비스-범위)에 맞춰 개선한다. 검색·현재 위치·상태 단서는 재사용할 수 있지만 실행기 UI·번호 점프·학습 지도·여러 진도띠를 자동 필수 도입하지 않는다. 원본 코드·브랜드·디자인 자산·서버·React/Spring/Docker·채점 계약을 가져오지 않는다. 시각 token과 대비는 [시각 설계](visual-design.md)를 따르며 이번 배치는 새 팔레트나 theme 채택이 아니다.

## 콘텐츠와 갱신

`[현재 사실]` 기존 JS 원문 세 개는 바이트 그대로 반입됐고 기존 교안·문항을 대체하지 않았다. [이전 콘텐츠 기록](../content-reviews/2026-09-09-local-review.md)은 당시 범위·해시·검증 근거다. 밤위키의 목차·계획·이동 기록과 실제 학습 본문, 출처 허용과 기술 검증, 제품 반입과 사용자 숙달은 각각 구분한다.

- bam의 교안·검증된 개념 노트를 정적 콘텐츠의 제작 재료로 사용한다. 원본은 읽기 전용으로 보존하며 [저작·관리 경계](../lesson-authoring.md#저작과-관리-책임-경계)에 따라 교육 내용의 보완은 bam에게 반환한다. 개념 오버레이의 짧은 설명도 승인된 발췌·요약 대상이며 이번 설계에서 새 교육 설명을 작성하지 않는다.
- ‘활성’이거나 공식 출처 대조 기록이 있는 개념 노트도 제품 공개 가능을 뜻하지 않는다. 개인용 노트의 source-note ID는 제작용 provenance에서 BAM conceptId에 대응시키며 기술 내용은 공개 가능한 교안·허용된 발췌와 공식 출처에 근거를 둔다. 개인 맥락·원문 경로를 제품에 그대로 옮기지 않는다.
- 제품에는 개인 비공개 기록·수업 일정 의존·공개 금지 디자인·HTML/CSS·이미지 자산을 포함하지 않는다. 학습 내용 사용 허락을 디자인 재배포 허락으로 확대하지 않는다.
- 문항의 관찰 가능한 목표·개념·모든 보기의 근거를 연결하고 단일/복합 개념 여부와 행동 유형·난이도를 분리한다. 새 문항과 의미 있는 변경에는 [A/E/C/T 설계](../learning-content-design.md)를 적용한다. 객관식만으로 직접 구현이나 T 성과를 인증하지 않는다.
- 정답·해설은 공식 출처로 검증하고 실행 결과를 묻는 코드는 명시한 버전·조건에서 실제 확인한다. 실행하지 않은 결과는 검증 완료로 적지 않는다. 기존 자료를 전체 재생성하지 않고 대표 범위 비교에서 발견한 부족분만 별도 작업으로 다룬다.
- 갱신은 원문·해시·출처·문항·기록 영향을 함께 검토하는 명시적 작업이다. 앱은 실행 중 밤위키·외부 API를 읽거나 자동 갱신하지 않는다. 제품 링크는 내부 콘텐츠 ID로 해석한다. R1 출처 UI는 밤위키 학습자료라는 설명과 반입일을 표시했으며, [주제 탐색·읽기 개선](#주제-탐색과-문서-읽기-개선)에서는 문서 상단 표시를 제거하고 목록 하단 안내로 옮겼다. 개인 보관함 경로를 출력하지 않는다. 기존 `source.originalPath`는 반입 이력 데이터로 보존하며 제작용 출처와 제품 데이터의 완전한 분리는 후속 이관 대상이다.
- `[확인 필요]` 현재 `source.originalPath` 계약은 `profile/` 상대경로만 허용하지만 밤위키는 2026-09-12에 관련 자료를 `wiki/학습자료/`로 이동했다. 과거 출처를 임의로 덮어쓰지 않고 제작용 출처·현재 위치와 제품용 표시를 분리하는 [출처 이관 제안](../content-schema.md#독립-학습문서객관식-목표-계약)을 검증한 뒤 반입한다.

## 객관식 문항 작성과 검토 기준

`[확정 결정]` 2026-09-10 bam의 사용 피드백에 따라, **구체적인 표현을 쓰고 풀이에 필요한 타입·코드·조건을 문제 안에 제시한다.** 이 기준은 앞으로 생성하거나 수정하는 객관식 문항의 작성·독립 검토에 적용한다. 아래 사례는 enum 미리보기에서 확인한 사용성 피드백이며, 기존 문제 은행 전체의 수정·검증 완료를 뜻하지 않는다.

| 기준 | 작성 방법과 검토 질문 |
| --- | --- |
| 첫 독해에서 요구 파악 | 문장의 첫 부분에 판단 대상과 주어진 행동을 쓰고, 무엇을 고르는지(출력값·반환값·최종 상태·적용할 동작·오류 이유)를 명시한다. “올바른 것은?”만 쓰지 않는다. 사람이 본문을 한 번 읽고 무엇을 판단해야 하는지 자신의 말로 바로 설명할 수 있는가? |
| 구체적으로 읽히는 표현 | 추상적인 용어만 나열하지 않고 대상·값·행동이 드러나는 문장으로 쓴다. 용어 자체가 학습 목표라면 쉬운 상황이나 예시를 함께 둔다. 입문자가 보기를 읽고 무엇을 뜻하는지 구체적인 상황으로 설명할 수 있는가? |
| 문항 안에 필요한 전제 제공 | 풀이에 영향을 주는 타입 선언, 관련 코드, 입력값과 조건을 제시한다. `Category`라는 이름만 보고 enum이라고 추측하게 하지 않는다. 버전·실행 환경에 따라 답이 달라질 때만 그 조건도 명시한다. 이전 문제, 대화 또는 숨겨진 프로젝트 파일을 보지 않아도 판단할 수 있는가? |
| 전제와 정답의 분리 | 판단에 필요한 정보만 제공하고, 묻는 반환값·동작·선택 이유를 설명이나 주석으로 미리 알려주지 않는다. 전제를 읽은 뒤에도 목표 개념을 적용해 답해야 하는가? |
| 비교 가능한 선택지 | 네 선택지는 같은 질문에 답하는 병렬 문장·같은 결과 단위와 비슷한 구체성으로 작성한다. 정답은 정확히 하나이며 모든 보기에 해당 조건에서 맞거나 틀린 이유를 쓴다. 실제로 혼동할 법한 오답을 쓰되 모호한 범위·중복 표현·제시하지 않은 전제 때문에 복수 정답이 되지 않게 한다. |
| 개념을 적용하는 상황 유지 | 단순 정의 확인과 함께 배운 개념을 달라진 상황에 적용하는 문항을 둔다. 긍정적 피드백을 받은 enum과 switch의 조합처럼 개념 사이의 연결을 판단하게 하되, 그 조합을 모든 문제에 강제하지 않는다. |

### 2026-09-10 enum 미리보기 피드백

| 항목 | 사용자 관찰 | 반영 기준과 전후 사례 |
| --- | --- | --- |
| 1번 문항의 1번 보기 | 무슨 말인지 확실히 와닿지 않는다. | 이전: “가능한 값을 정해진 상수 집합으로 표현하기 위해”. 개선 예: “도구의 분류를 NOTE, PRACTICE, REFERENCE처럼 미리 정한 값 중 하나로 나타내기 위해”. 어려운 용어를 더하는 대신 실제 분류와 후보 값으로 의미를 드러낸다. |
| 2번 문항의 전제 | `Category.values()`의 반환값을 묻기 전에 `Category`가 enum임을 알려야 한다. | 이전: 타입 선언 없이 `Category.values()`의 반환값을 질문. 개선 예: “다음과 같이 선언한 enum `Category`에서 `Category.values()`를 호출하면 무엇을 반환할까요?”와 아래 선언을 함께 제시한다. 반환값 자체는 전제에 설명하지 않는다. |
| 3번 문항 | 좋은 문제라는 긍정적 피드백. | enum과 switch를 함께 적용하는 상황형 문항의 방향을 유지한다. 모든 문제를 같은 형식으로 복제하거나 현재 문제 은행 전체가 검증됐다는 근거로 사용하지 않는다. |

2번 문항에 제공할 전제 코드 예시:


### 다음 문제에 반영하는 절차

1. 콘텐츠 생성자는 새 객관식을 만들거나 수정하기 전에 이 절과 해당 학습 목표·교안을 읽는다. 생성 요청에 이 기준의 링크를 포함한다.
2. 사용자가 문제 표현·누락된 전제·해설 등에 불편을 말하면 날짜, 대상 문항의 안정 ID(없으면 화면·주제·문항 번호), 관찰한 불편, 개선 기준과 예시를 이 정본에 남긴다. 이후 적용과 기존 문항 수정 여부는 구분한다. 일회성 대화 답변이나 미리보기 수정만으로 처리 완료로 삼지 않는다.
3. 콘텐츠 생성자는 인계 시 이 기준에 따른 자체 확인과 해당 피드백이 관련 문항에 어떻게 반영됐는지 남긴다. 독립 `content_validator`는 전제의 충분성, 정답 노출 여부, 표현의 명확성, 정답의 유일성과 선택지별 근거를 문항별로 확인하고 모호하면 수정을 요청한다.
4. 문서에 규칙을 기록했다는 사실, 새 문항에 적용했다는 사실, 기존 문항을 수정·검증했다는 사실을 각각 구분해 보고한다. 기존 문항은 실제 검토·수정한 범위만 완료로 기록한다.

## 풀이 기록과 집계

이 절은 `[제안]`이며 저장 필드의 정본은 [콘텐츠와 풀이 기록 계약](../content-schema.md#풀이-기록과-세션-계약-제안)이다. 현재 구현된 완료 세션 저장을 문제별 시도 이력으로 이미 이관했다고 해석하지 않는다.

미응답·선택 중·제출한 모름을 구분한다. 제출하면 불변 시도를 추가하고, 다시 풀기는 이전 시도를 참조하는 새 시도다. 같은 문제에 다시 답해도 최초 기록을 수정하지 않는다. 현재 헷갈림 표시는 변경할 수 있고 제출 당시 헷갈림·학습 지원 열람 여부는 해당 시도에 남긴다.

| 조회 기준 | 제안 의미 |
| --- | --- |
| 전체 | 선택한 키워드 범위의 고유 문항 전체 |
| 안 푼 / 푼 | 현재 문항 버전의 제출 시도가 없음 / 하나 이상 있음. 단순 선택은 안 푼 상태 |
| 오답 / 정답 | 현재 버전의 최근 제출 결과가 오답 / 정답. 모름은 별도 상태 |
| 헷갈림 / 모름 | 헷갈림은 현재 표시, 모름은 현재 버전 최근 제출 결과. 보조 필터 두 개를 함께 고르면 OR, 기본 탭과는 AND로 결합 |
| 최초·최근 | 접은 기록 상세에서 같은 문항·버전의 최초/최근 제출을 나란히 제공. 이력이 부족하면 ‘기록 없음/이전 버전’으로 표시하며 최초 정답을 추측하지 않음 |

한 번 시작한 범위는 고유 문항 `N`개로 고정한다. 그 세션에서 제출한 문항 수(모름 포함)를 `A`, 정답 수를 `C`라 할 때 완료율은 `A/N`, 제출 답 정답률은 `C/A`, 점수는 `C/N`이다. `A`는 모든 재도전 이벤트 수가 아니다. 즉시 문항 재도전 중에는 해당 현재 결과를 비우므로 A·C가 그 문항의 기여만큼 감소할 수 있고, 새 제출 뒤 한 문항의 결과로 다시 반영한다. N과 다른 문항 결과는 유지하며 이전 결과는 과거 기록에 보존한다. 분모 0은 `—`로 표시한다. 미완료 점수에는 ‘진행 중’을 붙인다. 예를 들어 5문항에서 정답 2·오답 1·모름 1·미응답 1이면 완료 4/5, 제출 답 정답률 2/4, 진행 중 점수 2/5다. 모름은 완료에 포함하지만 정답 점수는 0이며 미응답은 제출 집계에서 제외한다. 계산 계약과 화면 우선순위는 구분한다. 세 통계를 모두 전면 노출하지 않고 ‘정답 C / 답한 A’와 ‘전체 N중 A문제 풀이’를 주 표시로 삼으며 총범위 점수 C/N과 최초·최근 통계는 접은 상세로 제공한다.

관련 개념별로 연결된 문항 수·재확인 링크는 보여 줄 수 있다. 복합문항 한 개의 오답을 모든 연결 개념의 미숙 판정으로 복제하지 않는다. 문제별 시도의 최초·최근과 ‘현재 버전’·‘전체 과거 기록’은 표시를 구분하며 근거 없이 숙달률을 만들지 않는다.

문제는 정상 운영에서 자주 바꾸지 않는다. 오류 교정 때는 문구 변경도 revision으로 추적하고 평가 의미 변경 여부를 따로 기록하는 방식을 제안한다. 과거 점수를 현재 정답으로 재채점하지 않는다. 평가가 바뀌면 이전 버전 기록임을 표시하고 현재 문제 다시 풀기는 사용자가 선택한다. 해당 버전의 본문·해설을 보관하지 못한 경우에는 ‘당시 해설 없음’을 표시해 현재 해설이 당시 근거처럼 보이지 않게 한다. 정확한 보관량·버전 정책의 선택은 [로드맵](../roadmap.md#bam-결정-대기-목록)에 남긴다.

## 저장·문서 복귀·실패 상태

`[현재 사실]` R1은 별도 review-session 저장소 뒤에서 활성 세션 하나를 보존하며 기존 `ProgressRepository`의 완료 기록을 유지한다. `[제안]` 아래는 이후 문제별 제출·버전 이력까지 확장할 계약이다. 콘텐츠와 사용자 상태는 분리하며 다른 제품의 진도 배열·저장 키는 초기화하지 않는다. 같은 브라우저 프로필·origin의 새로고침과 재실행에서 복구한다. `localhost`·`127.0.0.1`, 다른 포트·프로필은 서로 다른 저장소이며 원격 동기화·기기 간 자동 이동을 추가하지 않는다.

시도 추가와 세션의 제출 결과 참조는 한 저장 갱신 또는 안정된 제출 ID로 일치시켜 새로고침으로 중복 시도를 만들지 않는다. 문서 이동 직전에 세션 ID, 고정 문항 ID·버전·순서, 모드·필터, 현재 문제, 선택·채점·펼친 해설·헷갈림, 카드 기준 스크롤 위치·offset, 돌아올 초점과 내부 복귀 문맥을 저장한다. 문서→문제는 같은 상태를 복원하고 채점 기록을 다시 추가하지 않는다. 문서 자체의 새로고침도 유효한 복귀 문맥을 보존한다.

‘문제로 돌아가기’는 **실제로 문제에서 생성된 내부 복귀 토큰이 있고 해당 세션·문항을 복원할 수 있을 때만** 표시한다. 보관된 세션이 있더라도 문서 메뉴·직접 URL로 들어오면 표시하지 않는다. 임의 외부 return URL은 받지 않는다. 토큰·세션이 만료·누락됐으면 가짜 복귀 대신 일반 문제 목록 연결과 복구 불가 이유를 제공한다. 기존 단원·언어 해시 URL은 계속 유효하게 유지한다. `#/` 홈, `#/learn` 문서 목록, `#/review` 문제 목록과 기존 깊은 URL은 R1에 구현됐다. 빈 hash도 홈으로 열며 기존 문서·단원 URL의 도착 대상을 보존한다.

| 경계·실패 | 제안 처리 |
| --- | --- |
| 세션 중 문항 갱신 | 시작한 버전으로 계속 풀 수 있으면 고정한다. 구버전 콘텐츠가 없으면 해당 문항을 중단하고 기존 기록을 보존한 채 현재 버전 새 시도를 안내한다. 분모·정답을 조용히 교체하지 않는다. |
| 문항·문서·앵커 없음 | 누락 대상을 알리고 안전한 목록 또는 해당 문서 시작으로 이동한다. 누락을 0점 완료나 전체 범위로 대체하지 않는다. |
| 저장 차단·용량 초과 | 메모리 상태로 계속할 수 있음을 알리고 재실행 복구가 보장되지 않음을 표시한다. 저장 성공을 꾸미거나 과거 기록을 무통보 삭제하지 않는다. |
| 다중 탭 충돌 | 같은 활성 세션의 외부 변경을 감지하면 새 기록을 덮어쓰지 않고 이어 받을 상태를 안내한다. 제출 ID 중복 제거와 저장 버전 확인으로 이중 제출·기록 소실을 방지하는 방향을 검증한다. 구체 충돌 UI는 구현 전 focused 설계 대상이다. |
| 잘못된 콘텐츠·응답 | 경로·JSON·참조·선택지 계약 실패와 미응답 안내를 분리한다. 앱 오류는 오답·모름으로 저장하지 않는다. |
| 새 범위 시작 | 미완료 활성 세션이 있으면 ‘이어서 풀기’와 ‘새 범위 시작’을 구분한다. 새 범위를 선택해도 이미 제출한 기록은 보존한다. |

원문과 출처 텍스트를 안전하게 렌더링하고 내부 ID·앵커만 허용된 링크로 변환한다. 핵심 문서·문항·개념 요약은 준비된 로컬 정적 자산만 사용하고 공식 출처의 원문 열기는 선택적 네트워크 동작이다. 사용자 비공개 자료를 런타임에 불러오지 않는다.

## 접근성·모바일

`[현재 사실]` R1은 네이티브 라디오 그룹·문제 제목 연결, 펼침 상태가 전달되는 해설 버튼과 이름 있는 네이티브 모달을 사용한다. 아래 키보드·좁은 화면의 실제 검증 범위는 R1 작업 카드에 둔다. `[제안]` 후속 헷갈림은 독립 체크박스로 제공한다. 정오·모름·저장 실패는 색뿐 아니라 텍스트와 상태 안내로 표현하고 채점 후 결과 영역에 예측 가능한 초점을 준다.

개념 오버레이는 이름 있는 모달로 열어 초점을 내부에 제한하고 배경 상호작용을 막는다. 닫기·Esc·배경 클릭을 지원하며 닫으면 열었던 관련 개념 버튼으로 초점을 돌린다. 문서 왕복은 해당 문제카드의 위치와 초점으로 돌아간다. 좁은 화면에서는 화면 폭에 맞는 대화상자로 사용하고 본문·보기는 줄바꿈, 긴 코드는 카드 안에서만 가로 스크롤한다. 320px·390px와 데스크톱, 키보드만의 전체 흐름에서 잘림·초점 유실을 확인한다. 대비와 focus의 정확한 기준은 [시각 설계](visual-design.md#대비와-색상-사용-계약)가 정본이다.

## 첫 사용 범위의 완료 기준

`[제안]` [우선 완성 순서 R1~R4](../roadmap.md#학습문서객관식의-우선-완성-순서)에 따라 홈과 학습문서·객관식 독립 진입을 먼저 완성한다. 기존 반입 JS 묶음은 기능 검증의 내부 시작 재료 제안이며 첫 제품 제공 범위를 제한하거나 별도 사용자 선택 gate로 만들지 않는다. 이미 제공하는 문항을 재생성하지 않는다. R1 기능 구현 전에는 오버레이·문서 왕복에 쓸 최소 기존 개념, 승인된 발췌와 문서 절 참조를 먼저 확인한다. R3는 이 기반을 바탕으로 복수문항·단일/복합 대표 범위를 넓혀 검증한다. 단일·복합 관계를 실제로 확인할 최소 대표 묶음이 필요하고, 복합문항이 없거나 연결이 부족하면 향후 별도 콘텐츠 작업에서 검증해 보완한다.

| 검증 영역 | 완료 증거 |
| --- | --- |
| 홈·선택·두 모드 | 홈에서 원하는 서비스로 바로 이동하고 과목·키워드만으로 자료·문제를 찾음. 필수 설정 단계 없이 시작하며 키워드에 연결된 단일·복합 문항을 중복 없이 선택하고 모드를 바꿔도 선택·채점·현재 위치가 유지됨 |
| 피드백·자율 상태 | 정답·선택한 오답 이유, 다른 보기 펼침, 명시적 모름·헷갈림과 즉시/나중 재도전이 의도대로 동작함. 전체 채점을 포함하는 단계에서는 채점 방식 전환의 상태 유지와 이미 채점·미응답 제외도 검증. 개별 선행 완료에서는 전체 채점 항목을 미적용·후속 미완료로 명시 |
| 문서 왕복 | 채점 전·후 오버레이→해당 문서 절→정확한 문제 상태 복귀. 문서 직접 진입에는 복귀 버튼이 없고 새로고침 후도 판별됨 |
| 기록·집계 | 미응답·선택·모름·정오답을 구분하고 최초/최근·버전·필터와 0분모·미완료 분모 예시가 일치함. 중복 제출·재도전이 과거 시도를 수정하지 않음 |
| 보존·오류 | 기존 완료 기록·오답·다른 기능 진도 보존, v1 읽기 이관, 누락 콘텐츠·버전 변경·저장 차단·다중 탭 대표 실패의 복구와 정직한 안내 |
| 사용성·오프라인 | 키보드만으로 전 흐름, 320px·390px·데스크톱의 긴 제목·보기·코드, 모바일 탐색 접기·빈 필터 초기화·명확한 주동작·현재 위치·저장 여부, 모달 닫기/초점 복구, 준비된 정적 자산의 외부 네트워크 없이 사용 증거 |
| 콘텐츠·통합 | 실제 바뀐 자료만 출처·본문·ID·목표·정답·오답 근거를 독립 확인. 필요한 focused 검사 뒤 작업 묶음 최종 상태에서 독립 `project_integrator`의 `npm run check`와 적용 가능한 브라우저 검증 |

R1의 개별 채점 기반 사용 가능, R1~R3의 대표 흐름 완성, 전체 채점 추가 완료를 나누어 보고한다. 사용자가 허용한 지연 사유로 전체 채점을 뒤로 미뤄도 개별 선행 단계의 완료를 막지 않지만, 전체 채점 기능은 후속 미완료로 남기고 두 방식 제공 완료를 주장하지 않는다.

R1 검증은 위 전체 목표의 PASS가 아니다. R1 밖의 보기 모드·전체 채점은 [후속 작업 카드](../work-items/2026-09-14-review-display-and-grading.md)에서 별도 판정하며 모름·헷갈림·문제별 이력·복합 관계는 후속 미완료다. 전과목 대량 반입·전체 감사·설치 패키지·Java runner·React 이관·외부 웹과제는 이 첫 사용 범위의 선행 gate로 끌어오지 않는다. 각 기존 제품 결정은 해당 작업 착수와 설치형 MVP 전체 완료 시 그대로 적용된다. 미결정의 정본은 [로드맵](../roadmap.md#bam-결정-대기-목록)이며 확정된 요구를 다시 질문하지 않는다.
